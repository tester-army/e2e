# RFC0001: e2e v2 — the agentic testing framework on the TesterArmy engine

Status: draft for review (Oskar, Szymon, Krzysztof)
Supersedes: RFC0000 (`RFC.md`) and `PLAN.md` as implementation direction.
The v1 spec survives selectively — see "What we keep" below.

## Summary

e2e is the framework for building testing agents. It ships four layers:

1. **An API to write tests the agentic way** — `test()`, `agent.act()`,
   `agent.assert()`, `agent.login()`. No selectors, no deterministic authoring
   tier in v0: determinism is *compiled by the cache*, not written by hand.
2. **A tool vocabulary** — `ui_click`, `ui_select`, `ui_type`, … for **web and
   mobile**, executed through swappable backends. The framework owns what a
   tool *means*; the backend owns how it lands on a device.
3. **A harness** — a simple, extendable public build of TesterArmy's
   `test-runner`: step lifecycle, budgets, the run ledger → report, and the
   **adaptive cache** (capture on success, zero-turn replay, escalate to the
   agent on divergence, recapture — stored locally in `.e2e/cache/`).
4. **A brain socket** — the agent, model, and prompts are the builder's.
   e2e ships a deliberately simple example agent; TesterArmy's production
   agent is a private package that implements the same interface.

Kitchen public, recipes private. Anyone can build their own testing agent on
e2e; anyone who doesn't want the struggle runs ours — one config line either
way, and the tests survive the swap in both directions.

## Why v2

v1 tried to build everything from scratch — its own runner, agent, cache, and
driver — and stalled the moment the production platform needed attention. v2
inverts the approach: **extract, don't rewrite.** The monorepo's engine
(`@testerarmy/test-runner` + `qa-tools` + `snapshot`) is proven under
customers, runs web *and* mobile, and now includes adaptive action caching
live in production (measured: 19.9s agentic → 1.19s zero-turn replay). e2e v2
is that engine, packaged with a public API and a private brain.

This is the Next.js posture: rigidly opinionated about the harness (lifecycle,
actions, cache, reports), completely unopinionated about the sauce (your
agent, your model, your prompts).

## Layer 1 — the test API

```ts
import { test, agent, credentials } from 'e2e';

test('member upgrades to Pro', async () => {
  await agent.login(credentials.user('member'));
  await agent.act('open billing settings and upgrade to the Pro plan');
  await agent.assert('the billing page shows Pro as active');
});
```

- `agent.act()` semantics are TesterArmy's current autonomous step: one prose
  instruction, driven to completion by the executor within harness budgets.
- Step kinds mirror the platform's existing vocabulary (`act`, `assert`,
  `login`, `files`, `screenshot`, `javascript`) so dashboard-native tests and
  code-native tests are the *same program in two forms*. Dashboard tests
  remain first-class in the platform with no e2e requirement.
- **Deliberately absent in v0:** `screen.getByRole()`-style locators and
  `expect` matchers. The stance, stated in the docs as a feature: *you never
  write selectors — first runs are agentic, repeat runs replay from cache.*
  The v1 locator/expect engine stays on the shelf if the market demands a
  hand-written deterministic tier later.

## Layer 2 — tools over backends

- The **vocabulary** (`ui_click`, `ui_select`, `ui_type`, `press`, `scroll`,
  `navigate`, `upload`, …) is framework-owned, versioned, and closed-ish. It
  is the grammar that budgets, secret gating, cache entries, replay, and
  reports are defined over. No shared vocabulary ⇒ no caching harness.
- The **backend SPI** owns execution: Playwright ships as the default web
  backend; mobile backends follow the same contract (this is `qa-tools`'
  existing contracts/backends architecture, published). Backends are
  swappable without invalidating cache entries — entries record intent
  (target + value), not mechanism.
- **Extensions:** builders may register namespaced extension tools, under one
  rule — an extension declares its semantics (replayable? mutating?
  secret-touching?) or it is cache-excluded and untrusted by default.
  Extension tools are **AI SDK `tool()` definitions plus an e2e semantics
  annotation** — schema, description, and `execute` exactly as the ecosystem
  already writes them, wrapped once (`defineTool(aiSdkTool, { replay, mutates,
  secrets })`). Extending e2e's tool surface should feel identical to adding a
  tool to any AI SDK agent, because it is.
- **Extensions are project capabilities, not test-run plumbing.** The same
  definition is served to the dev-loop MCP (`e2e mcp`), so the coding agent
  building the feature gets `airplane_mode` or `simulate_gravity` alongside
  the vocabulary — one tool, every agent, the same annotations enforced
  everywhere. A project's `e2e/tools/` directory is its testability surface,
  and `e2e mcp` is effectively an auto-generated, app-specific MCP server.
- **Private tools:** TesterArmy's model-facing surface — tool descriptions,
  per-turn gating, composite tools (scene understanding, wait-with-judge,
  issue reporting with veto), vision arsenal — stays in the private agent
  package. The public vocabulary is grammar; the presentation layer is sauce.

## Layer 3 — the harness and the adaptive cache

The public runner is a simplified, extendable build of
`@testerarmy/test-runner`: plan/dispatch, step lifecycle, budgets, retries,
and the append-only run ledger emitted as the local report (the same format
the TesterArmy cloud will store as the run receipt).

The adaptive cache ports from the platform as a harness capability:

- capture successful actions per step (framework-owned entry format);
- store locally under `.e2e/cache/` (a store interface, so the TesterArmy
  cloud's shared cache can replace the filesystem without the agent noticing);
- replay zero-turn on repeat runs; on divergence, **flow back to the agent**
  mid-step, let it drive, and recapture — the adaptive loop exactly as it
  runs in production today;
- CI defaults to read-only cache; committed caches are untrusted input.

## Layer 4 — the brain socket

The socket is the **step executor**: given a step, the tool surface, and the
session, drive the step to completion within budgets. Everything a builder
wants to own — the loop, the model, the prompts, the judgment — lives behind
this interface. The harness owns everything around it.

- **Design principle: AI SDK native at the edges, e2e-owned at the seam.**
  Everything a builder touches is idiomatic AI SDK: the model slot accepts any
  AI SDK `LanguageModel` (any provider, the gateway, middleware-wrapped),
  tools are AI SDK `tool()` shapes, and the golden path for defining a brain
  is an AI-SDK-style agent config:

  ```ts
  import { createAgent } from 'e2e/agent';

  export default createAgent({
    model: anthropic('claude-sonnet-5'),  // any AI SDK model
    system: myPrompt,                     // your sauce
    tools: { ...myExtensionTools },       // merged with the e2e vocabulary
  });
  ```

  Building a testing agent on e2e should feel like writing AI SDK code you
  already know — because it is. `@testerarmy/agent` is the same shape with a
  much bigger config; the example agent is the same shape with a tiny one.
- The seam itself — the step-executor interface (step in → verdict + ledger
  out) — **is owned by e2e**, not the AI SDK: `createAgent()` returns an
  executor, but a hand-rolled executor that never touches the AI SDK is
  equally valid. Two reasons: the AI SDK moves fast (the monorepo pins
  `ai@7.0.84` for deploy safety today — a public contract can't inherit that
  churn), and cache/security semantics attach at the e2e layer, which the AI
  SDK has no concept of. AI SDK is a `peerDependency` with a tested range,
  isolated behind the `e2e/agent` adapter so a major bump is our migration,
  not every builder's.
- `@testerarmy/agent` (private, closed-license npm): the production executor —
  prompt corpus, healing, vision, judges. Implements the public interface
  with no backchannel into the runner. If it needs one, the framework is
  broken; fix the interface.
- **Public example agent:** a minimal executor (~150 lines, BYO model key),
  clearly and intentionally weaker than TesterArmy's, scaffolded via
  `create-e2e-agent`. It is a starting dough meant to be forked, the proof the
  socket has two implementations, and the executable fixture for conformance.

## The public/private line

| Public (e2e) | Private (TesterArmy) |
|---|---|
| Test API, config, CLI | Prompt corpus, step policy, judges |
| Tool vocabulary + backend SPI (web, mobile) | Model-facing tool surface, vision arsenal |
| Harness: lifecycle, budgets, ledger/report | `@testerarmy/agent` (closed npm) |
| Adaptive cache: format, local store, replay | Cloud: hosted runs, receipts, devices/leases, shared cache, PR verdicts, dashboard |
| Example agent + `create-e2e-agent` | Everything tuned per customer |

Leak rules: prompts, judges, and behavior heuristics never cross into a
public package; public packages contain interfaces, formats, and shells;
the license — not obfuscation — is the wall (local-first means the private
package is technically inspectable; we accept that consciously).

## Business model

Build-vs-buy on one substrate. Companies that want to build their own testing
agent get the ingredients free — they were never going to buy the agent, and
on e2e they become ecosystem instead of from-scratch competitors. Companies
that don't want the recurring struggle (models drift, sites change, edge cases
accumulate) run `@testerarmy/agent`: one config line to adopt, one to leave,
tests portable in both directions. That portability is the trap door *and* the
anti-lock-in guarantee.

Three revenue lines, in order of arrival:

1. **The agent** — `@testerarmy/agent` for everyone who doesn't want the
   struggle.
2. **The devices** — leased remote browsers/simulators for local runners
   (the Linux-developer-testing-iOS case), metered, agent-agnostic.
3. **The infra** — *Vercel for testing agents*: bring your own executor and
   deploy it on our cloud. The customer uploads an execution bundle (their
   brain + config + tests); we supply devices, parallelism, the harness with
   the shared cache, secrets brokering, receipts, PR verdicts, schedules, and
   monitoring. We are indifferent at this layer — we win whenever tests run,
   whoever's brain runs them. Building an agent is a weekend of fun; running
   a device fleet, a receipt store, and PR plumbing is a career — the DIY
   segment self-selects into exactly the customers who need this. v1's
   `spec/roadmap/cloud.md` (execution bundles, OIDC identity, isolation,
   brokered secrets) survives as the design sketch for this profile. The
   hard prerequisite is sandboxed execution of untrusted executor code in
   our workers; not v0, but the socket architecture is what makes it
   possible at all.

Requirement this places on us: **the public benchmark.** Our agent must
visibly, continuously win on a shared yardstick (the web-benchmark bug-book
suite, published). The agent-quality flywheel — evals, benchmark CI, verdict
accuracy — is the pricing power. The moat is the pace of the kitchen, not the
secrecy of the recipes.

## What we keep from v1, what we retire

**Keep:** the npm name `e2e` (+ `@e2edev` scope), the release plumbing
(changesets, trusted publishing, SHA-pinned CI), the fern docs site, the
spec's security/cache/budget chapters — demoted from "contract for a new
engine" to requirements and conformance fixtures for the extracted one — and
the lean v1 agent as the seed of the public example agent.

**Retire:** the v1 runner and agent internals; PR #83 (close with a note —
the production `qa-agent` *is* the planning tier); the deterministic
locator/expect engine (shelved, not deleted); the "open standard" framing
until a conformance suite can actually verify a third-party implementation.

## v0 plan

Quiet release to existing TesterArmy customers first — they have keys and
asked for tests-in-code; they validate the API with zero community overhead.

Build list (mostly packaging):
1. Monorepo hygiene: `qa-tools`, `snapshot`, CLI into root `test`/`typecheck`.
2. Formalize the step-executor interface at the seam where `run-streams.ts`
   already branches; `qa-agent` becomes its first private implementer.
3. Publish the engine packages from the monorepo (one source of truth — the
   e2e repo consumes, never copies).
4. Local cache store (`.e2e/cache/`) and local report output for the harness.
5. `e2e` package: API + config + CLI shell; `create-e2e-agent` scaffold.
6. Local MCP ships inside `e2e` (web now; mobile = local simulator where
   available, leased remote device where not) — driver tools free, agentic
   tools light up with a TesterArmy key.

Public moment (separate decision, later): example agent green on the v1
testbeds with a BYO key; license finalized (lean: fair-source/FSL, converting
to open later); benchmark published; a named owner for the repo week to week.

## Open questions

1. License final call at the public moment: fair-source vs Apache-from-day-one.
2. Package naming: engine packages under `@e2edev/*` or `@testerarmy/*`.
3. Mobile in the local MCP v0: local simulator only, or leases from day one?
4. Criteria for un-shelving the deterministic tier (demand signal, not vibes).
5. Cloud hosting of third-party executors ("Vercel for testing agents"):
   direction affirmed as revenue line 3 — open question is timing and the
   sandboxing approach, not whether.
