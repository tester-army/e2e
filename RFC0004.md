# RFC0004 — Data-defined tests as a first-class value

Status: draft. Motivated by the embedding-host surface (`e2e/run`, RFC in the
host-surface PR): a platform stores tests as data rows, not files, and today
must generate one suite file per run to feed the runner.

## Problem

A test in e2e is a file: `collect` discovers files by the config `tests` glob,
imports each module, and derives identity from the file path — `file`,
`absolutePath`, and `source` location flow into `TestIdentity`
(`packages/e2e/src/collect/collect.ts`), which keys the trace cache and names
every report row. A host whose tests live in a database (a `kind` + a
natural-language instruction per step) has no file. The working path today is to
materialize the rows into a `*.e2e.ts` source and write it to disk before the
run (the TesterArmy materializer,
`apps/website/lib/services/run-executor/e2e-engine/materialize.ts`, does exactly
this). That works, and it stays the supported path until this lands, but it
forces temp-file management, a filesystem the host may not want, and a file
identity that does not correspond to anything the host stored.

## Goal

Let `run()` accept tests as values, with stable file-less identity, so a host
streams a run straight from its rows — no disk, no glob — while a file-based
project is completely unchanged.

## Design sketch

### The value

`RunOptions` gains a `suite` alternative to file discovery:

```ts
interface ProgrammaticTest {
  readonly title: string;
  /** Stable identity the host owns; keys the trace cache and names the report. */
  readonly id: string;
  readonly fn: TestFunction; // same ({ web, agent, screen, ... }) => Promise<void>
  readonly annotations?: { readonly tags?: readonly string[] };
}
run({ suite: ProgrammaticTest[], /* no `tests` glob */ });
```

`suite` and a file `tests` glob are mutually exclusive per run. When `suite` is
present, `collect` skips discovery and builds `CollectedTest`s directly from the
values.

### Identity without a file

`TestIdentity` currently requires `file`. This RFC makes the identity source a
union: a file location **or** a host-owned `id`. The trace-cache key
(`cache/identity.ts`) already hashes `testId`; it switches from
"project + file + title" to "project + identity", where identity is the file
path today or the host `id` under `suite`. The report row carries the `id` in
place of `file`. `app.identity` (added in the host-surface PR) already
establishes the precedent that logical identity, not physical location, keys the
cache; this extends the same idea to the test.

### Data steps, later

A host still writes `fn` as code today (the materializer generates it). A
follow-on may accept steps as data directly —
`{ steps: [{ type: 'act', instruction }, { type: 'assert', instruction }] }` —
and build `fn` from a built-in interpreter, making the data form fully
round-trippable (the "prebuild/eject" idea). That interpreter is out of scope
here; this RFC delivers the file-less value and identity, which is the blocker.

## Phasing

1. **File-less identity.** Make `TestIdentity` source a union and thread it
   through the cache key and report. No API change yet; internal.
2. **`run({ suite })`.** Accept programmatic tests; `collect` builds from them.
   Mutually exclusive with the `tests` glob.
3. **Data steps + interpreter.** The round-trippable data form.

## Interim

Until phase 2, generating one suite file per run is the supported path and is
what the TesterArmy materializer does. Nothing here blocks the web integration;
it removes temp-file management and gives the report rows the host's own ids.

## Non-goals

- Changing file-based collection. A project with a `tests` glob is untouched.
- The data-step interpreter (phase 3), which is a separable feature.
