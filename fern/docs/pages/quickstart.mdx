<Callout intent="note">
Requires Node.js 20.19 or newer.
</Callout>

<Steps>
  <Step title="Initialize">
    <CodeBlocks>
      ```bash title="npm"
      npx @e2edev/e2e@beta init
      ```
      ```bash title="pnpm"
      pnpm dlx @e2edev/e2e@beta init
      ```
    </CodeBlocks>

    Init adds the runner to `devDependencies`. For this guide, select
    **Playwright**, keep **AI testing** enabled, and confirm installation. This
    also adds the browser engine and AI SDK v7. You can skip either optional
    package: without an engine, the example checks an HTTP response; without
    AI, the generated files make no model calls.

    Config and test files are ES modules. In an empty directory, `init` creates
    a private `package.json` with `"type": "module"`. An existing `package.json`
    keeps its module type; `init` prints `npm pkg set type=module` so you can
    opt in, which also changes how the package's existing `.js` files run.

    For mobile tests, choose **agent-device** instead. Init defaults to iOS on
    macOS and Android elsewhere, and writes a Settings example; see
    [Device](/reference/device) for simulator and emulator setup.
  </Step>

  <Step title="Define your agent">
    With Playwright and AI selected, init writes this config:

    ```ts title="e2e.config.ts"
    import type { E2EConfig } from '@e2edev/e2e';
    import { createAgent } from '@e2edev/e2e/agent';
    import { playwright } from '@e2edev/playwright';

    export default {
      agent: createAgent({
        system: 'You are a thorough QA agent. Verify every outcome.',
      }),
      // The engine declares the app it drives; APP_URL overrides the default at run time.
      targets: [{ name: 'web', platform: 'web', engine: playwright({ url: process.env.APP_URL ?? 'http://localhost:3000' }) }],
    } satisfies E2EConfig;
    ```

    Set `APP_URL` when running tests, or edit the default `url` passed to
    `playwright()`. A scheme is optional: `localhost:3000`
    becomes `http://localhost:3000` and `app.example.com` becomes
    `https://app.example.com`. The runner knows no platform, so every target
    names the engine that drives it, and the engine declares the app under
    test: a URL for a browser, a bundle id for a device.

    `system` shapes how it works. Later you can hand it your own tools, or
    replace it with a custom executor; [Your own agent](/agents) covers both.

    The model comes from the `E2E_MODEL` environment variable as a
    `provider/model-id` string, routed through the Vercel AI Gateway so one
    `E2E_MODEL_API_KEY` reaches any provider. To use a provider directly, pass
    an AI SDK model instance: `createAgent({ model: openai('gpt-5.4-mini') })`.

    The runner can also start your dev server for you; see
    [Let the runner start your app](#let-the-runner-start-your-app) below.
  </Step>

  <Step title="Write a test">
    Test files match `tests/**/*.e2e.ts`.

    ```ts title="tests/signup.e2e.ts"
    import { test } from '@e2edev/playwright';
    import { expect } from '@e2edev/e2e';

    test('a visitor signs up for a trial', async ({ app, agent, screen }) => {
      await app.open('/');

      await agent.act('sign up for a free trial as {name} with email {email}', {
        name: 'Ada Lovelace',
        email: 'ada@example.test',
      });

      await agent.assert('the welcome screen greets Ada by name');
      await expect(screen.getByRole('status')).toContainText('trial');
    });
    ```

    Import `test` from `@e2edev/playwright` when a test touches the `web`
    fixture: it is the same runtime `test` as `e2e`'s, typed with the fixture
    the browser engine contributes. One goal per `act`. Real values go through
    `params`, not through the instruction. The final `expect` is deterministic: it costs no model calls
    and cannot vary. There are no waits or sleeps anywhere: queries poll,
    actions wait, assertions retry.
  </Step>

  <Step title="Run">
    ```bash
    E2E_MODEL=anthropic/claude-sonnet-4.5 E2E_MODEL_API_KEY=... npx --no-install e2e run
    ```

    Missing browsers download automatically on the first run.

    ```bash
    npx --no-install e2e run tests/signup.e2e.ts   # one file
    npx --no-install e2e run --tag smoke           # by tag
    npx --no-install e2e run --headed              # watch it happen
    npx --no-install e2e run --debug               # save full agent transcripts
    npx --no-install e2e run --ai-trace            # record every model call for a trace viewer
    ```

    Every run writes `.e2e/report.json`: results, attempts, steps, artifacts,
    and model usage. Exit codes separate test failures (1) from configuration
    (2) and infrastructure (3); blocked agent steps land in the latter two.
  </Step>
</Steps>

## Let the runner start your app

Instead of starting a database and a dev server by hand before `e2e run`, give
the engine the whole stack: the dependencies as `services`, then the app as
`command`:

```ts title="e2e.config.ts"
export default {
  targets: [
    {
      name: 'web',
      platform: 'web',
      engine: playwright({
        url: 'http://127.0.0.1:3000',
        services: [
          {
            executable: 'docker',
            args: ['compose', 'up', '--wait', 'postgres'],
            waitForExit: true,
            teardown: { executable: 'docker', args: ['compose', 'down'] },
          },
          { executable: 'pnpm', args: ['db:migrate'], waitForExit: true },
        ],
        command: { executable: 'pnpm', args: ['dev'], startupTimeout: 120_000 },
      }),
    },
  ],
} satisfies E2EConfig;
```

Services start one at a time in declaration order, each ready before the next
starts (a `waitForExit` service is ready when it exits 0, otherwise its
`readyUrl` must answer), and `command` only starts once the last service is
ready. On every exit path the runner stops the app, then stops the services in
reverse order, then runs their `teardown` commands in reverse order, so
`docker compose down` runs after the migration step and the app are gone.
Every service option is in the [config reference](/reference/config#services).

The runner spawns the command, waits until `readyUrl` (by default `url`)
answers with a 200-499 status, and terminates it when the run finishes, fails,
or is interrupted with Ctrl-C, so a launcher script that boots and kills the
server is unnecessary. Set `reuseExisting: true` locally to attach to the dev
server you already have running instead of starting a second one; without it an
already-answering `url` fails the run with `APP_ALREADY_RUNNING`, and CI
always does. On macOS and Linux the command runs as its own process
group and the whole group is signalled; on Windows only the launched process is
signalled, so point `executable` at the server itself rather than a wrapper. A
third Ctrl-C exits immediately without teardown. The child sees only `PATH`, `HOME`, and the
temp-directory variables plus whatever you put in `command.env`; model
credentials and CI tokens are never inherited, so anything the app needs must
be passed explicitly. A server that never becomes ready fails the run with
`APP_UNREACHABLE` and still leaves a `.e2e/report.json`; set
`command.log: '.e2e/logs/app.log'` to keep what the server printed, since
output is otherwise discarded. Every option is in the
[config reference](/reference/config#command).
