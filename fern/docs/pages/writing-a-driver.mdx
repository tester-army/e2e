---
title: Writing a driver
subtitle: How the runner talks to a backend, and what it takes to add a new one.
---

Everything in `e2e` above the backend is portable. `test`, `expect`, `screen`,
`app`, and the agent tiers never touch a browser, a simulator, or a device: they
speak one narrow interface called `driver-1`, and a driver is the package that
maps it onto a real automation backend.

`@e2edev/playwright` is one such package. A driver for iOS, Android, a desktop
shell, or a backend nobody has thought of yet is the same amount of surface -
the runner cannot tell them apart, and neither can a test.

<Callout intent="warning" title="Non-web platforms are not schedulable yet">
`driver-1` is platform-neutral, and you can write and unit-test a mobile or
desktop driver against it today. But the v0 runner rejects any target whose
`platform` is not `'web'` with `PLATFORM_UNSUPPORTED`, during config
resolution, before a driver is ever instantiated. Until that boundary lifts a
non-web driver cannot complete an end-to-end run.
</Callout>

## The ownership boundary

Read this table before writing any code. Most driver bugs are a driver doing
the runner's job.

| Concern | Owner |
| --- | --- |
| Collection, targets, retries, hooks, sessions | runner |
| Query polling and strict single-match cardinality | runner |
| Assertion polling | runner |
| One immediate query, one node read | driver |
| One node's actionability and input dispatch | driver |
| Agent planning, prompts, budgets, ledger | runner |
| Tool authorization and secret resolution | runner |
| Backend process, page, and device mechanics | driver |
| Source masking of secure observations | driver |
| Defense-in-depth redaction | runner |

The two rules that follow from it and get broken most often: a driver **must
not** add hidden query retries - `resolve` answers with what is on screen right
now and returns an empty array without complaint - and a driver **must not**
enforce single-match strictness, because `screen.getByRole(...)` deciding that
two matches is an error is a runner decision.

## The shape of a driver

A driver is a factory returning a branded handle. `defineDriver` validates the
manifest, freezes it, and stamps the brand that makes the handle acceptable in
target config.

```ts title="src/index.ts"
import { defineDriver, type Driver } from 'e2e/driver';

export function hyperdrive(): Driver {
  return defineDriver({
    id: 'hyperdrive',
    version: '1.0.0',
    platforms: ['web'],
    spiVersion: 1,
    capabilities: {
      fixtures: ['web'],
      artifacts: ['screenshot'],
      state: false,
    },
    async launch(context) {
      return createSession(context);
    },
  });
}
```

That is the whole top-level contract: a manifest, `launch`, and the optional
`prepare` and `dispose` hooks. Everything else hangs off the session that
`launch` returns.

<Callout intent="note">
Depend on `e2e/driver` only. `e2e/internal` exists so first-party driver
packages can share one copy of text and route pattern matching; it carries no
semver guarantee and is not part of the public API.
</Callout>

## Walkthrough

<Steps>

<Step title="Create the package">

Community drivers are conventionally named `e2e-driver-*`. Take `e2e` as a
**peer** dependency, never a regular one - the driver and the runner must agree
on one copy of the error classes, and the runner already resolves the graph.

```json title="package.json"
{
  "name": "e2e-driver-hyperdrive",
  "type": "module",
  "exports": { ".": "./dist/index.js" },
  "peerDependencies": { "e2e": ">=0.1.0 <1" }
}
```

</Step>

<Step title="Declare the manifest">

The manifest is read before anything launches, so selection can decide which
tests a target can even run.

| Field | Meaning |
| --- | --- |
| `id` | Stable across releases. Lowercase ASCII letters, numbers, `-`, `.`, `/`. |
| `version` | The driver package version. Lands in report provenance. |
| `platforms` | Every platform this driver can drive, e.g. `['ios', 'android']`. |
| `spiVersion` | Exactly `1`. Any other value is rejected before launch. |
| `capabilities.fixtures` | Capability ids this driver serves. A test declaring `requires: ['web']` is only selected on a target whose driver lists `'web'`. |
| `capabilities.artifacts` | Subset of `'screenshot'`, `'trace'`, `'video'`. Configuring an artifact you did not declare is a pre-run `UNSUPPORTED_ARTIFACT`. |
| `capabilities.state` | `true` only if you implement both `captureState` and `restoreState` faithfully. |

`defineDriver` throws a `TypeError` on a malformed manifest, and the returned
object is frozen: a driver cannot change its manifest after definition, and the
runner validates the live manifest against the target and artifact config before
the first launch.

</Step>

<Step title="Launch a session">

`launch` creates one logical attempt. It receives everything resolved:

```ts
async launch(context) {
  context.target;        // sanitized wire target: name, platform, browser, viewport
  context.app.baseUrl;   // app.url from config
  context.app.allowedOrigins;
  context.app.testIdAttribute;
  context.artifactsDir;  // absolute; every returned path is relative to it
  context.runId;
  context.attemptId;
  context.operation;     // signal + timeoutMs for the launch itself
  context.launchOptions.headed;
}
```

Launch gets `config.launchTimeout`, independent of any test timeout. If it
rejects, roll back **every** partial acquisition first - there is no session for
the runner to close, so anything you acquired and did not release leaks for the
rest of the run.

A session launches with nothing open. The first query or action before
`app.open()` or `web.goto()` must fail, which is what surfaces to a test as
`APP_NOT_OPEN`:

```ts
throw new DriverError('INVALID_STATE', 'no app page is open; call app.open() first', {
  retryable: false,
});
```

</Step>

<Step title="Resolve, read, and act">

`session.screen` is the deterministic half of the SPI and the part every driver
must implement.

```ts
screen: {
  // Returns every current match, immediately. No polling, no strictness.
  async resolve(expression, operation) {
    return project(expression).map((node) => this.track(node));
  },
  // One node, read at its revision. Values here are never truncated.
  async read(ref, operation) { /* ... */ },
  // Exactly one action against exactly one node.
  async perform(ref, action, operation) { /* ... */ },
  async swipe(direction, momentum, operation) { /* ... */ },
}
```

A `LocatorExpression` is a complete, immutable, five-arm tree that you project
onto your backend:

| Arm | Shape |
| --- | --- |
| `query` | A `SemanticQuery` (`role`, `label`, `placeholder`, `text`, `displayValue`, `testId`) with optional `scope` |
| `filter` | `source` narrowed by `hasText` or a nested `has` expression |
| `index` | `source` at `number`, `'first'`, or `'last'` |
| `web-selector` | A raw platform selector - web only |
| `frame` | `source` inside the frame named by a selector |

Text arrives as a `TextPattern`, never a `RegExp`: either
`{ kind: 'string', value, exact }` or `{ kind: 'regexp', source, flags }`. A
regexp crosses the boundary as source and flags precisely so an out-of-process
driver can carry it.

A `NodeRef` is `{ id, revision }` and identity is the **pair**. A ref whose
revision is no longer current is stale, and stale before dispatch is the one
condition worth retrying:

```ts
throw new DriverError('NODE_STALE', `node reference ${ref.id} is stale`, {
  retryable: true,
});
```

Backend actionability waiting is allowed inside `perform`, and only there, and
only within `operation.timeoutMs`.

</Step>

<Step title="Observe">

`observe` returns one atomic, fully redacted snapshot for a single revision. It
is what the agent tiers see, so it is the security boundary as much as the
capability boundary.

```ts
async observe(operation, options) {
  const revision = this.nextRevision();
  const [tree, pixels] = await Promise.all([
    this.captureTree(revision),
    options?.pixels === true ? this.capturePixels().catch(() => undefined) : undefined,
  ]);
  return {
    revision,
    capturedAt: new Date().toISOString(),
    tree,
    ...(pixels !== undefined ? { pixels } : {}),
    viewport: { width: 1280, height: 720, scale: 1 },
    redaction: {
      secureNodeCount: tree.secureCount,
      maskedRegionCount: pixels?.maskedRegionCount ?? 0,
      complete: true,
    },
  };
}
```

Four rules the runner actively enforces:

- **`redaction.complete: false` is rejected outright.** The observation never
  reaches a model and is never persisted. Say `false` when you cannot prove the
  masking your profile requires.
- **Pixels are withheld when `maskedRegionCount < secureNodeCount`**, reported
  to the test as `visionDegraded: 'MASKING_UNPROVEN'`. Mask a superset of the
  secure nodes: that is the safe direction.
- **`pixels.width`/`height` must be measured, not assumed.** They are the
  coordinate space of everything read off the image; `scale` relates that space
  to the CSS pixels in `SemanticNode.rect`, which is the space actions dispatch
  in. One image pixel is `1 / scale` CSS pixels.
- **Truncate observed `name` and `text` at the exported limits**, so that
  `length >= limit` is a precise truncation signal:

```ts
import { OBSERVED_NAME_LIMIT, OBSERVED_TEXT_LIMIT } from 'e2e/driver';
```

Secure fields carry `states.secure: true` with their `value`, text, and
sensitive attributes masked, and an `inputPurpose` of `'username'`,
`'password'`, `'one-time-code'`, `'generic-secret'`, or `'none'`. Pixel masking
and tree masking should be driven by **one** definition of what is secure -
otherwise the image and the tree can describe different sets of elements, which
is exactly what the runner's clearance check catches.

A capture that lost its document to a navigation in flight dispatched nothing
and is repeatable: `NODE_STALE`, retryable. A capture that ran out of budget is
`OPERATION_TIMEOUT` and is not retried in place.

</Step>

<Step title="Return artifacts">

`artifacts.screenshot` is required by every profile. Return a **relative POSIX
path** beneath `context.artifactsDir`; canonicalize, and reject traversal or
symlink escape.

```ts
artifacts: {
  async screenshot(label, operation) {
    const name = `screenshots/${pad(this.counter++)}${label ? `-${sanitize(label)}` : ''}.png`;
    await writeFile(join(this.artifactsDir, name), await this.capture());
    return name;
  },
}
```

`startTrace`/`stopTrace` and `startVideo`/`stopVideo` are optional and gated on
the manifest. Start and stop pairs must be idempotent under cancellation, and
partial artifacts are finalized during `close`.

</Step>

<Step title="Close">

`close` receives a **fresh** cleanup budget and signal, independent of the
attempt that may have just been cancelled. It must be idempotent and must
release every session-scoped resource: page, listener, temporary file, device
lease.

```ts
async close(context) {
  if (this.closed) return;
  this.closed = true;
  await this.stopTracingIfRunning();
  await this.releaseSession();
}
```

The runner calls it after pass, failure, timeout, cancellation, and signal.
Nothing you own may keep mutating the app after it resolves.

</Step>

<Step title="Point a target at it">

Import the factory and hand the handle to a target. A metadata-only object is
rejected: only a `defineDriver` handle carries the brand.

```ts title="e2e.config.ts"
import { defineConfig } from 'e2e';
import { hyperdrive } from 'e2e-driver-hyperdrive';

export default defineConfig({
  app: { url: 'http://localhost:3000' },
  targets: [{ name: 'hyperdrive', platform: 'web', driver: hyperdrive() }],
});
```

Each worker builds its own driver instance by re-importing this config, so a
factory must be safe to call more than once per run. String driver ids are
reserved for the well-known names the runner documents - today only
`'playwright'` - and anything else is `INVALID_CONFIG`.

</Step>

</Steps>

## Lifecycle

| Hook | Called | Contract |
| --- | --- | --- |
| `prepare?` | Once per driver **id** per run, before any session launches | Idempotent, safe to run concurrently from another process, progress on stderr only. A rejection aborts the run. |
| `launch` | Once per test or serial-group attempt | Bounded by `config.launchTimeout`. Rolls back every partial acquisition on rejection. |
| `close` | After every attempt, on any outcome | Idempotent, fresh budget, releases everything session-scoped. |
| `dispose?` | At most once per driver **instance**, after every session is closed | Idempotent. Must not affect already-captured artifacts or state. |

Slow one-time provisioning belongs in `prepare` - browser downloads, simulator
boots, device leases - precisely so it is never charged against a launch
timeout. Note the asymmetry: `prepare` is grouped by driver id because it
provisions shared backend state, while `dispose` runs per instance because it
releases what that instance retained.

<Callout intent="info" title="Sessions are strictly serialized">
The runner never calls `launch` while a previous session of the same instance is
still open. Parallelism comes from **one driver instance per worker** - one
browser process, one device - never from concurrent sessions on a shared
instance. So you may keep an expensive backend resource alive between sessions,
as long as each new session observes fully isolated app state, and you release
it in `dispose`.
</Callout>

## Errors

Throw `DriverError` for expected backend conditions. Anything else becomes a
non-retryable `DRIVER_FAILURE` with sanitized cause metadata. A driver never
assigns test status, an agent error code, or an exit code - those are runner
decisions.

| Code | When | Retryable |
| --- | --- | --- |
| `NODE_STALE` | A ref's revision is no longer current, before dispatch | yes |
| `FRAME_NOT_FOUND` | A frame selector matched nothing | yes |
| `FRAME_AMBIGUOUS` | A frame selector matched more than one frame | no |
| `NOT_ACTIONABLE` | The node exists but could not be acted on in budget | no |
| `ACTION_MAY_HAVE_COMMITTED` | Input, navigation, or state mutation may have landed | no |
| `OPERATION_TIMEOUT` | The operation budget ran out | no |
| `CANCELLED` | `operation.signal` aborted | no |
| `UNSUPPORTED_CAPABILITY` | The backend cannot express the request at all | no |
| `INVALID_STATE` | The session is not in a state where this is meaningful | no |
| `DRIVER_FAILURE` | Any other backend fault | no |

<Callout intent="warning" title="Retryability is a closed set">
Only `NODE_STALE` and `FRAME_NOT_FOUND` may be retryable. Passing
`retryable: true` with any other code does not throw - the error is silently
downgraded to a non-retryable `DRIVER_FAILURE`, and a genuine timeout loses its
meaning in reports. Never guess: an unknown commit state is
`ACTION_MAY_HAVE_COMMITTED`, not a retry.
</Callout>

The stale-versus-committed rule applies to every mutator, not just locator
actions: agent actions, viewport swipes, app lifecycle, navigation, raw input,
route decisions, and both nodes of a drag. Before dispatch, stale is retryable.
After anything may have committed, it is `ACTION_MAY_HAVE_COMMITTED`.

Every operation must observe both `operation.signal` and `operation.timeoutMs`,
and aborted work must stop before the promise settles. A backend you cannot
interrupt has to be isolated in a terminable child process that you kill.

## The rest of the session

Required on every session:

| Member | Purpose |
| --- | --- |
| `app` | `open`, `restart` (keeps state), `clearState` (clears and relaunches), `back`, `deepLink` |
| `screen` | `resolve`, `read`, `perform`, `swipe` |
| `actions` | Agent-tier `tap`, `longPress`, `type`, `scroll`, `press` |
| `artifacts` | `screenshot`, plus declared recorders |
| `observe` | One atomic redacted observation |
| `runtime` | Current viewport, scale, and backend provenance |
| `close` | Idempotent teardown |

`actions` overlaps `screen.perform` on purpose: it is the agent's vocabulary,
and it can simply delegate. `type` is a `fill` that carries a `sensitive` flag
you must honour in logs and traces.

Optional, and gated on what you declared:

- **`actions.tapPoint?`** - dispatch at a runner-validated viewport point.
  Optional, so a backend with no coordinate input simply omits it.
- **`captureState?` / `restoreState?`** - required together by
  `capabilities.state`. Capture returns opaque JSON-safe `DriverState`
  (`{ format, version, data }`) and must not write shared files. Restore
  **replaces** every store; it must never merge into the current context. The
  runner owns the session envelope, persistence, and validation.
- **`web?`** - the browser-only channel: navigation, `evaluate`, routes,
  cookies, viewport, dialogs, downloads, keyboard and mouse. The public `web`
  object a test sees is a runner proxy over it, which is why every method takes
  an operation context. Never return your backend's page or context object. The
  runner executes route and dialog callbacks; download waiting is two-phase -
  `beginDownload`, the runner fires the trigger, then `finishDownload` or
  `cancelDownload`.
- **`capabilityFixtures?`** - runtime values for a third-party capability
  family, keyed by its namespaced id. A manifest entry with no runtime value, or
  a runtime value with no manifest entry, is a driver error.

Whatever you skip, the universal surface stays: every platform implements `app`,
`screen`, `observe`, `actions`, `artifacts`, cancellation, and cleanup.

## Testing your driver

Unit-test the parts that are pure - locator projection, error translation,
semantic-tree shaping - and integration-test one real session against a fixture
app you control. `@e2edev/playwright` is laid out for exactly this split, and is
worth reading as the reference: `locators.ts` is expression projection in 127
lines, `support.ts` is the error taxonomy, `session.ts` is everything else.

<Callout intent="info" title="The conformance harness lands later">
`spec/conformance/v0-requirements.json` defines the requirement ids a driver
must satisfy - 8 for `driver-1`, 10 for `core-0.1`, 13 for `web-0.1`. The
machine-executable harness and its reference application land in a later
milestone; there is no `verifyDriver` API until it can actually run vectors.
Until then, treat the requirement manifest as the checklist and write the
vectors yourself.
</Callout>

## Trust

An in-process driver has the same authority as your test and config code: it
reads environment variables, repository files, backend state, and the raw values
it is asked to type. Conformance is compatibility testing, not a security
certification. Installed drivers are trusted dependencies, and secrets must
never reach model input, digests, logs, or reports.

The canonical contract is
[`spec/api/driver.d.ts`](https://github.com/tester-army/e2e/blob/main/spec/api/driver.d.ts),
with the normative prose in
[`spec/09-drivers.md`](https://github.com/tester-army/e2e/blob/main/spec/09-drivers.md).
Where this page and the spec disagree, the spec wins.
