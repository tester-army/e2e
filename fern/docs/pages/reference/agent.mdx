Every `agent` call is one bounded invocation: a fresh observation, an explicit
deadline, a model-call budget, and no shared transcript between calls. Acquiring
the fixture without a configured model fails with `MODEL_UNAVAILABLE`.

<Callout intent="warning" title="Not implemented yet">
The `act` options `schema` (structured output) and `vision` reject with
`UNSUPPORTED_CAPABILITY`.
</Callout>

```ts
export interface Agent {
  act<Schema extends StandardSchemaV1>(
    instruction: string,
    params: AgentParams | undefined,
    options: AgentSchemaOptions<Schema>,
  ): Promise<AgentResultWithData<StandardSchemaV1.InferOutput<Schema>>>;
  act(
    instruction: string,
    params?: AgentParams,
    options?: AgentOptions,
  ): Promise<AgentResult>;
  waitFor(
    condition: string,
    options?: VisionOption & { timeout?: number; intervalMs?: number; maxModelCalls?: number },
  ): Promise<void>;
  extract<Schema extends StandardSchemaV1>(
    instruction: string,
    options: VisionOption & { schema: Schema; timeout?: number; maxModelCalls?: number },
  ): Promise<StandardSchemaV1.InferOutput<Schema>>;
  assert(
    assertion: string,
    options?: VisionOption & {
      timeout?: number;
      screenshot?: boolean;
    },
  ): Promise<void>;
}
```

## Budgets

Model calls count every model request including repair rounds. Action steps count
committed backend actions. Every timeout is additionally capped by the remaining
test timeout.

| Method | Model calls | Action steps | Default timeout |
| --- | ---: | ---: | --- |
| `act` | `config.agent.maxModelCalls`, 25 | `config.agent.maxSteps`, 25 | `config.timeout`, 120000 ms |
| `waitFor` | `config.agent.maxModelCalls`, 25 | 0 | 30000 ms |
| `extract` | 2 | 0 | 30000 ms |
| `assert` | 1 | 0 | 30000 ms |

## agent.act

```ts
act(
  instruction: string,
  params?: AgentParams,
  options?: AgentOptions,
): Promise<AgentResult>;
```

Plans and executes one bounded multi-action flow. The harness owns the step
(observations, actions, budgets, origin policy, recording) and hands only the
thinking to the configured step executor. The call ends in an explicit verdict:
a passing one returns `{ ok: true }`; a failing or blocked one throws an
`AgentError` whose `code` and `blocked` flag say why.

| Name | Type | Default | Valid |
| --- | --- | --- | --- |
| `instruction` | `string` | - | 1 through 8192 UTF-8 bytes after NFC |
| `params` | `AgentParams` | `undefined` | JSON-safe values plus `Secret`, at most 64 KiB and 32 levels deep |
| `options.timeout` | `number` | `config.timeout` | positive safe integer |
| `options.maxSteps` | `number` | `config.agent.maxSteps` | positive integer, at most the resolved limit |
| `options.maxModelCalls` | `number` | `config.agent.maxModelCalls` | positive integer, at most the resolved limit |

Values come from your code through `params`, never from the model. A `Secret`
in `params` is projected before the model sees anything: the model receives the
secret's name and purpose, and the harness fills the value host-side, subject
to the same authorization as `locator.fill`: the credential must be
registered, the current origin must be allowed by both the target's allowed
origins (the backend's `allowedOrigins` declaration) and the credential's own
`allowedOrigins`, the field must be an enabled secure
input whose purpose equals the secret's purpose.

```ts
await agent.act('invite {email} as an editor', { email: 'ada@example.test' });

const member = credentials.user('member');
await agent.act('Sign in', {
  username: member.username,
  password: member.password,
});
```

Throws `ACTION_FAILED` for a failed verdict with no more specific code; a
blocked code such as `AUTH_CREDENTIAL_UNAVAILABLE`, `ENVIRONMENT_UNAVAILABLE`,
`SEED_DATA_MISSING`, `TEST_SETUP_FAILED`, or `AUTOMATION_UNSUPPORTED` when the
step could not reach a product verdict; `STEP_BUDGET_EXHAUSTED` and
`STEP_TIMEOUT` when a budget or the deadline ran out; and `INVALID_ARGUMENT`
for a malformed instruction or oversized `params`.

## Vision

`assert`, `waitFor`, and `extract` accept `vision`. It controls what evidence
the model is shown: the semantic tree, a masked screenshot of the current
observation, or both. Sending pixels needs a model that accepts images.

```ts
await agent.assert('the chart trends upward', { vision: true });
await agent.assert('the search form is visible and not covered', { vision: 'only' });
```

| Name | Type | Default |
| --- | --- | --- |
| `options.vision` | `boolean \| 'fallback' \| 'only'` | `config.agent.vision`, `false` |

| Mode | What the model sees | Cost |
| --- | --- | --- |
| `false` | the tree | no image tokens |
| `true` | the tree and a screenshot, every call | image tokens on every call |
| `'fallback'` | the tree; behaves like `false` for `assert`, `waitFor`, and `extract` | no image tokens |
| `'only'` | the screenshot, and not the tree | image tokens, minus the observation bytes |

Set `agent.vision` in config to make a mode the project default; a per-call value
always wins. Images are billed as input tokens, so `true` costs more than the
same call without it on every call.

<Callout intent="warn" title="'fallback' behaves like false">
`'fallback'` exists for calls that can discover mid-flight that the tree was
not enough. A judgment never does: `assert`, `waitFor`, and `extract` always
produce an answer from the tree, so there is no miss to escalate on;
escalating on a `false` judgment would just bias it toward `true`. Under
`'fallback'` they run tree-only, exactly like `false`. Use `vision: true` or
`'only'` when you need pixels judged.
</Callout>

### Judging pixels and nothing else

`vision: true` sends the tree *and* the screenshot, and that is a problem for a
visual assertion: the tree is a cheaper path to an answer, and the model will take
it.

```ts
// Passes on the tree alone (the form is present, enabled, and named) while a
// consent sheet covers it on screen.
await agent.assert('the search form is visible and not covered', { vision: true });

// Judged on the screenshot. There is no tree in the request to answer from.
await agent.assert('the search form is visible and not covered', { vision: 'only' });
```

Same for a price rendered at `opacity: 0`, a button under a cookie banner, or a
broken layout, all of which the tree happily reports as fine. Use `'only'` when
the question is about what the page *presents*; use `true` when the tree is part
of the answer (`'the submit button is disabled'` is in the tree and often not
visible at all).

`'only'` is cheaper than `true`, not more expensive: you drop the observation
bytes. The runner still captures the observation and reports against it; it
just isn't sent. The step records `visionOnly: true` and zero
`observationBytes`.

<Callout intent="warn" title="Pixels are viewport-scoped, the tree is document-scoped">
The screenshot is the viewport, never the full page. So a condition the tree
satisfies can be false on screen, and that is usually the point. But it also
means `'only'` cannot see below the fold.

```ts
// Tree: passes. The DOM holds prices for all 6701 matched offers.
// 'only':  fails. The first card is cut off just above its price.
await agent.waitFor('a list of offers with hotel names and prices is visible', { vision: 'only' });
```

Write `'only'` conditions about what is on screen, and let the flow scroll first
when you want to ask about something further down.
</Callout>

One consequence worth knowing: **no pixels means no answer.** If the viewport is
pixel-tainted by a secret fill, or masking cannot be proven complete, `'only'`
fails with `POLICY_DENIED`. Every other mode degrades to the tree; `'only'` will
not answer a question about pixels from the tree instead.

Calls that send pixels use `agent.visionModel` when it is set, and `agent.model`
otherwise, and keep it for the rest of the invocation, including polling rounds
whose pixels were withheld, so a polling method never switches models between
rounds.

<Callout intent="info" title="Additive, never pixels-only">
In every mode but `'only'`, the tree is always sent. It is byte-budgeted and
cheap, and its node references are what keep a step auditable.
</Callout>

Pixel evidence degrades instead of failing the call. It is withheld, and the tree
sent alone, when the viewport is pixel-tainted by a secret fill
(`visionDegraded: "PIXEL_TAINTED"` on the step), when the backend masked fewer
regions than the secure fields it observed (`MASKING_UNPROVEN`), or when the
backend cannot capture pixels (`UNSUPPORTED_CAPABILITY`). A step that did send
pixels to the model records `visionInput: true` and `metrics.pixelBytes`.

`options.vision` and `assert`'s `options.screenshot` are unrelated: `screenshot`
controls failure evidence attached to the report after the judgment, `vision`
controls what the model is shown before it.

## Judgments and extraction

### agent.assert

```ts
assert(
  assertion: string,
  options?: { timeout?: number; screenshot?: boolean; vision?: VisionMode },
): Promise<void>;
```

One fresh observation, exactly one judgment. It does not poll.

| Name | Type | Default |
| --- | --- | --- |
| `assertion` | `string` | - |
| `options.timeout` | `number` | `30000` |
| `options.screenshot` | `boolean` | `true` |
| `options.vision` | `VisionMode` | `config.agent.vision`, `false` |

Throws `ASSERTION_FAILED` on a false judgment, carrying the explanation and, when
permitted, a screenshot path. Evidence is skipped with `screenshot: false` and
once any secret has been filled in the attempt.

```ts
await agent.assert('the dashboard shows a trial badge');
```

### agent.waitFor

```ts
waitFor(
  condition: string,
  options?: { timeout?: number; intervalMs?: number; maxModelCalls?: number; vision?: VisionMode },
): Promise<void>;
```

One observation and one judgment per interval. Succeeds on the first true
judgment.

| Name | Type | Default | Valid |
| --- | --- | --- | --- |
| `condition` | `string` | - | - |
| `options.timeout` | `number` | `30000` | positive safe integer |
| `options.intervalMs` | `number` | `3000` | integer 100-60000 |
| `options.maxModelCalls` | `number` | `config.agent.maxModelCalls` | positive integer, at most the resolved limit |

Throws `STEP_TIMEOUT` on deadline expiry and `STEP_BUDGET_EXHAUSTED` on budget
exhaustion, each carrying the last judgment, and `INVALID_ARGUMENT` for an
out-of-range option.

```ts
await agent.waitFor('the upload progress reports completion', { intervalMs: 500 });
```

### agent.extract

```ts
extract<Schema extends StandardSchemaV1>(
  instruction: string,
  options: { schema: Schema; timeout?: number; maxModelCalls?: number; vision?: VisionMode },
): Promise<StandardSchemaV1.InferOutput<Schema>>;
```

Takes one fresh observation, requests structured output, validates it, and
returns the validated value. It performs no app actions.

| Name | Type | Default | Valid |
| --- | --- | --- | --- |
| `instruction` | `string` | - | - |
| `options.schema` | `Schema` | - | any Standard Schema v1 validator |
| `options.timeout` | `number` | `30000` | positive safe integer |
| `options.maxModelCalls` | `number` | `2` | positive integer, at most 2 |

Invalid output is repaired while budget remains. Throws `INVALID_ARGUMENT` for a
schema that is not Standard Schema v1 or `maxModelCalls` above 2, and
`MODEL_OUTPUT_INVALID` when validation still fails.

```ts
const summary = await agent.extract('the workspace name and plan', {
  schema: z.object({ name: z.string(), plan: z.string() }),
});
```

## Types

```ts
export interface VisionOption {
  vision?: VisionMode;
}

export type VisionMode = boolean | 'fallback' | 'only';

export interface AgentOptions extends VisionOption {
  timeout?: number;
  maxSteps?: number;
  maxModelCalls?: number;
}

export interface AgentSchemaOptions<Schema extends StandardSchemaV1>
  extends AgentOptions {
  schema: Schema;
}

export type AgentParam =
  | JsonPrimitive
  | Secret
  | readonly AgentParam[]
  | { readonly [key: string]: AgentParam };
export type AgentParams = Readonly<Record<string, AgentParam>>;

export interface AgentResult {
  readonly ok: true;
}

export interface AgentResultWithData<Output> extends AgentResult {
  readonly data: Output;
}
```

Per-call budgets must be positive integers and can only lower the resolved
configuration limits.

`AgentOptions`, `AgentSchemaOptions`, `AgentParams`, `AgentResult`, and
`AgentResultWithData` are consumed by `act`. Judgments return `void`;
`extract` returns the validated value directly.

## AgentError

```ts
export class AgentError extends Error {
  readonly code: AgentErrorCode;
  readonly explanation: string;
  readonly screenshot?: string;
  readonly blocked: boolean;
}
```

| Property | Type | Description |
| --- | --- | --- |
| `code` | `AgentErrorCode` | Closed union, assigned by the runner, never taken from model text |
| `explanation` | `string` | Sanitized, bounded prose. Same value as `message`. |
| `screenshot` | `string \| undefined` | Artifact path, present only when evidence was captured and permitted |
| `blocked` | `boolean` | True when the failure reports a blocked step (credentials, environment, or budget), not a product failure |

Check `code` rather than using `instanceof`. Every code, its class, and its exit
code are in [Errors](/reference/errors).

Model usage accounting is shared by executor steps and judgment calls. A step
reports `tokenAccounting: 'provider'` only when every call supplies complete
provider token counts. Missing, partial, or estimated usage keeps the aggregate
at `adapter-upper-bound`, even if later calls report complete counts. Available
token counts, per-call peaks, and valid reported costs still accumulate.
Malformed counters are excluded from model events as well as step totals.
Token sums that exceed the safe integer range saturate at
`Number.MAX_SAFE_INTEGER` and make accounting non-authoritative. An overflowing
cost total is omitted for the rest of that step. Run summaries also cap token
sums and omit overflowing cost totals.
