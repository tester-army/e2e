---
title: Embedding (e2e/run)
description: Run the runner programmatically and stream structured events.
---

`@e2edev/e2e/run` is the host surface: everything a program embedding the runner — a
hosted platform, a CI wrapper, an IDE — needs to start runs, stream progress,
and read outcomes in-process. The CLI is a thin consumer of exactly this
surface. It is host tooling, not part of the sdk-0.1 test API: it can grow in
minor releases, and `report.json` (report-1) stays the canonical record of a
run.

```ts
import { run } from '@e2edev/e2e/run';

const outcome = await run({
  cwd: '/path/to/project',
  onEvent: (event) => publish(event),
  interruptSignal: controller.signal,
  quiet: true,
});

outcome.status; // 'passed' | 'failed' | 'error' | 'interrupted'
outcome.report; // the full report-1 document, in memory
```

`run()` never calls `process.exit`. It resolves config exactly like the CLI
(`cwd` + `configPath`, or a preloaded `rawConfig`), honors `interruptSignal`
for cancellation, and returns the complete report alongside the raw result
records. One `run()` at a time per process: the runner installs signal
handlers and a process-wide credential registry.

## RunOptions

Everything the CLI flags map to (`files`, `tags`, `targetIds`, `headed`,
`retries`, `workers`, `reporters`, `artifactsDir`, `passWithNoTests`,
`noCache`, `debug`), plus the host-only fields:

| Field | What it does |
| --- | --- |
| `rawConfig` | Preloaded config object, bypassing file discovery. It may hold live values (a `StepExecutor`, a model instance, a `TraceCacheStore`, an `ArtifactStore`), so it cannot cross a process boundary: the run executes in-process on one worker. A file-backed config keeps full parallelism. |
| `env` | The environment the run resolves against, instead of `process.env`. This controls CI detection (`CI`), model credentials, and `E2E_USER_*` overrides. |
| `quiet` | Suppresses the terminal reporter; pair it with `onEvent`. |
| `interruptSignal` | Cancellation, what the CLI's first Ctrl-C does: the running test ends at once, its teardown runs, every worker disposes its engine, and the run finishes with status `interrupted` and exit code 130. |
| `forceSignal` | Forced cancellation, the CLI's second Ctrl-C: every worker disposes its engine right away instead of finishing its test and is killed after the cleanup budget. Counts as an interrupt on its own. |
| `onEvent` | The structured event stream below. |

## The event stream

`onEvent` receives every lifecycle fact as plain JSON data — the same records
the report persists, streamed while the run is going. Each event carries a
`seq` stamped by the run's single writer (so ordering survives any transport
that preserves per-connection order) and an ISO `at` timestamp.

```ts
type RunEventFact =
  | { type: 'run-started'; runId; projectId; projectRoot; ci; targets; model? }
  | { type: 'plan'; total; files: { file; target; tests }[] }
  | { type: 'notice'; target; message }
  | { type: 'test-started'; testId; title; file; serialId; target }
  | { type: 'step'; testId; target; progress: StepProgress }
  | { type: 'test-finished'; result: RunEventResult }
  | { type: 'serial-group'; group: SerialGroupRecord }
  | { type: 'run-error'; error: SerializedError }
  | { type: 'run-interrupted'; mode: 'graceful' | 'forced' }
  | { type: 'run-finished'; status; exitCode; reportPath?; junitPath?; aiTracePath? };
```

`plan` announces the run's size: `total` counts every test-target pair,
while `files` breaks the reportable pairs (run or explicitly skipped) down per
test file and target, so a consumer can tell when a file's results are
complete. `notice` carries one line of run-level progress outside any test — a
engine's `prepare` hook narrating a first-run browser download, for example.
`step` events stream each public step's `start` and `end` phases plus its
child events (observations, model calls, engine actions, policy decisions) as
they happen — the same feed the list reporter renders. `test-finished`
carries the full result record with the live target flattened to
`{ name, platform }`, so every payload survives `JSON.stringify`. A serial
group announces each member with its own `test-started` (carrying the group's
`serialId`) as it begins, then emits `serial-group` once the group completes,
followed by every member's `test-finished`. Member results carry
`serialGroupId` and no attempts of their own: their steps, durations, and
errors live in the group record a consumer has already received.
`run-interrupted` is emitted once when `interruptSignal` aborts (`graceful`)
and once more if `forceSignal` aborts (`forced`). The runner installs no
process signal handlers and never exits the process; Ctrl-C is the CLI's, see
[Signals](/reference/cli#signals). A host that wants the same ladder wires its
own signals to these two options. In a `rawConfig` run the test body shares
the host's process and cannot be abandoned, so an interrupt there ends the
attempt at the body's next harness call or its timeout, whichever comes first.

The sink must not block and must not throw: a sink that throws is quarantined
for the rest of the run, and a sink whose returned promise rejects is
quarantined once the rejection settles — events emitted before then may still
reach it. Either way the run is never affected. `run-finished` carries
`reportPath` only when the canonical report was actually written: it is
absent when the write failed (an infrastructure run error that also joins the
exit code) and on a configuration failure, where no report exists at all.
`junitPath` follows the same rule for the `junit` reporter's XML, and
`aiTracePath` for the model-call trace a run requested with `aiTrace: true`
(the CLI's `--ai-trace`); see [CLI](/reference/cli#output).
Redaction happens before events are built; secret values never appear in the
stream.

## Hosted caching

Two config seams exist for hosts that own a shared trace cache
([Config → cache](/reference/config#cache)):

- `cache.store` accepts any `TraceCacheStore` (a Redis adapter, an API). A
  host-supplied store is exempt from the CI read-only clamp: it is not a
  committed file cache, and it states its own trust through `writable`.
- The engine's `identity` declaration (`playwright({ url, identity })`) keys
  cache and session identity by what the app *is* rather than the origin it
  happens to be served from, so ephemeral per-deploy origins (PR previews)
  share their recorded traces.
- `artifacts.store` accepts any `ArtifactStore`
  ([Config → artifacts](/reference/config#artifacts)): every screenshot
  and trace is handed to it the moment it is complete, with its bytes, digest,
  and report identity, and its returned reference lands on the artifact record
  as `ref`. A host uploads evidence as the run produces it instead of reading
  the report's paths back off disk afterwards.
