The `agent` fixture is how you dial model authority up and down. Each call is one
bounded operation with its own deadline and model-call budget, and your code
always decides the order.

```ts
await agent.act('complete checkout with the test card');  // plan and execute
await agent.assert('the dashboard shows a trial badge');   // answer one question
const data = await agent.extract('the invoice total', { schema }); // return data
```

## Configure a model

The AI SDK (`ai`) is an **optional peer dependency**: deterministic suites and
custom executors never load it, and installing `e2e` does not pull it in. Add
`ai` to your project to use models — the built-in agent, gateway model
references, and the judgment tier all require it.

There is no default model. Set one in config:

```ts title="e2e.config.ts"
export default defineConfig({
  agent: { model: 'anthropic/claude-sonnet-4.5' },
});
```

Or per run:

```bash
E2E_MODEL=openai/gpt-5.4-mini E2E_MODEL_API_KEY=... npx e2e run
```

A `provider/model-id` string is routed through the
[Vercel AI Gateway](https://vercel.com/docs/ai-gateway), so one key reaches any
provider. The key is read from `E2E_MODEL_API_KEY`, falling back to
`AI_GATEWAY_API_KEY`, and never appears in logs or reports.

To use a provider directly, pass a live AI SDK model instance. It brings its own
transport and credentials, so any provider package works - including a local one:

```ts title="e2e.config.ts"
import { openai } from '@ai-sdk/openai';

export default defineConfig({
  agent: { model: openai('gpt-5.4-mini') },
});
```

Give the model a little project context when your UI has domain language:

```ts
export default defineConfig({
  agent: {
    model: 'anthropic/claude-sonnet-4.5',
    context: 'A billing dashboard. Plans are Free, Pro, and Enterprise.',
  },
});
```

## Planned flows

`agent.act` hands one goal to the model and lets it plan and execute the steps to
reach it. Use it for flows that are tedious to spell out or still changing shape.

```ts
await agent.act('complete checkout with the test card');
await agent.act('invite {email} as an editor', { email: 'ada@example.test' });
```

Values come from your code through `params`, never from the model's imagination.
The call is still bounded by a deadline, a step budget, and a model-call budget,
and it is still one step in your test: it returns, and your next line runs.

A `Secret` in `params` stays host-side. The model sees only the secret's name
and purpose, and the harness fills the value itself, through the same
authorization policy that governs `locator.fill` — so a whole sign-in is one
planned step with no password in any prompt:

```ts
const member = credentials.user('member');
await agent.act('Sign in', {
  username: member.username,
  password: member.password,
});
```

Under the hood, the harness owns the step — it captures redacted observations,
performs every action, enforces budgets and origin policy, and records
everything into the report — and hands only the *thinking* to a step executor.
The built-in executor is a tool-loop agent over a small action vocabulary
(`tap`, `type`, `press`, `select`, `scroll`, `navigate`, `observe`), and the
only way for it to finish is an explicit verdict:

- **passed** — the application behaved as the step required, verified on screen.
- **failed** — the application did not.
- **blocked** — credentials, the environment, or the agent's own budget
  prevented a product verdict. Blocked says nothing about your app: it carries
  an error code (`AUTH_CREDENTIAL_UNAVAILABLE`, `APP_UNREACHABLE`, …) and maps
  to the configuration/infrastructure exit codes, not the test-failure exit.

That last verdict is what makes agentic testing reliable in practice: a missing
seed record or an expired credential reads as *blocked*, not as a red product
failure, so trust in red survives. Blocked is first-class in the report too:
the step records `status: "blocked"`, and a run whose every non-passing test
was blocked reports `run.status: "blocked"`.

The loop also polices itself: guards detect a model literally repeating the
same call (or cycling the same short sequence) and force a verdict instead of
burning budget; a wind-down fires near the turn budget *and* near the step
clock, so slow providers conclude rather than time out. Run with `--debug`
and every planned step saves its full model transcript as a `log` artifact —
when a step wanders, you read what happened instead of guessing.

<Tip title="Write instructions like you would say them out loud">
Name the visible affordances, and prefer the exact wording on screen: `'the Sign
in button'` beats `'the submit control at the bottom of the form'`. Keep one
goal per call — the flow inside it is the model's job, the order of goals is
yours.
</Tip>

<Callout intent="warning" title="Not implemented yet">
`agent.act` structured output (`options.schema`) and per-call `vision` are not
part of this release and reject with `UNSUPPORTED_CAPABILITY`.
</Callout>

## Bring your own agent

The executor behind `agent.act` is a socket, not a fixture of the runner. Three
levels of customization, smallest first:

**Extend the built-in agent.** The `agent` config value accepts the agent
itself. `createAgent` from `e2e/agent` builds the built-in one, extended with
your tools (AI SDK tools with declared semantics), `system` prompt, or `model`
(any AI SDK language model):

```ts title="e2e.config.ts"
import { defineConfig } from 'e2e';
import { createAgent, defineTool } from 'e2e/agent';
import { tool } from 'ai';
import { z } from 'zod';

const seedCart = defineTool(
  tool({
    description: 'Seed the cart with a SKU via the store test API',
    inputSchema: z.object({ sku: z.string() }),
    execute: async ({ sku }) => fetch(`${process.env.APP_URL}/api/test/cart?sku=${sku}`).then((r) => r.text()),
  }),
  { replay: 'none', mutates: true, secrets: false },
);

export default defineConfig({
  app: { url: process.env.APP_URL! },
  agent: createAgent({ tools: { seedCart } }),
});
```

`createAgent()` with no arguments is exactly what runs when `agent` is an
options block or absent; unset options fall back to config (`agent.model`,
`E2E_MODEL`) and the base execution rules.

**Replace it entirely.** `agent` also accepts anything implementing the
`StepExecutor` interface — one step in, one verdict out — with no AI SDK
involved at all (`agent: myBrain`):

```ts
import type { StepExecutor } from 'e2e';

const myBrain: StepExecutor = {
  name: 'my-brain',
  version: '1',
  async runStep(ctx) {
    const screen = await ctx.observe();          // redacted semantic tree
    await ctx.actions.tap({ id: 'n42' });        // policed, budgeted, recorded
    return { status: 'passed', summary: 'did the thing and saw the result' };
  },
};
```

Everything the executor does bottoms out in `ctx.actions` and `ctx.observe()`,
so swapping brains changes only the thinking — never safety, budgets, or the
report. The full contract lives in the spec's executors chapter.

**The middle path.** If your executor is still a tool loop — just with a
different tool vocabulary (a device toolkit, an internal API) — build it on
`createToolLoopExecutor` from `e2e/agent`: it ships the verdict tool, hard
stops, loop guards, wind-down, model accounting, and the `--debug` transcript,
and takes your `tools`, `system`, and `buildPrompt`. The built-in agent is
exactly this chassis plus the web grammar toolset.

## Judgments

Ask a yes/no question about the screen. One observation, one answer, one
explanation.

```ts
await agent.assert('the todo list contains exactly one item called "Buy milk"');
```

A false answer raises `ASSERTION_FAILED` with the model's explanation, and a
screenshot is attached to the report as evidence. It is an ordinary test failure:

```ts
try {
  await agent.assert('the page shows a completed checkout receipt');
} catch (cause) {
  const error = cause as { code?: string; explanation?: string };
  expect(error.code).toBe('ASSERTION_FAILED');
}
```

`assert` looks once. To wait for something to become true, use `waitFor`:

```ts
await agent.waitFor('the network status reports that users finished loading', {
  intervalMs: 500,
  timeout: 120_000,
});
```

## Extracting data

Pull structured values off the screen, validate them, then branch in TypeScript.

```ts
import { z } from 'zod';

const data = await agent.extract('every todo title and how many remain', {
  schema: z.object({
    titles: z.array(z.string()),
    remaining: z.number().int(),
  }),
});

expect(data.titles).toContain('Ship runner');
expect(data.remaining).toBe(2);
```

Any [Standard Schema](https://standardschema.dev) validator works, zod included.
Invalid output gets one repair attempt and then fails with
`MODEL_OUTPUT_INVALID`. A guess never passes as a success.

<Callout intent="warning" title="Assert on meaning, not on wording">
Different models phrase things differently. Check containment and shape rather
than an exact sentence:

```ts
expect(summary.plan).toContain('Pro');   // good
expect(summary.plan).toBe('Pro plan');   // brittle
```
</Callout>

## What the model sees

By default only three things reach the model:

- a redacted snapshot of the screen: roles, accessible names, text, test IDs, and
  states
- a short summary of previous steps in the same test
- your `agent.context` string

It never receives raw HTML, cookies, headers, network bodies, or environment
values. Password fields arrive masked, and any configured credential value found
on screen is replaced with a placeholder before the snapshot leaves the runner.
Screenshots are for your report, not the model, unless you ask for them with
`vision`.

## Seeing the screen

Some things no snapshot describes: a chart drawn on a canvas, a map pin, a
WebGL scene, a custom widget with no semantics, or a purely visual property like
a trend or a broken layout. Pass `vision: true` and the model also gets a masked
screenshot of the current screen.

```ts
await agent.assert('the chart trends upward', { vision: true });
```

It needs a model that accepts images. Set `agent.vision` in config to pick a
default for a whole project, and override it per call.

The snapshot still goes with it — vision adds pixels, it never replaces the tree.

### Judging the screen, not the snapshot

`vision: true` gives the model both, which is wrong for a visual assertion: the
snapshot is the easier read, so that is what gets read. "The form is visible and
not covered" is *satisfied* by a snapshot in which the form is present and named,
even with a consent sheet over it.

```ts
await agent.assert('the search form is visible and not covered', { vision: 'only' });
```

`'only'` sends the screenshot and leaves the snapshot out, so there is nothing
else to answer from. It costs less than `true`, not more. Reach for `true` when
the snapshot is part of the answer — "the submit button is disabled" lives in the
snapshot and is often invisible on screen.

If pixels are unavailable — a tainted viewport after a secret fill — `'only'`
fails instead of quietly answering from the snapshot.

One thing to expect: the screenshot is the viewport, not the whole page. A
snapshot-based "the list shows prices" passes because the DOM holds every price;
the same question on pixels fails when the first card is cut off above its price.
That is the mode working, not breaking — but write `'only'` conditions about what
is on screen, and scroll before asking about anything further down.

One more mode exists: `vision: 'fallback'` behaves exactly like `false` for
`assert`, `waitFor`, and `extract`. A judgment always produces an answer from
the snapshot, so there is no miss to escalate on — escalating on a failed
assertion would only bias it toward passing. Use `vision: true` or `'only'`
when you need pixels judged.

Two things to expect:

- Images are billed as input tokens, so `vision: true` costs more than the same
  call without it on every call. Reach for it on the step that needs pixels.
- Once a test fills a secret, the screen stays pixel-tainted for the rest of the
  attempt: vision calls silently continue with the snapshot alone, and the report
  records that pixels were withheld.

### Pinning a model for pixels

The model that reads your snapshots well is often not the model that reads
pixels well. `agent.visionModel` pins the one that vision calls use, leaving
every other call on `agent.model`:

```ts
export default defineConfig({
  agent: {
    model: 'google/gemini-3-flash',
    visionModel: 'openai/gpt-5.6-luna',
  },
});
```

`E2E_VISION_MODEL` overrides it, the way `E2E_MODEL` overrides `agent.model`.
Unset, calls that send pixels use `agent.model`. Each step in the report records the model
it actually used, so a mixed run stays auditable.

## Cost and limits

Every call is bounded, so a bad prompt cannot spend your budget in a loop.

| Call | Model calls | Default timeout |
| --- | --- | --- |
| `act` | up to `agent.maxModelCalls`, default 25 | test `timeout`, 120 s |
| `assert` | 1 | 30 s |
| `extract` | 2 | 30 s |
| `waitFor` | up to `agent.maxModelCalls`, default 25 | 30 s |

`vision: true` changes no budget in this table; it makes each of those calls
carry an image, which costs input tokens.

Exceeding a budget raises `STEP_BUDGET_EXHAUSTED`; running out of time raises
`STEP_TIMEOUT`. Both are test failures you can see in the report.

Keeping an agentic suite cheap:

- Assert with `expect` when the check is mechanical. It is free.
- Scope `agent.act` to the step that breaks, not to the whole test.
- Give `timeout` room when a provider is slow. Latency is not a defect.
- Keep `waitFor` intervals coarse; each poll is a model call.
