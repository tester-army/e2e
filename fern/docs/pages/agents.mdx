The agent you pass to `defineConfig` is a **step executor**: one step in, one
verdict out. The runner owns everything around it: redacted observations,
every action, budgets, origin policy, secrets, the report. Customizing the
agent changes how it decides, not what it is allowed to do.

## Pick a model

There is no default model. The `agent.model` setting, or `E2E_MODEL`, names a
`provider/model-id` string routed through the Vercel AI Gateway, so one
`E2E_MODEL_API_KEY` (or `AI_GATEWAY_API_KEY`) reaches any provider:

```bash
E2E_MODEL=anthropic/claude-sonnet-4.5 E2E_MODEL_API_KEY=... npx e2e run
```

To use a provider directly, pass a live AI SDK model instance. Any provider
package works, including a local one:

```ts title="e2e.config.ts"
import { openai } from '@ai-sdk/openai';

export default defineConfig({
  agent: { model: openai('gpt-5.4-mini'), executor: myAgent },
});
```

The model alone runs the judgment tier: `agent.assert`, `agent.waitFor`, and
`agent.extract` need nothing else. `agent.act()` needs a **step executor** too,
and the runner ships none: pass yours as `agent.executor`, or set `agent` to
the executor itself. A config without one runs every deterministic test and
every judgment, and fails its first `agent.act()` with `INVALID_CONFIG`
naming what is missing. `context` is a sentence or two of project vocabulary
and reaches every `agent.*` call; `visionModel` pins a separate model for
calls that carry pixels. The AI SDK (`ai`) is an optional peer dependency;
deterministic suites and model-free executors never load it.

## What the runner hands an executor

Every `agent.act` step is one fresh call to `runStep(ctx)`. The context carries
the instruction and its params, the ledger of completed steps, budgets, the
model, and two things the executor talks to the app through: `ctx.observe()`
and `ctx.actions`.

An observation is the screen as a tree of nodes, one line per node
(`#id role "name"`, attributes, `[states]`), redacted and size-bounded, with
the current `path`. Node ids are stable: the backend stamps an id on each
element the first time it is observed and reads it back on every later
observation, so an element keeps its id for as long as it lives in the
document, and an executor can diff screens instead of re-reading them. A
combobox lists its options as child nodes. Observations settle before they
are returned: the runner waits for the data requests earlier actions set off
(bounded by 5 s) and then for the screen to hold still, so a save is observed
with its result, never with the screen the click left behind. The same holds
for `agent.assert`, `waitFor`, and `extract`.

Between steps, the ledger hands over four things per step. Two are the
runner's: a `did:` line built from the actions it recorded (`type "Nimbus
Paper Co" into textbox "Supplier name"; tap button "Add supplier"`) and a
`saw:` line quoting the text that appeared or changed on screen during the
step (`Ticket TK-6830 · colour Amber · desk 8`). Two are the executor's:
`noted:` facts it flagged in its verdict (`StepVerdict.facts`) and its
`observed:` summary. A step the trace cache replayed hands over only what it
did and showed on this run, never the verdict recorded earlier.

The ledger has a byte budget, and long flows overrun it. Compaction keeps
what later steps can act on: the three newest agent steps stay in full; every
other step appears in compact form (its head plus `saw:` and `noted:`, with
runs of passed checks folded into one line); over budget, the runner drops the
least valuable entries first — folded checks, then steps that surfaced no
facts, then steps with facts — middle first within each group, marking each
gap. A ticket code issued in step two is still there at step fifty.

## Run to run

A test that passes once should pass fifty times when nothing changed. The
runner removes the variance it can, for any executor:

- Model calls made through the chassis sample at temperature 0, and
  `providerOptions` pin a provider's thinking level so latency and reasoning
  cost hold steady. Gateway models carry a stall guard: a response that has
  not arrived in 120 s is abandoned and re-issued.
- Every observation waits for the requests earlier actions set off and then
  for the screen to hold still, as described above.
- A `complete_step` issued alongside other tool calls is discarded: a verdict
  has to follow the evidence it claims.
- The trace cache replays a recorded step zero-turn and hands over to the
  executor when the app diverged. A trace records the text that appeared over
  the step and waits for it to return before it self-finalizes; a typed value
  the step derived at run time (an app-issued code) is a hand-off point, never
  replayed; and a control is relocated by the row it sat in, so same-named
  buttons in different rows replay without a guess.

What remains is the app's own nondeterminism and the executor's judgment.
Pair every `agent.act` with an `expect`, keep `agent.assert` for judgments an
`expect` cannot make, and keep the trace cache on.
`packages/testbed/bench-repeat.mjs` in the repository runs a suite N times and
tallies pass rates per test; that number, not a single green run, is the one
to watch.

## Build an executor on the chassis

`createToolLoopExecutor` from `e2e/agent` is the chassis: the verdict tool,
budget hard stops, loop guards, wind-down near the clock, discarded batched
conclusions, model accounting, and `--debug` transcripts. You bring the tool
vocabulary and the first prompt. The grammar an executor acts through is
`ctx.actions` (`tap`, `type`, `typeSecret`, `press`, `select`, `scroll`,
`navigate`); `ctx.target.verbs` is the subset the target's backend declared,
so offer a model exactly that.

```ts title="e2e.config.ts"
import { defineConfig } from 'e2e';
import { createToolLoopExecutor, defineTool } from 'e2e/agent';
import { tool } from 'ai';
import { z } from 'zod';

const seedCart = defineTool(
  tool({
    description: 'Seed the cart with a SKU via the store test API',
    inputSchema: z.object({ sku: z.string() }),
    execute: async ({ sku }) =>
      fetch(`${process.env.APP_URL}/api/test/cart?sku=${sku}`).then((r) => r.text()),
  }),
  { replay: 'none', mutates: true, secrets: false },
);

const myAgent = createToolLoopExecutor({
  name: 'my-agent',
  version: '1',
  system: 'You are a QA agent executing one test step. Verify every outcome on screen.',
  tools: (ctx, helpers) => ({
    tap: tool({
      description: 'Tap one node.',
      inputSchema: z.object({ target: z.string() }),
      execute: ({ target }) =>
        helpers.guard(async () => {
          await ctx.actions.tap({ id: target });
          return `Tapped #${target}.\n\n${(await ctx.observe()).text}`;
        }),
    }),
    seed_cart: seedCart.tool,
  }),
  buildPrompt: async (ctx) =>
    `Execute this test step: ${ctx.step.instruction}\n\n${ctx.ledger}\n\nScreen:\n${(await ctx.observe()).text}`,
  prepareMessages: (messages) => messages, // compact history, or return { messages, stop }
});

export default defineConfig({
  app: { url: process.env.APP_URL! },
  agent: { model: process.env.E2E_MODEL, executor: myAgent },
});
```

`defineTool` attaches the semantics the harness keys on (`replay`, `mutates`,
`secrets`, optional `platforms`); `isDefinedTool` and `toolAppliesTo` let an
executor merge project tools into its own set and keep a swipe tool off a web
target. `prepareMessages` runs between turns: what it returns carries forward,
and `{ messages, stop }` forces the conclusion when the executor has evidence
the loop guards cannot see.

## Keep the loop, change the vocabulary

`createToolLoopExecutor` is the same chassis over a different vocabulary: the verdict
tool, budget hard stops, loop guards, wind-down near the clock, model
accounting, and `--debug` transcripts. Bring your own tool vocabulary and it
does the rest. This is how you drive something that is not a browser, such as
a device-automation toolkit:

```ts title="e2e.config.ts"
import { createToolLoopExecutor } from 'e2e/agent';
import { tool } from 'ai';
import { z } from 'zod';
import { device } from './my-device'; // e.g. a computer-use / device SDK

export default defineConfig({
  agent: createToolLoopExecutor({
    name: 'device-agent',
    system: 'You control a device. Address elements by their visible label.',
    buildPrompt: (ctx) => ctx.step.instruction,
    tools: (ctx, { guard }) => ({
      screenshot: tool({
        description: 'Look at the device screen',
        inputSchema: z.object({}),
        execute: () =>
          guard(async () => {
            ctx.budgets.recordToolCall({ name: 'screenshot', mutates: false });
            return device.describeScreen();
          }),
      }),
      tap: tool({
        description: 'Tap an element by label',
        inputSchema: z.object({ label: z.string() }),
        execute: ({ label }) =>
          guard(async () => {
            ctx.budgets.recordToolCall({ name: 'tap', mutates: true });
            return device.tap(label);
          }),
      }),
    }),
  }),
});
```

`guard()` stops a tool from running once the step is concluding and turns
budget and timeout stops into a clean end of the loop; `recordToolCall` is
what counts your tool against the step's action budget; the chassis cannot
see inside a foreign tool, so an unrecorded call is an unbudgeted one. The
step deadline still settles the verdict either way, but a device operation
that ignores cancellation finishes on its own time, so keep tool bodies
short and interruptible.

## Replace the executor

`agent` accepts anything implementing `StepExecutor`: no AI SDK, no model,
any decision process you like.

```ts
import type { StepExecutor } from 'e2e';

const scripted: StepExecutor = {
  name: 'scripted',
  version: '1',
  async runStep(ctx) {
    const screen = await ctx.observe();      // redacted semantic tree
    await ctx.actions.tap({ id: 'n42' });    // policed, budgeted, recorded
    return { status: 'passed', summary: 'did the thing and saw the result' };
  },
};

export default defineConfig({ agent: scripted });
```

`ctx.actions` is the whole action surface (`tap`, `type`, `typeSecret`,
`press`, `select`, `scroll`, `navigate`) and `ctx.observe()` is the only view
of the app. `ctx.target.verbs` is the subset of those verbs the target's backend
declared (a backend with `perform` gives `tap`/`type`/`typeSecret`/`press`/
`select`, `swipe` gives `scroll`, `app.navigate` gives `navigate`); offer a model
exactly that vocabulary rather than a verb the
surface can only reject.
Secrets in params arrive as name-only placeholders; `actions.typeSecret(target,
name)` performs the authorized fill without the plaintext ever passing through
your code or a model.

## The verdict

Whatever the executor, a step ends one of three ways:

- **passed**: the app behaved as the step required, verified on screen.
- **failed**: it did not. An ordinary test failure.
- **blocked**: credentials, the environment, seed data, or budget prevented a
  product verdict. The error code decides the exit: credential, environment,
  and seed-data blocks exit as configuration or infrastructure; budget and
  timeout blocks remain test failures.

The loop chassis also polices itself: guards catch a model repeating the same
call or cycling, and a wind-down forces a conclusion near the turn budget and
the step clock, so slow providers conclude rather than time out.

## Cost

| Call | Model calls | Default timeout |
| --- | --- | --- |
| `act` | up to `agent.maxModelCalls`, default 25 | test `timeout`, 120 s |
| `assert` | 1 | 30 s |
| `extract` | 2 | 30 s |
| `waitFor` | up to `agent.maxModelCalls`, default 25 | 30 s |

Exceeding a budget raises `STEP_BUDGET_EXHAUSTED`; running out of time,
`STEP_TIMEOUT`. Keep suites cheap: assert with `expect` when the check is
mechanical, scope `act` to the step that breaks, and give slow providers
`timeout` room; latency is not a defect.

## Inspect a run

`--debug` tells you how long each step took and what it cost. To see *why* —
which tokens went to the system prompt, the tool definitions, or a screen
snapshot that was resent five times — record the run and open it in a trace
viewer:

```bash
npx e2e run --ai-trace
npx unbox-ai .e2e/ai-trace.json
```

`--ai-trace` writes `.e2e/ai-trace.json` next to the report, in the AI SDK
devtools database shape that [unbox-ai](https://github.com/tester-army/unbox-ai)
reads directly. Every agent step is one run, named after the test and the
step, so `unbox-ai runs .e2e/ai-trace.json` lists your agent steps and
`unbox-ai compare --run 0 --run 1` diffs two of them. Inside a run, every model
round trip is one step: an `agent.act` turn, a `waitFor` poll, a judgment's
repair round. A generation made inside a `defineTool` tool nests under the
step that called it, and a step the trace cache replayed zero-turn makes no
model call and so leaves no run. Each step carries the prompt as sent (system prompt first), the tool
definitions with their JSON schemas, the response, usage, model latency, and
the provider metadata — including the AI Gateway's per-request cost.

The trace records the model's view and nothing else. Observations are
redacted before the model sees them, so the trace holds no secret the model
did not; image evidence appears by byte size, never as pixels. It is a
debugging aid, not part of the report, and `e2e init` ignores it.

The recorder is an AI SDK telemetry integration, so it also sees calls a
custom executor makes through its own `ai` import. The reverse works too:
`registerTelemetry` in your config runs in every worker, so any AI SDK
telemetry integration observes the run — for example the
[`@ai-sdk/devtools`](https://www.npmjs.com/package/@ai-sdk/devtools) recorder
whose live viewer `npx unbox-ai devtools` replaces. That integration keeps one
database per process and rewrites it whole, so use it with `workers: 1`.
