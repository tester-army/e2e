The `agent` fixture is how you dial model authority up and down. Each call is one
bounded operation with its own deadline and model-call budget, and your code
always decides the order.

```ts
await agent.act('complete checkout with the test card');  // plan and execute
await agent.tap('the Pro plan card');                     // pick one node
await agent.assert('the dashboard shows a trial badge');   // answer one question
const data = await agent.extract('the invoice total', { schema }); // return data
```

## Configure a model

There is no default model. Set one in config:

```ts title="e2e.config.ts"
export default defineConfig({
  agent: { model: 'anthropic/claude-sonnet-4.5' },
});
```

Or per run:

```bash
E2E_MODEL=openai/gpt-5.4-mini E2E_MODEL_API_KEY=... npx e2e run
```

A `provider/model-id` string is routed through the
[Vercel AI Gateway](https://vercel.com/docs/ai-gateway), so one key reaches any
provider. The key is read from `E2E_MODEL_API_KEY`, falling back to
`AI_GATEWAY_API_KEY`, and never appears in logs or reports.

To use a provider directly, pass a live AI SDK model instance. It brings its own
transport and credentials, so any provider package works - including a local one:

```ts title="e2e.config.ts"
import { openai } from '@ai-sdk/openai';

export default defineConfig({
  agent: { model: openai('gpt-5.4-mini') },
});
```

Give the model a little project context when your UI has domain language:

```ts
export default defineConfig({
  agent: {
    model: 'anthropic/claude-sonnet-4.5',
    context: 'A billing dashboard. Plans are Free, Pro, and Enterprise.',
  },
});
```

## Planned flows

`agent.act` hands one goal to the model and lets it plan and execute the steps to
reach it. Use it for flows that are tedious to spell out or still changing shape.

```ts
await agent.act('complete checkout with the test card');
await agent.act('invite {email} as an editor', { email: 'ada@example.test' });
```

Values come from your code through `params`, never from the model's imagination.
The call is still bounded by a deadline, a step budget, and a model-call budget,
and it is still one step in your test: it returns, and your next line runs.

You can also ask a planned flow to hand data back:

```ts
const result = await agent.act('read the receipt', undefined, {
  schema: z.object({ total: z.number() }),
});
```

<Callout intent="warning" title="Not implemented yet">
`agent.act` and `agent.login` reject with `UNSUPPORTED_CAPABILITY` in the current
release. Described targets and judgments, below, are complete and cover the same
ground one step at a time.
</Callout>

## Described targets

Located actions are the workhorse. The model sees one snapshot of the screen and
returns one node; the runner turns that into a readable query and performs one
action.

```ts
await agent.tap('the Add button');
await agent.type('the new todo input', 'Buy milk');
await agent.press('the search field', 'Enter');
await agent.select('the Team dropdown', 'Mobile');
await agent.check('the Email notifications checkbox');
await agent.hover('the card actions area');
await agent.longPress('the Design review card');
await agent.dragTo('the Design review card', 'the Done column');
await agent.upload('the Attachment file input', 'fixtures/attachment.txt');
await agent.scroll({ direction: 'down', momentum: 'fast' });
await agent.scrollTo('the Acknowledge release notes button');
```

Two rules make these predictable:

- The model chooses the target. You choose the verb and the value.
- File paths come from your code, never from the model.

<Tip title="Write targets like you would describe them out loud">
Name the visible affordance, and prefer the exact wording on screen: `'the Sign
in button'` beats `'the submit control at the bottom of the form'`. Describe one
target, not a flow - if you catch yourself writing "and then", split the call.
</Tip>

## Judgments

Ask a yes/no question about the screen. One observation, one answer, one
explanation.

```ts
await agent.assert('the todo list contains exactly one item called "Buy milk"');
```

A false answer raises `ASSERTION_FAILED` with the model's explanation, and a
screenshot is attached to the report as evidence. It is an ordinary test failure:

```ts
try {
  await agent.assert('the page shows a completed checkout receipt');
} catch (cause) {
  const error = cause as { code?: string; explanation?: string };
  expect(error.code).toBe('ASSERTION_FAILED');
}
```

`assert` looks once. To wait for something to become true, use `waitFor`:

```ts
await agent.waitFor('the network status reports that users finished loading', {
  intervalMs: 500,
  timeout: 120_000,
});
```

## Extracting data

Pull structured values off the screen, validate them, then branch in TypeScript.

```ts
import { z } from 'zod';

const data = await agent.extract('every todo title and how many remain', {
  schema: z.object({
    titles: z.array(z.string()),
    remaining: z.number().int(),
  }),
});

expect(data.titles).toContain('Ship runner');
expect(data.remaining).toBe(2);
```

Any [Standard Schema](https://standardschema.dev) validator works, zod included.
Invalid output gets one repair attempt and then fails with
`MODEL_OUTPUT_INVALID`. A guess never passes as a success.

<Callout intent="warning" title="Assert on meaning, not on wording">
Different models phrase things differently. Check containment and shape rather
than an exact sentence:

```ts
expect(summary.plan).toContain('Pro');   // good
expect(summary.plan).toBe('Pro plan');   // brittle
```
</Callout>

## What the model sees

By default only three things reach the model:

- a redacted snapshot of the screen: roles, accessible names, text, test IDs, and
  states
- a short summary of previous steps in the same test
- your `agent.context` string

It never receives raw HTML, cookies, headers, network bodies, or environment
values. Password fields arrive masked, and any configured credential value found
on screen is replaced with a placeholder before the snapshot leaves the runner.
Screenshots are for your report, not the model, unless you ask for them with
`vision`.

## Seeing the screen

Some things no snapshot describes: a chart drawn on a canvas, a map pin, a
WebGL scene, a custom widget with no semantics, or a purely visual property like
a trend or a broken layout. Pass `vision: true` and the model also gets a masked
screenshot of the current screen.

```ts
await agent.assert('the chart trends upward', { vision: true });
await agent.tap('the red pin on the map', { vision: true });
```

It needs a model that accepts images. Set `agent.vision` in config to pick a
default for a whole project, and override it per call.

The snapshot still goes with it — vision adds pixels, it never replaces the tree.
That is what keeps a vision `tap` on a real control resolving to a real node.
When the tree genuinely describes nothing, as on a canvas, the model can point at
the screenshot instead, and the runner validates that point, checks what is under
it, records both, and taps exactly there. Only `tap` and `click` can act on a
point; everything else needs a node.

### Judging the screen, not the snapshot

`vision: true` gives the model both, which is wrong for a visual assertion: the
snapshot is the easier read, so that is what gets read. "The form is visible and
not covered" is *satisfied* by a snapshot in which the form is present and named,
even with a consent sheet over it.

```ts
await agent.assert('the search form is visible and not covered', { vision: 'only' });
```

`'only'` sends the screenshot and leaves the snapshot out, so there is nothing
else to answer from. It costs less than `true`, not more. Reach for `true` when
the snapshot is part of the answer — "the submit button is disabled" lives in the
snapshot and is often invisible on screen.

A locate under `'only'` can only point, since no node identifiers were shown, so
`tap` and `click` work and `type`, `select`, `upload`, `scrollTo`, and `dragTo`
refuse it rather than blind-clicking something they could have addressed. And if
pixels are unavailable — a tainted viewport after a secret fill — `'only'` fails
instead of quietly answering from the snapshot.

One thing to expect: the screenshot is the viewport, not the whole page. A
snapshot-based "the list shows prices" passes because the DOM holds every price;
the same question on pixels fails when the first card is cut off above its price.
That is the mode working, not breaking — but write `'only'` conditions about what
is on screen, and scroll before asking about anything further down.

### Paying for pixels only when the tree fails

`vision: 'fallback'` is the middle setting. The call runs on the snapshot alone
first, and pixels are attached only if that misses — the model says nothing
matches, or the node it picked cannot be re-found by any derived query. That
second case is the common one on real sites: an offer card is a single link whose
accessible name is the entire card, so nothing can address it again. Seeing the
card, the model picks the small inner control it would actually click.

```ts
// Free on a page whose tree is fine; pays for one screenshot on a page whose isn't.
await agent.tap('the first offer card in the results', { vision: 'fallback' });
```

It escalates once per call, never after an action has been dispatched, and the
step records `visionEscalated: true` so you can see which steps needed it.

`assert`, `waitFor`, `extract`, and `scrollTo` stay on the snapshot under
`'fallback'`: they always produce an answer, so there is no miss to detect —
escalating on a failed assertion would only bias it toward passing. Use
`vision: true` there.

Three things to expect:

- Images are billed as input tokens, so `vision: true` costs more than the same
  call without it on every call. Reach for it on the step that needs pixels, use
  `'fallback'` when you only want it as a safety net.
- Once a test fills a secret, the screen stays pixel-tainted for the rest of the
  attempt: vision calls silently continue with the snapshot alone, and the report
  records that pixels were withheld.
- Pointing needs a model that is good at visual grounding, which is a much higher
  bar than accepting an image. A weak model judges a chart correctly and still
  returns a confident wrong coordinate for a pin. Pin `agent.visionModel` for
  suites that point.

### Pinning a model for pixels

The model that reads your snapshots well is often not the model that points
accurately. `agent.visionModel` pins the one that vision calls use, leaving every
other call on `agent.model`:

```ts
export default defineConfig({
  agent: {
    model: 'google/gemini-3-flash',
    visionModel: 'openai/gpt-5.6-luna',
  },
});
```

`E2E_VISION_MODEL` overrides it, the way `E2E_MODEL` overrides `agent.model`.
Unset, calls that send pixels use `agent.model`. Each step in the report records the model
it actually used, so a mixed run stays auditable.

When a pointed tap lands in the wrong place, the step tells you where it went:
the report records the point the model chose, what the runner hit-tested there,
and the model's own explanation.

```
the model pointed at (391, 253) for "the red pin on the map";
the runner hit-tested no semantic node there.
The model explained: The red pin is the red circular marker in the map area.
```

## Cost and limits

Every call is bounded, so a bad prompt cannot spend your budget in a loop.

| Call | Model calls | Default timeout |
| --- | --- | --- |
| Located actions (`tap`, `type`, `select`, …) | 2 | `actionTimeout`, 30 s |
| `dragTo` | 4 | `actionTimeout`, 30 s |
| `scroll` without `within` | 0 | `actionTimeout`, 30 s |
| `assert` | 1 | 30 s |
| `extract` | 2 | 30 s |
| `waitFor` | up to `agent.maxModelCalls`, default 25 | 30 s |

`vision: true` changes no budget in this table; it makes each of those calls
carry an image, which costs input tokens.

Exceeding a budget raises `STEP_BUDGET_EXHAUSTED`; running out of time raises
`STEP_TIMEOUT`. Both are test failures you can see in the report.

Keeping an agentic suite cheap:

- Assert with `expect` when the check is mechanical. It is free.
- Use a described target for the step that breaks, not for the whole test.
- Give `actionTimeout` room when a provider is slow. Latency is not a defect.
- Keep `waitFor` intervals coarse; each poll is a model call.

## Caching

Repeat runs should not pay for work already done. e2e caches how a described
target resolved, so a later run replays a readable query instead of asking the
model again.

```ts
await agent.tap('the Pro plan card');
// first run:  one model call, then getByRole('button', { name: 'Pro' })
// later runs: cache hit, same query, no model call
```

Keys include the test, the target, the instruction and its parameters, the route
you were on, and your configuration. They deliberately do **not** include the
page's content: a listing whose prices and ordering change every minute would
otherwise cold-start the cache on every run. What keeps a hit correct is that the
stored locator is semantic and gets re-resolved and re-verified against the live
page before anything happens.

Set the policy with `agent.cache`, or per call:

```ts
await agent.tap('the Pro plan card', { cache: false });
```

```ts title="e2e.config.ts"
export default defineConfig({
  agent: { cache: 'read-only' },  // 'off' | 'read-only' | 'read-write'
});
```

Entries live in `.e2e/cache/`, one JSON file per key. They are meant to be
committed: a teammate's checkout and CI then start warm. `e2e init` leaves the
directory out of `.gitignore` for exactly that reason.

A cache is never authority. A hit still goes through normal actionability and
origin policy, a stale or corrupt entry falls back to one fresh model locate and
replaces itself, and deleting the directory cannot change what a correct test
means.

<Callout intent="info" title="Scope in this release">
Only located actions are cached (`tap`, `click`, `type`, `scroll`, `scrollTo`,
`longPress`). Other located verbs, and elements inside iframes, report
`bypassed`. Path caching for `agent.act` arrives with the planning tier.
</Callout>

### Positional targets are not cached

Describe a target by *what it is* and it caches. Describe it by *where it sits*
and it will not:

```ts
await agent.tap('the Pro plan card');   // cached
await agent.tap('the first search result');  // never cached
```

The reason is that a stored locator addresses content. If "the first result" were
recorded, the entry would keep resolving to whichever item happened to be first
when it was written — so once the list reordered, a hit would click the *wrong*
row. A cache is allowed to miss; it is never allowed to be wrong. So the runner
recognises a positional instruction and declines to record it, reporting
`not recorded: the instruction targets a position` under `--debug`.

If a step matters and you want it cached, name the thing itself:

```ts
// instead of "the first offer", say what makes it the one you mean
await agent.tap('the offer for the Brilliant Holiday Resort');
```

### Seeing what the cache did

`e2e run --debug` prints one row per agent step explaining what the cache did
and why, plus what it cost and what the hits saved.

```text
[e2e debug] locate cache (1 hit, 1 written, 2 bypassed, cache time 41ms, est. 3.4s model time avoided, net 3.3s faster)
  step                                cache     key           bytes  cache time  model time  why
  agent.tap "the Pro plan card"       hit       f58afea12623   1422        14ms         0ms  replayed getByRole("button", name: "Pro") to role=button name="Pro"
  agent.tap "the annual toggle"       written   9c1d40b7ae02   1180        27ms       3.4s  no entry for this key; recorded getByRole("switch", name: "Annual")
  agent.hover "the price tooltip"     bypassed  -                 -         0ms         0ms  agent.hover is not a cacheable cache-1 method
  agent.waitFor "the plan list …"     bypassed  -                 -         0ms       2.9s  the call performs no located action
```

The `why` column is the useful part. Typical answers:

| Status | Why | Meaning |
| --- | --- | --- |
| `hit` | `replayed <query> to <node>` | The stored query resolved to one node with the recorded identity. No model call. |
| `written` | `no entry for this key; recorded <query>` | Cold call. The next run with the same screen hits. |
| `miss` | `the stored locator matched 0 nodes` | The UI moved. One fresh locate replaced the entry. |
| `miss` | `the stored key differs` | Something in the key changed — screen, instruction, config, or driver version. |
| `invalid` | a parse or digest failure | The file on disk is not a usable `cache-1` entry and was ignored. |
| `bypassed` | `agent.hover is not a cacheable cache-1 method` | Outside the cacheable verb set. |
| `bypassed` | `the call passed cache: false` | Opted out at the call site. |
| `bypassed` | `agent.cache mode is off` | Disabled by configuration. |
| `bypassed` | `retry attempts never consult the cache` | A retry starts from clean state by design. |
| `miss` | `the instruction targets a position` | Positional target; nothing was recorded, on purpose. |
| `written`/`miss` | `… not recorded: <reason>` | Nothing was stored, so the next run will pay again too. |

<Callout intent="info" title="How the saving is estimated">
A hit avoids exactly one locate model call, but that call never happened, so its
duration cannot be measured. The estimate prices each hit at the mean model call
the same run actually recorded, and is labelled `est.` for that reason. With no
model call to compare against, no number is printed. `cache time` is measured,
not estimated: it is the real cost of reading the entry and resolving its query.
</Callout>

`E2E_DEBUG=agent` additionally streams the same reasons live, as each step runs.

<Callout intent="warning" title="Sharing a cache across machines">
Two key fields decide whether a cache travels: `projectId` and the app's base
URL. `projectId` falls back to a hash of the absolute project path, and the base
URL contributes its origin and path, so a different checkout location or a
random preview port produces a cold cache. Set both explicitly before relying on
a shared or committed cache. The driver version contributes as `major.minor`, so
a patch upgrade keeps your cache warm.
</Callout>
