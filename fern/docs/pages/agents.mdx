The agent you pass to `defineConfig` is a **step executor**: one step in, one
verdict out. The runner owns everything around it: redacted observations,
every action, budgets, origin policy, secrets, the report. Customizing the
agent changes how it decides, not what it is allowed to do.

## Pick a model

There is no default model. `createAgent()` reads `E2E_MODEL`, a
`provider/model-id` string routed through the Vercel AI Gateway, so one
`E2E_MODEL_API_KEY` (or `AI_GATEWAY_API_KEY`) reaches any provider:

```bash
E2E_MODEL=anthropic/claude-sonnet-4.5 E2E_MODEL_API_KEY=... npx --no-install e2e run
```

To use a provider directly, pass a live AI SDK model instance. Any provider
package works, including a local one:

```ts title="e2e.config.ts"
import { openai } from '@ai-sdk/openai';
import { createAgent } from '@e2edev/e2e/agent';

export default defineConfig({
  agent: createAgent({ model: openai('gpt-5.4-mini') }),
});
```

The `agent` key also accepts an options block when you have nothing to
construct: `agent: { model: 'anthropic/claude-sonnet-4.5', context: '...' }`
runs `createAgent()` with those settings. `context` is a sentence or two of
project vocabulary and reaches every `agent.*` call; `visionModel` pins a
separate model for calls that carry pixels. The AI SDK (`ai`) is an optional
peer dependency; deterministic suites and model-free executors never load it.

## Add project tools

`createAgent` builds the built-in agent extended with your tools (AI SDK
tools with declared semantics), and the `agent` config value accepts the agent
itself:

```ts title="e2e.config.ts"
import { defineConfig } from '@e2edev/e2e';
import { createAgent, defineTool } from '@e2edev/e2e/agent';
import { tool } from 'ai';
import { z } from 'zod';

const seedCart = defineTool(
  tool({
    description: 'Seed the cart with a SKU via the store test API',
    inputSchema: z.object({ sku: z.string() }),
    execute: async ({ sku }) =>
      fetch(`${process.env.APP_URL}/api/test/cart?sku=${sku}`).then((r) => r.text()),
  }),
  { replay: 'none', mutates: true, secrets: false },
);

export default defineConfig({
  app: { url: process.env.APP_URL! },
  agent: createAgent({ tools: { seedCart } }),
});
```

Now `agent.act('seed three items and check out')` can call your test API
mid-flow. A tool that only makes sense on some targets declares them:
`{ ..., platforms: ['ios', 'android'] }` keeps a swipe tool off a web target,
and the model never sees a verb the surface cannot honor. `createAgent()` with no arguments is exactly what runs by default;
`system` appends guidance, `model` overrides the config-resolved one.

## Three layers, like the AI SDK

The harness redacts and records; what the model reads is the agent's
decision. The agent surface is layered the way the AI SDK is: a small
opinionated agent on top, the loop under it, and primitives you can call from
your own `ToolLoopAgent` or `generateText` for anything else.

1. **`createAgent`** — the golden path: `model`, `system`, `tools`,
   `maxTurns`, `providerOptions`. Nothing else; when you want to change what
   the model reads, step down one layer.
2. **`createToolLoopExecutor`** — the same loop with your prompt and your
   vocabulary: `buildPrompt` (a string, or a message history to carry a
   conversation across steps), `tools`, `prepareMessages` for between-turn
   compaction, `onConclude` with the step's full transcript, and `loopGuards`
   / `windDown` to tune or disable the loop's own notices.
3. **Primitives** — `createGrammarTools(ctx)`, `createVerdictTool()`,
   `trackModelCalls(ctx, model)`, `conversationMemory(ctx)`,
   `serializeLedger(steps, maxBytes)`, `compactSnapshotHistory(messages)`,
   `formatReplayedPrefix(prefix)`. None loads the `ai` package; each is one
   piece of the discipline above, usable alone.

A model that remembers everything it did in a test is the default loop and
grammar with a prompt that carries the conversation:

```ts title="e2e.config.ts"
import {
  compactSnapshotHistory,
  conversationMemory,
  createGrammarTools,
  createToolLoopExecutor,
} from '@e2edev/e2e/agent';

export default defineConfig({
  agent: createToolLoopExecutor({
    name: 'remembering-agent',
    system: 'Act on node ids from the newest screen; conclude with complete_step.',
    tools: (ctx, { guard }) => createGrammarTools(ctx, { guard }),
    prepareMessages: compactSnapshotHistory,
    buildPrompt: async (ctx) => {
      const memory = conversationMemory(ctx);          // lives in ctx.attempt.memory
      const screen = await ctx.observe();
      const content = `${ctx.step.instruction}\n\nCurrent screen (revision ${screen.revision}):\n${screen.text}`;
      return [...memory.messages, { role: 'user', content }];
    },
    onConclude: (ctx, { messages }) => conversationMemory(ctx).remember(messages),
  }),
});
```

A model that sees nothing but the instruction and the screen is the same
with a `buildPrompt` that returns that string. Steps the model did not run —
a `screen` click, a step the trace cache replayed — are in `ctx.priorSteps`;
filter by `index` past `memory.lastStepIndex` and `serializeLedger` the rest
into a note if you want the model to know.

The third layer with no chassis at all is ordinary AI SDK code:

```ts
import { ToolLoopAgent, stepCountIs } from 'ai';
import { createGrammarTools, createVerdictTool, trackModelCalls, VERDICT_RULES } from '@e2edev/e2e/agent';
import type { StepExecutor } from '@e2edev/e2e';

const raw: StepExecutor = {
  name: 'raw-loop',
  async runStep(ctx) {
    const verdict = createVerdictTool();
    const usage = trackModelCalls(ctx, myModel);
    const agent = new ToolLoopAgent({
      model: myModel,
      instructions: `Drive the step with the tools. ${VERDICT_RULES}`,
      tools: { ...createGrammarTools(ctx), complete_step: verdict.tool },
      stopWhen: [() => verdict.concluded(), stepCountIs(ctx.budgets.maxModelCalls)],
    });
    const screen = await ctx.observe();
    await agent.generate({
      prompt: `${ctx.step.instruction}\n\n${screen.text}`,
      abortSignal: ctx.signal,
      onStepStart: usage.onStepStart,
      onStepEnd: usage.onStepEnd,
    });
    return verdict.verdict() ?? { status: 'failed', summary: 'no verdict' };
  },
};
```

The grammar tools still bottom out in `ctx.actions`, so every action is
policed, budgeted, and recorded; `trackModelCalls` reports each turn to the
step budget; the verdict tool enforces the blocked-code policy. What the
loop reads, remembers, or forgets is yours.

A hand-rolled executor gets the same raw material on its context:
`ctx.priorSteps` (structured, sanitized records of every completed step),
`ctx.ledger` (the runner's serialization of them), `ctx.attempt.memory` (a
per-attempt map the harness holds and never reports), and
`ctx.observe({ tree: true, pixels: true })` for the redacted node tree and
masked pixels instead of, or beside, the text.

## Keep the loop, change the vocabulary

`createToolLoopExecutor` is the chassis under the built-in agent: the verdict
tool, budget hard stops, loop guards, wind-down near the clock, model
accounting, and `--debug` transcripts. Bring your own tool vocabulary and it
does the rest. This is how you drive something that is not a browser, such as
a device-automation toolkit:

```ts title="e2e.config.ts"
import { createToolLoopExecutor } from '@e2edev/e2e/agent';
import { tool } from 'ai';
import { z } from 'zod';
import { device } from './my-device'; // e.g. a computer-use / device SDK

export default defineConfig({
  agent: createToolLoopExecutor({
    name: 'device-agent',
    system: 'You control a device. Address elements by their visible label.',
    buildPrompt: (ctx) => ctx.step.instruction,
    tools: (ctx, { guard }) => ({
      screenshot: tool({
        description: 'Look at the device screen',
        inputSchema: z.object({}),
        execute: () =>
          guard(async () => {
            ctx.budgets.recordToolCall({ name: 'screenshot', mutates: false });
            return device.describeScreen();
          }),
      }),
      tap: tool({
        description: 'Tap an element by label',
        inputSchema: z.object({ label: z.string() }),
        execute: ({ label }) =>
          guard(async () => {
            ctx.budgets.recordToolCall({ name: 'tap', mutates: true });
            return device.tap(label);
          }),
      }),
    }),
  }),
});
```

`guard()` stops a tool from running once the step is concluding and turns
budget and timeout stops into a clean end of the loop; `recordToolCall` is
what counts your tool against the step's action budget; the chassis cannot
see inside a foreign tool, so an unrecorded call is an unbudgeted one. The
step deadline still settles the verdict either way, but a device operation
that ignores cancellation finishes on its own time, so keep tool bodies
short and interruptible.

## Replace the executor

`agent` accepts anything implementing `StepExecutor`: no AI SDK, no model,
any decision process you like.

```ts
import type { StepExecutor } from '@e2edev/e2e';

const scripted: StepExecutor = {
  name: 'scripted',
  version: '1',
  cache: 'off',                              // every step reaches runStep; no cached replay
  async runStep(ctx) {
    const screen = await ctx.observe();      // redacted semantic tree as text
    await ctx.actions.tap({ id: 'n42' });    // policed, budgeted, recorded
    return { status: 'passed', summary: 'did the thing and saw the result' };
  },
};

export default defineConfig({ agent: scripted });
```

The context tells the executor where it is: `ctx.step.index` in the attempt's
timeline, `ctx.attempt` with the test id, attempt id, retry index, a signal
that fires when the attempt ends, and `memory` for anything the executor
wants to keep across the steps of one test. Serial-group members share the
attempt scope, as they share the ledger.


`ctx.actions` is the whole action surface (`tap`, `type`, `typeSecret`,
`press`, `select`, `scroll`, `navigate`) and `ctx.observe()` is the only view
of the app. `ctx.target.verbs` is the subset of those verbs the target's backend
declared (a backend with `perform` gives `tap`/`type`/`typeSecret`/`press`/
`select`, `swipe` gives `scroll`, `app.navigate` gives `navigate`); offer a model
exactly that vocabulary, as the built-in agent does, rather than a verb the
surface can only reject.
Secrets in params arrive as name-only placeholders; `actions.typeSecret(target,
name)` performs the authorized fill without the plaintext ever passing through
your code or a model.

## The verdict

Whatever the executor, a step ends one of three ways:

- **passed**: the app behaved as the step required, verified on screen.
- **failed**: it did not. An ordinary test failure.
- **blocked**: credentials, the environment, seed data, or budget prevented a
  product verdict. The error code decides the exit: credential, environment,
  and seed-data blocks exit as configuration or infrastructure; budget and
  timeout blocks remain test failures.

The loop chassis also polices itself: guards catch a model repeating the same
call or cycling, and a wind-down forces a conclusion near the turn budget and
the step clock, so slow providers conclude rather than time out.

## Cost

| Call | Model calls | Default timeout |
| --- | --- | --- |
| `act` | up to `agent.maxModelCalls`, default 25 | test `timeout`, 120 s |
| `assert` | 1 | 30 s |
| `extract` | 2 | 30 s |
| `waitFor` | up to `agent.maxModelCalls`, default 25 | 30 s |

Exceeding a budget raises `STEP_BUDGET_EXHAUSTED`; running out of time,
`STEP_TIMEOUT`. Keep suites cheap: assert with `expect` when the check is
mechanical, scope `act` to the step that breaks, and give slow providers
`timeout` room; latency is not a defect.

## Inspect a run

`--debug` tells you how long each step took and what it cost. To see *why* —
which tokens went to the system prompt, the tool definitions, or a screen
snapshot that was resent five times — record the run and open it in a trace
viewer:

```bash
npx --no-install e2e run --ai-trace
npx unbox-ai .e2e/ai-trace.json
```

`--ai-trace` writes `.e2e/ai-trace.json` next to the report, in the AI SDK
devtools database shape that [unbox-ai](https://github.com/tester-army/unbox-ai)
reads directly. Every agent step is one run, named after the test and the
step, so `unbox-ai runs .e2e/ai-trace.json` lists your agent steps and
`unbox-ai compare --run 0 --run 1` diffs two of them. Inside a run, every model
round trip is one step: an `agent.act` turn, a `waitFor` poll, a judgment's
repair round. A generation made inside a `defineTool` tool nests under the
step that called it, and a step the trace cache replayed zero-turn makes no
model call and so leaves no run. Each step carries the prompt as sent (system prompt first), the tool
definitions with their JSON schemas, the response, usage, model latency, and
the provider metadata — including the AI Gateway's per-request cost.

The trace records the model's view and nothing else. Observations are
redacted before the model sees them, so the trace holds no secret the model
did not; image evidence appears by byte size, never as pixels. It is a
debugging aid, not part of the report, and `e2e init` ignores it.

The recorder is an AI SDK telemetry integration, so it also sees calls a
custom executor makes through its own `ai` import. The reverse works too:
`registerTelemetry` in your config runs in every worker, so any AI SDK
telemetry integration observes the run — for example the
[`@ai-sdk/devtools`](https://www.npmjs.com/package/@ai-sdk/devtools) recorder
whose live viewer `npx unbox-ai devtools` replaces. That integration keeps one
database per process and rewrites it whole, so use it with `workers: 1`.
