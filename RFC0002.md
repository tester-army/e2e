# RFC0002: the host tool registry — replaceable tool vocabularies over the policed grammar

Status: draft (Oskar). Depends on RFC0001 (executor socket, trace-1 cache).
Not scheduled; written so the design is agreed before any host swaps its tool
vocabulary in.

## The problem

RFC0001 promises "toolsets on top are replaceable per agent." Today an
executor that brings its own tools has exactly one honest seam:
`budgets.recordToolCall({ name, mutates })`. It is self-reported, the harness
never sees the input or output, a mutating call consumes an action slot and
poisons the rest of the step's replayable prefix (a `tool` gap marker,
`cache/trace.ts`), and the report shows `tool:<name>` with no detail.

That seam keeps the invariants honest, but at the worst possible exchange
rate: a host with a rich vocabulary — email inboxes, SMS, JS evaluation,
vision clicks, file uploads — loses replay for every step that touches one,
and the harness loses the ability to validate, bound, or describe the calls
it is being told about. A host that instead bypasses `recordToolCall`
entirely loses budgets, policy, recording, and the report. Both failure
modes get worse as the vocabulary grows; TesterArmy's is ~60 tools.

The fix is the same inversion RFC0001 applied to the step: the executor
thinks, the harness dispatches. Tools become **registered capabilities the
harness executes**, not calls the executor confesses to afterwards.

## Design

### Registration

```ts
export interface HostTool {
  readonly name: string;                  // stable, kebab or snake; joins events and traces
  readonly description: string;           // for the executor's own prompt assembly
  readonly inputSchema: StandardSchemaV1; // validated by the harness before execute
  readonly replay: 'ui' | 'readonly' | 'mutating';
  execute(input: JsonValue, caps: HostToolCapabilities): Promise<JsonValue>;
}

// config
agent: { executor, tools: [emailInbox, runJavascript, visionClick, ...] }
```

`inputSchema` follows the repo's one schema story (agent/model/schema.ts):
authors write zod (or any Standard Schema vendor), the harness validates via
`~standard.validate`, and `tools.list()` serves the projected JSON Schema
through the existing `deriveJsonSchema` — no new validator dependency, and
tool authors get the same authoring experience executors already have.

Like executors, model instances, and cache stores, tools are live config
values: they never cross a process boundary; workers re-resolve the config
module.

### Dispatch

`StepExecutorContext` gains `tools`:

```ts
tools: {
  list(): readonly { name: string; description: string; inputSchema: JsonSchema }[];
  call(name: string, input: JsonValue): Promise<JsonValue>;
}
```

`list()` is static for the run — the registry is config, not per-step state.
An executor that gates tools per step simply doesn't offer a tool to its
model; the menu is discovery, not mandate.

`call` is harness-owned end to end: the input is schema-validated
(`MODEL_OUTPUT_INVALID` on mismatch, same as verdicts), the call runs under
the step deadline and `actionTimeout`, it serializes on the step's grammar
chain (no tool call interleaves with a grammar action or observation), the
result is passed through the run's redactor before the executor sees it, and
the whole dispatch is recorded as a step event (`kind: 'driver'`,
`name: 'tool:<name>'`, `detail` from the tool name + a bounded input digest —
never the raw input, which may embed page content).

### Capabilities

`execute` receives a narrow, policed surface — not the driver:

```ts
interface HostToolCapabilities {
  actions: ExecutorActions;      // the step's own policed grammar
  observe(): Promise<ExecutorObservation>;
  redact(text: string): string;
  signal: AbortSignal;
}
```

No secret plaintext, ever: a tool that needs a credential goes through
`actions.typeSecret`, which runs the full authorization policy. Tools that
talk to the outside world (an inbox API) hold their own credentials in their
own closure — the harness neither sees nor stores them.

### Replay tiers

The tier is the tool author's declaration of what a recorded call means:

- **`ui`** — the tool is a vocabulary skin over the grammar: its `execute`
  acts only through `caps.actions`. Nothing new is recorded for the tool
  itself; the underlying grammar actions record and replay exactly as if the
  executor had called them directly. This is the tier for `ui_click`,
  `ui_fill`, `ui_hover`-style tools, and it is why a host can replace the
  entire UI vocabulary without touching trace-1: replay is free.
- **`readonly`** — the call observes project state without changing it
  (`email_read`, `analyze_page`). Recorded as a skippable marker: replay
  omits it, because the verification tail after the step owns semantic
  drift, exactly as spec 10 argues for ambient context. It never consumes an
  action slot.
- **`mutating`** — the call changes state the grammar cannot reproduce
  (`run_javascript`, `email_send`, a seed-data API). Consumes an action
  slot and records the same prefix-ending gap marker as today. Honest and
  unchanged: a replay must never silently skip a state change.

A fourth tier — tools that record enough to re-execute themselves on replay
— is deliberately out of scope until someone needs it; it requires per-tool
descriptor durability rules and a re-execution safety argument (OQ3).

**Tiers are declarations, not proofs.** The harness cannot see inside an
`execute` closure: a tool declared `ui` or `readonly` whose closure also
mutates external state records nothing for that side effect, and a replay
silently skips it — exactly the failure the `mutating` tier exists to
prevent, reachable by misdeclaration. Tiers are therefore audited-by-review
trust, enforced socially (a first-party tool registry, code review), not
mechanically. The direct consequence for hosted platforms: a tool authored
by an untrusted third party MUST be registered as `mutating` regardless of
its declaration — the pessimistic tier is the only one that is safe to
assume. OQ5 tracks whether a capability-restricted tier (an `execute` that
receives no ambient I/O) can ever make `ui`/`readonly` mechanically
checkable.

### What `recordToolCall` becomes

It stays, unchanged, as the escape hatch for executor-owned calls the
harness cannot dispatch (a hosted executor calling its own backend). The
registry is the recommended path; the escape hatch keeps its current
worst-case semantics (mutating = gap), which is the correct price for
opacity.

## What this unlocks

- TesterArmy swaps its ~60-tool vocabulary in without forking the harness:
  UI tools ride the grammar (replay intact), inbox/SMS/JS tools declare
  their tier, per-step tool gating stays executor-side (the executor simply
  doesn't offer a tool to the model — `tools.list()` is a menu, not a
  mandate).
- The report and the live event stream describe tool calls with the same
  fidelity as grammar actions (`event.detail`), so a dashboard renders
  `email: read inbox "signup"` without a side lookup.
- OSS builders get the same contract; nothing in the registry names any
  host.

## Open questions

- **OQ1 — cache identity: resolved.** The registered tool roster (names +
  tiers) does not join the trace cache key; it joins the entry's provenance,
  mirroring OQ10's executor-identity answer. A trace that replays is a trace
  whose actions all relocate, regardless of which tools were on the menu —
  but a shared hosted cache needs the roster recorded on the entry to make
  provenance complete evidence, so recording it is normative, not optional.
- **OQ2 — readonly skipping vs. evidence.** A skipped `readonly` call means
  a self-finalized step never re-ran that observation. The verification-tail
  rule (a step self-finalizes only when its recorded tail re-verifies)
  arguably covers it; confirm against a bench flow that gates on an email
  before shipping the tier.
- **OQ3 — the replayable tier.** Deferred until a host demonstrates a
  concrete tool whose replay is both safe and worth it.
- **OQ4 — cost attribution.** A tool that spends model tokens internally
  (`scene_assert`-style) should report usage through a capability rather
  than invisibly; shape TBD with the first such tool.
- **OQ5 — mechanical tier checking.** Whether a capability-restricted
  `execute` (no ambient network/fs, only `caps`) can make `ui`/`readonly`
  declarations verifiable instead of audited. Until then, third-party tools
  are `mutating` by fiat (see "Tiers are declarations, not proofs").
