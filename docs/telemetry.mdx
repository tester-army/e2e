The `e2e` CLI sends anonymous usage data so we can see which commands,
engines, and features are used and where runs fail. It is on by default.
Telemetry includes counts and version information, but no test content, app
content, or credentials.

## Opt out

Any one of these turns it off:

<CodeGroup>
```bash npm
npx e2e telemetry disable   # saved in ~/.config/e2e/telemetry.json
export E2E_TELEMETRY_DISABLED=1          # for a shell or a CI job
export DO_NOT_TRACK=1                    # the cross-tool convention
```

```bash pnpm
pnpm exec e2e telemetry disable   # saved in ~/.config/e2e/telemetry.json
export E2E_TELEMETRY_DISABLED=1          # for a shell or a CI job
export DO_NOT_TRACK=1                    # the cross-tool convention
```

```bash bun
bunx e2e telemetry disable   # saved in ~/.config/e2e/telemetry.json
export E2E_TELEMETRY_DISABLED=1          # for a shell or a CI job
export DO_NOT_TRACK=1                    # the cross-tool convention
```
</CodeGroup>

`npx e2e telemetry` prints the status and, when it is off, why.
`enable` reverses a saved `disable`. Environment variables take precedence.
Running commands check the saved setting again before sending, so disabling
telemetry also applies to commands already running in another terminal.

## See what would be sent

<CodeGroup>
```bash npm
E2E_TELEMETRY_DEBUG=1 npx e2e run
```

```bash pnpm
E2E_TELEMETRY_DEBUG=1 pnpm exec e2e run
```

```bash bun
E2E_TELEMETRY_DEBUG=1 bunx e2e run
```
</CodeGroup>

This prints the exact event payloads to stderr as `[telemetry] {...}` and
sends nothing.

## What is sent

Each command sends a session event. `run` and `explore` also send a run event,
`init` an init event, and `mcp` one event per MCP session. `--help` and
`--version` send nothing, also when asked on a command. Events go in one
request when the command ends, with a two-second deadline for all telemetry
work. `e2e mcp` runs as long as its client does, so it sends each MCP session
event in its own request when that session ends, with the same deadline.

Every event carries these properties.

Who ran it:

| Property | Value |
| --- | --- |
| `distinct_id` | A random id stored in the preferences file. CI uses `ci:<vendor>` instead, and a platform that runs e2e for its users uses `fleet:<name>` when it sets `E2E_TELEMETRY_FLEET` |
| `project_id` | A hash derived from the repository's root commit, shared across full clones. `null` outside git and in a shallow clone |
| `session_id` | A random id for this one invocation |
| `first_run`, `days_since_first_run` | Whether this command created the preferences file, and whole days since it was created. `null` in CI and in a fleet, where no machine persists, and for a preferences file from before the time was recorded |

Where it ran:

| Property | Value |
| --- | --- |
| `os`, `os_release`, `arch`, `cpu_count`, `memory_gb`, `docker`, `wsl`, `tty` | The machine class |
| `sandbox` | The microVM the kernel announces itself as (`firecracker`), else `null` |
| `ci`, `ci_name` | Whether `CI` is set, and the vendor when one announces itself (`github-actions`, `gitlab`, `circleci`, ...) |
| `fleet` | The value of `E2E_TELEMETRY_FLEET` when it is a plain token, `other` when it is not, `null` when unset |
| `coding_agent` | The coding agent whose shell ran the command, when one announces itself (`claude-code`, `cursor`, `codex`, ...) |

Versions:

| Property | Value |
| --- | --- |
| `e2e_version`, `package_manager` | The e2e version and the package manager that invoked the CLI |
| `runtime`, `runtime_version`, `node_version` | `node`, `bun`, or `deno`, and its version; `node_version` is Node's own version, or the Node compatibility version under Bun or Deno |
| `$lib`, `$lib_version`, `$process_person_profile`, `$geoip_disable` | `e2e`, its version, `false`, and `true`: PostHog keeps no person profile and derives no location |

`e2e_cli_session`, once per command:

| Property | Value |
| --- | --- |
| `command` | `init`, `run`, `list`, `cache ls`, `guide`, `telemetry`, ... |
| `flags` | The names of the flags given, such as `--headed` or `--tag`. Never their values |
| `exit_code`, `duration_ms` | How the command ended and how long it took |
| `error_code` | The runner code of the failure that ended the command before it could run (`CONFIG_NOT_FOUND`, `INVALID_CONFIG`, ...), `CLI_USAGE` for a flag or argument the CLI rejected, `null` otherwise. A code that is not an upper-case token is reported as `OTHER` |

`e2e_init_completed`, once per `e2e init`:

| Property | Value |
| --- | --- |
| `result` | `scaffolded`, `already-initialized`, `cancelled`, `install-failed`, `not-interactive`, or `invalid-project` |
| `yes`, `existing_config` | Whether `--yes` was given, and whether a config already existed so no engine or gateway was asked |
| `engine`, `gateway` | The ids of the engine and the model gateway chosen for a new config (`web`, `mobile`, `none`; `vercel`, `openrouter`, `openai-compatible`, `chatgpt`, `copilot`, `grok`, `none`), `null` when not asked. Never the endpoint typed for an OpenAI-compatible gateway |
| `skill`, `mcp`, `install` | Whether the agent skill, the MCP registration, and the dependency install were chosen |

`e2e_run_completed`, once per `e2e run` or `e2e explore`, built from the numbers in `report.json` and the resolved config:

| Property | Value |
| --- | --- |
| `command` | `run` or `explore` |
| `status`, `exit_code`, `duration_ms` | The run's outcome |
| `flags` | The names of the flags given to the run command, never their values |
| `tests_discovered`, `tests_selected`, `tests_executed`, `tests_passed`, `tests_failed`, `tests_interrupted`, `tests_flaky`, `tests_skipped` | The summary counts |
| `attempts_total`, `tests_retried` | How many attempts the run made across tests and serial groups, and how many of them needed more than one |
| `targets`, `platforms`, `engines` | How many targets, on which platforms, and with which engines and versions, as your config declares them: `web`, `ios`, `web@0.6.1`, or your own engine's name and version. A name that is not a plain token of letters, digits, dots, dashes, and underscores is reported as `other` |
| `steps_total`, `steps_agent`, `steps_locator`, `steps_assertion`, `steps_screen`, `steps_app`, `steps_session`, `steps_resource` | Step counts by kind |
| `agent_steps_replayed`, `agent_steps_partial`, `agent_steps_missed`, `agent_steps_vision` | How the replay cache served the agent steps, and how many used pixel evidence |
| `agent_actions` | How often the agent took each action, by the runner's own names: `{"tap": 12, "typeText": 3, "scroll": 2}`. A project's own tools are counted together as `tool` and anything else as `other`; no other name is sent |
| `model_gateway`, `model_provider`, `model_id`, `model_calls`, `model_tokens`, `model_cached_tokens`, `estimated_cost_usd` | For the first model-backed step: the AI SDK provider that served it (`gateway` for the Vercel AI Gateway, `openrouter.chat`, `openai.chat`, ...), the vendor (the first segment of a `vendor/model` id, else the provider), and the public model id (a fine-tuned or routed id is reported as `other`); then the run's totals |
| `cost_source` | `provider` when the provider priced the calls, `none` when the run made model calls nobody priced, `null` for a run without model calls |
| `artifact_bytes` | Size of the artifacts the run wrote |
| `errors`, `error_codes` | How many run-level errors, and the distinct error codes seen anywhere in the run (`LOCATOR_NOT_FOUND`, `APP_UNREACHABLE`, ...), at most 20. A code that is not an upper-case token, the shape of every runner code, is reported as `OTHER` |
| `primary_error_code` | The first error the run recorded, which is the one that decided its status: a run-level error, else the failed attempt's verdict, else a step's; `null` for a clean run |
| `error_kinds` | For `ENGINE_FAILURE`, `MODEL_PROVIDER_FAILED`, and `ERROR`, whose code says where a failure surfaced but not what it was: the code and a kind read off the message against a closed list (`auth`, `rate-limit`, `overloaded`, `timeout`, `network`, `server`, `bad-request`, `device`, `daemon`, `browser`, `permission`, `not-found`, `memory`, `other`), as `MODEL_PROVIDER_FAILED:rate-limit`. Only the kind's name leaves the machine, never the message |

Which config features the run used, absent when the config did not load. Each
is a count, a boolean, or one of the runner's own option values, never a name,
a path, or free text you wrote:

| Property | Value |
| --- | --- |
| `config_workers`, `config_retries` | The worker count and retries the run resolved |
| `config_agents`, `config_custom_executor`, `config_separate_judge`, `config_project_tools` | How many agents are configured, whether any has a custom executor or a judge model of its own, and how many distinct project tools they declare |
| `config_credentials`, `config_secrets` | How many credentials and secrets are configured |
| `config_cache_mode`, `config_cache_store`, `config_cache_strict` | `off`, `read-only`, or `read-write`; `file` or `custom`; whether strict replay is on |
| `config_reporters`, `config_custom_reporters`, `config_artifact_store` | The built-in reporter ids (`list`, `json`, `junit`, `markdown`), how many reporter objects the config adds, and whether an artifact store is set |
| `config_video_modes` | The distinct video modes across targets (`off`, `on`, `retain-on-failure`, `on-first-retry`, `on-all-retries`) |
| `config_app_commands`, `config_environments` | How many targets start an app command, and the distinct app environments (`test`, `staging`, `production`) |

On `e2e explore` only, what the exploration was given and found, by count.
Never the goal, a step's charter, or a finding's words:

| Property | Value |
| --- | --- |
| `explore_ended` | Why it stopped: `finished`, `step-limit`, `time`, `stuck`, or `aborted` |
| `explore_max_steps`, `explore_timeout_ms` | The budgets it ran with |
| `explore_steps`, `explore_steps_passed`, `explore_steps_failed`, `explore_steps_blocked`, `explore_steps_exhausted` | Exploration steps, by how each ended |
| `explore_assessed` | Whether the agent gave a closing assessment |
| `explore_issues`, `explore_warnings`, `explore_findings_by_severity` | Findings by kind, and by severity: `{"1": 0, "2": 1, "3": 0, "4": 0, "5": 1}` |

`e2e_mcp_session`, once per `open_session` an `e2e mcp` server receives, sent when the session closes or the open fails. A session still open when the client kills the server is not sent:

| Property | Value |
| --- | --- |
| `client`, `client_version` | The name and version the MCP client gives itself (`claude-code`, `cursor-vscode`, ...). A value that is not a plain token is reported as `other`; `null` before the client introduced itself |
| `outcome`, `error_code` | `closed` for a session that opened, `open-failed` with the runner code it failed with (`APP_UNREACHABLE`, `ENGINE_FAILURE`, ...) |
| `ended_by` | `agent` for `close_session`, `idle`, `step` for the session's time limit, `server` when the server shut down; `null` for a failed open |
| `platform`, `engine`, `headed` | The target's platform and engine with its version, as for a run, and whether the UI was shown |
| `duration_ms`, `sessions_open` | How long the session lived, and how many other sessions were open when it opened |
| `calls_total`, `calls_failed`, `calls` | Tool calls, failed calls, and calls by the session's own tool names: `{"observe": 4, "tap": 9, "locate": 2, "screenshot": 1}`. A project's own tools are counted together as `tool` and anything else as `other`; no other name is sent |
| `error_codes` | How often each runner code failed a call: `{"LOCATOR_NOT_FOUND": 2}`, at most 20 codes. A code that is not an upper-case token is reported as `OTHER` |

## What is never sent

Test titles, file paths, URLs, origins, instructions, observations, page
content, screenshots, error messages, stack traces, environment variable
values, credentials, or file contents. Nor the names of targets, agents,
credentials, secrets, or project tools, the arguments or results of MCP tool
calls, an exploration's goal, or its findings. Events include only the properties
listed above.

## In CI

CI runs are attributed to the CI vendor rather than to a machine, no
preferences file is written on the runner, and no notice is printed. A coding
agent that sets `CI` in its shell, with no CI vendor around it, counts as the
machine it runs on. Set `E2E_TELEMETRY_DISABLED: '1'` in the job's `env` to
send nothing from CI.

## In a fleet

A platform that runs e2e on its users' behalf starts each run on a fresh
machine, and every fresh machine would otherwise count as a new user. Set
`E2E_TELEMETRY_FLEET=<name>` in those machines and they are attributed to
`fleet:<name>` instead, like CI: no preferences file and no notice. Or set
`E2E_TELEMETRY_DISABLED=1` and send nothing.

## Where it goes

Events go to a PostHog project we operate, in one request to
`eu.i.posthog.com`. PostHog keeps no person profile for the ids and stores
no request address; every event also asks it to skip its GeoIP step, so no
country, city, or coordinates are derived from where the request came from.
The data is read in aggregate. Telemetry falls under the
[security policy](https://github.com/tester-army/e2e/blob/main/SECURITY.md).
[Outbound connections](/security#outbound-connections) lists every other
connection a run can make.

## Feedback

[`e2e feedback`](/reference/cli#e2e-feedback) is not telemetry. It sends
nothing until you, or the coding agent in your shell, run it, and then it
sends the words written into its flags as one `e2e_feedback` event to the
same PostHog project, with the machine facts above. Because it is an explicit
request, a saved `e2e telemetry disable` does not stop it, but
`E2E_TELEMETRY_DISABLED=1` and `DO_NOT_TRACK=1` do: an environment that set
either sends nothing, feedback included. `E2E_TELEMETRY_DEBUG=1` and
`--dry-run` print it instead of sending it. When telemetry is on, the
event carries the same anonymous id as your telemetry events. Secret-named
environment variable values and well-known token shapes are redacted before
it is sent.

## The notice

The first command prints a notice on stderr explaining how to opt out.
`e2e init` is exempt, so a scaffold starts with its prompts rather than a
disclaimer; the first command after it prints the notice. `e2e telemetry`
is exempt too, since it is where you act on the notice. The notice leaves
`--reporter json` output intact. The notice appears again after a
material change to the data collected.
