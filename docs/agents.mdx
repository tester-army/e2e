title: Agents and personas
description: Configure several agents in one suite, pin tests to them, and run one flow as each persona.
---

`agents` in your config is a record of agents by name. `default` is the one
tests run with. Other entries are other brains for the same suite: a model
that reads screens more carefully, a playbook for a UX review, a persona who
has never seen the app.

```ts title="e2e.config.ts"
import type { E2EConfig } from '@e2edev/e2e';
import { createAgent } from '@e2edev/e2e/agent';
import { playwright } from '@e2edev/playwright';
import { gateway } from 'ai';

export default {
  targets: [{ engine: playwright({ url: 'http://localhost:3000' }) }],
  agents: {
    default: { model: gateway('openai/gpt-5.6-luna') },
    thorough: { model: gateway('anthropic/claude-opus-5'), context: 'Verify every claim on screen before concluding.' },
    buyer: { model: gateway('openai/gpt-5.6-luna'), context: 'You are a first-time buyer who has never seen this site.' },
    admin: { model: gateway('openai/gpt-5.6-luna'), context: 'You manage orders and approve refunds.' },
    ux: createAgent({ model: gateway('openai/gpt-5.6-luna'), system: 'Check that each control has a clear label and each action gives visible feedback.' }),
  },
} satisfies E2EConfig;
```

An entry takes one of three shapes:

- **An options block.** `model`, `context`, `visionModel`, `vision`,
  `maxSteps`, `maxModelCalls`, `providerOptions`. This runs the built-in
  agent with those settings.
- **`createAgent(...)`.** The built-in agent with a `system` prompt and your
  own [tools](/tools).
- **An options block with `executor`.** Any [custom executor](/executors),
  composed with the model and budget options.

`context` is a sentence or two of project vocabulary that reaches every
`agent.*` call. `system` on `createAgent` shapes how the agent works.
`visionModel` pins a separate model for calls that carry pixels. The
[config reference](/reference/config#agents) lists every key.

## Pick an agent per run

Without a flag, tests run as `default`. `--agent` re-points them:

```bash
npx --no-install e2e run --agent thorough tests/checkout.e2e.ts
```

Several names run every unpinned test once per agent, a whole-suite sweep
without touching a file:

```bash
npx --no-install e2e run --agent buyer,admin
```

## Pin an agent in the suite

A test, a describe block, or a single call can name its agent. Innermost
wins: a call's `agent` beats the test's, which beats its groups, which beat
the run.

The test bodies below are abbreviated to show agent selection; replace
the placeholder bodies with your app's checkout and refund steps.

```ts title="tests/checkout.e2e.ts"
import { test } from '@e2edev/e2e';

test.describe('checkout as a first-time buyer', { agent: 'buyer' }, () => {
  test('pays for one item', async ({ app, agent }) => { /* ... */ });

  test.describe('refunds', { agent: 'admin' }, () => {
    test('refunds the order', async ({ agent }) => { /* ... */ });
  });

  test('reorders, and the admin approves', async ({ app, agent }) => {
    await app.open('/orders');
    await agent.act('reorder the most recent order');
    // One step under another brain; the ledger carries what the buyer did.
    await agent.act('approve the pending reorder', { agent: 'admin' });
    await agent.assert('the reorder shows as approved');
  });
});
```

`--agent` never overrides a pin it does not name. A persona stays itself
while you benchmark a model across everything that has no opinion. A pin
that names nothing in `agents` fails at collection; a call's unknown name is
`INVALID_ARGUMENT`. Every agent step in the report records the agent it ran
with.

## One flow, several personas

A pin can be a list. The test then runs once per agent named, as one result
each, in one run:

```ts title="tests/checkout.e2e.ts"
import { test } from '@e2edev/e2e';

test.describe('checkout', { agent: ['buyer', 'admin'] }, () => {
  test('pays for one item', async ({ app, agent }) => { /* runs once per persona */ });
  test('applies a promo code', async ({ app, agent }) => { /* ... */ });
});
```

Every result carries the agent it ran as: `agent` in the report, `[admin]`
after the title in the terminal and in JUnit case names, its own result id,
and its own artifact directory. With a list pin, `--agent admin` narrows the
block to the admin alone, while `--agent thorough` leaves it running as both
personas.

A serial group runs as one unit per agent, so its members share the group's
pin. A setup test pins at most one agent.

A persona that must be signed in pairs its pin with a `session`. A session is
one name per block, so a sweep over signed-in personas is a loop over describe
blocks: [Authentication](/authentication#personas) shows the setup test that
produces one session per persona and the loop that consumes them.

## Add project tools

`createAgent` builds the built-in agent extended with your tools (AI SDK
tools with declared semantics), and an `agents` entry accepts the agent
itself:

```ts title="e2e.config.ts"
import type { E2EConfig } from '@e2edev/e2e';
import { createAgent, defineTool } from '@e2edev/e2e/agent';
import { tool } from 'ai';
import { z } from 'zod';

const seedCart = defineTool(
  tool({
    description: 'Seed the cart with a SKU via the store test API',
    inputSchema: z.object({ sku: z.string() }),
    execute: async ({ sku }) =>
      fetch(`${process.env.APP_URL}/api/test/cart?sku=${sku}`).then((r) => r.text()),
  }),
  { mutates: true },
);

export default {
  targets: [{ name: 'web', engine: playwright({ url: process.env.APP_URL! }) }],
  agents: { default: createAgent({ tools: { seedCart } }) },
} satisfies E2EConfig;
```

Now `agent.act('seed three items and check out')` can call your test API
mid-flow. A tool that only makes sense on some targets declares them:
`{ ..., platforms: ['ios', 'android'] }` keeps a swipe tool off a web target,
and the model never sees a verb the surface cannot honor. `createAgent()` with no arguments is exactly what runs by default;
`system` appends guidance, `model` overrides the config-resolved one.

The harness reserves a mutating tool's action slot before executing it and
queues it with grammar actions. Failed calls still consume their reserved
slot and are recorded as failures. Parallel tool calls cannot exceed the
budget by checking it at the same time. Project-tool mutations always mark
trace replay gaps.

Read-only tools can call `getToolContext(executionOptions).observe({ pixels:
true })`, importing `getToolContext` from `@e2edev/e2e/agent`. This is the same
redacted observation and pixel-withholding policy the executor uses. Mutating
tools must request observations in a separate read-only call; their bodies
already occupy the action queue. A tool with evidence worth keeping hands the
observation's pixels to `attachScreenshot(pixels, label)` from the same
context: the file becomes a `screenshot` artifact of the step, in the attempt's
artifact directory and the report's artifact records, and reaches a configured
artifact store, and the call resolves with the artifact's id.

## What the built-in agent sends

The opening prompt carries the instruction, the params, the ledger of
completed steps, and the whole screen once. Every action result and every
`observe` after that reports what changed since the screen the model last
received: lines that appeared, lines that changed with what they read before,
lines that went away. Node ids are stable for as long as an element exists, so
a line the model saw earlier still names the same element and a change update
is a complete picture, not a hint. A node that only moved to another depth is
not reported, and a screen cut at the observation byte limit reports no
removals, since the nodes past the limit were left out rather than gone. A
screen that changed mostly goes out whole again, and the full screen it
replaced is elided from the transcript, which keeps the conversation prefix
stable for prompt caching.

An action result is read after the action's effect. The runner waits, bounded
to two seconds, for the screen to leave the shape the action was resolved
against, so a tap on a link reports the page it opened rather than the page it
left, and a control that did nothing is reported as having no visible effect
instead of returning a stale screen. Clock-like text is ignored when comparing
shapes, so a ticking timer neither ends the wait nor keeps a screen from
settling. A scroll or a mutating project tool waits half a second instead,
long enough for a windowed list to render its next rows; a secret fill, which
leaves no visible trace, waits for nothing. The model may batch several
actions in one turn; they run in order and each reports its own changes, and
an id from the screen the turn saw still resolves when a look in between
renumbered the tree, as an engine that mints ids per observation does, by
re-finding the node's descriptor in the newest screen. A failed action returns
the failure together with the current screen, so a stale id costs no extra
turn, and a targeted action, its secret authorization included, waits at most
15 seconds for its node to become actionable, so a tap blocked by a consent
banner or a modal reports the element in the way instead of spending the whole
`actionTimeout` on it. A node the engine reports stale is re-found by its
descriptor in a fresh capture and the action retried, up to twice, so a list
that remounts its rows under the pointer costs no model turn. Three failed
actions in a row earn a notice to change approach; five force the conclusion.
The `scroll` tool takes `times` to move several screens in one call; each
screen is one recorded action.

## Two layers

The harness redacts and records; what the model reads is the agent's
decision. The agent surface has two layers:

1. **`createAgent`** — the golden path: `model`, `system`, `tools`,
   `maxTurns`, `providerOptions`. Nothing else; when you want to change what
   the model reads, step down one layer.
2. **`createToolLoopExecutor`** — the same loop with your prompt and your
   vocabulary: `buildPrompt` (a string, or a message history to carry a
   conversation across steps), `tools`, and `prepareMessages` for
   between-turn compaction, which may also return `{ messages, stop }` when
   your own history shows the step is not progressing.

A hand-rolled executor gets the raw material on its context: `ctx.ledger`
(the runner's serialization of every completed step), `ctx.attempt.memory` (a
per-attempt map the harness holds and never reports), and
`ctx.observe({ tree: true, pixels: true })` for the redacted node tree and
masked pixels instead of, or beside, the text.

## Keep the loop, change the vocabulary

`createToolLoopExecutor` is the chassis under the built-in agent: the verdict
tool, budget hard stops, loop guards, wind-down near the clock, model
accounting, and `--debug` transcripts. Bring your own tool vocabulary and it
does the rest. This is how you drive something that is not a browser, such as
a device-automation toolkit:

```ts title="e2e.config.ts"
import { createToolLoopExecutor } from '@e2edev/e2e/agent';
import { tool } from 'ai';
import { z } from 'zod';
import { device } from './my-device'; // e.g. a computer-use / device SDK

export default {
  agents: {
    default: createToolLoopExecutor({
      name: 'device-agent',
      system: 'You control a device. Address elements by their visible label.',
      buildPrompt: (ctx) => ctx.step.instruction,
      tools: (ctx, { guard }) => ({
        screenshot: tool({
          description: 'Look at the device screen',
          inputSchema: z.object({}),
          execute: () =>
            guard(() => ctx.budgets.runTool({ name: 'screenshot', mutates: false }, async () => {
              const observation = await ctx.observe();
              return observation.text;
            })),
        }),
        tap: tool({
          description: 'Tap an element by label',
          inputSchema: z.object({ label: z.string() }),
          execute: ({ label }) =>
            guard(() => ctx.budgets.runTool({ name: 'tap', mutates: true }, () => device.tap(label))),
        }),
      }),
    }),
  },
} satisfies E2EConfig;
```

`guard()` stops a tool from running once the step is concluding and turns
budget and timeout stops into a clean end of the loop. `runTool` reserves the
action budget before the body runs, serializes mutations, and records their
outcomes. A mutating `runTool` body must call its engine directly; queuing another grammar operation from
inside that body would wait on itself. The
step deadline still settles the verdict either way, but a device operation
that ignores cancellation finishes on its own time, so keep tool bodies
short and interruptible.

## Replace the executor

An agent is anything implementing `StepExecutor`: no AI SDK, no model,
any decision process you like.

```ts
import type { StepExecutor } from '@e2edev/e2e';

const scripted: StepExecutor = {
  name: 'scripted',
  version: '1',
  cache: 'off',                              // every step reaches runStep; no cached replay
  async runStep(ctx) {
    const screen = await ctx.observe();      // redacted semantic tree as text
    await ctx.actions.tap({ id: 'n42' });    // policed, budgeted, recorded
    return { status: 'passed', summary: 'did the thing and saw the result' };
  },
};

export default { agents: { default: scripted } } satisfies E2EConfig;
```

The context tells the executor where it is: `ctx.step.index` in the attempt's
timeline, `ctx.attempt` with the test id, attempt id, retry index, a signal
that fires when the attempt ends, and `memory` for anything the executor
wants to keep across the steps of one test. Serial-group members share the
attempt scope, as they share the ledger.


`ctx.actions` is the whole action surface (`tap`, `type`, `typeSecret`,
`press`, `select`, `scroll`, `navigate`, `tapAt`) and `ctx.observe()` is the
tree view of the app. `ctx.target.verbs` is the subset of those verbs the
target's engine declared (an engine with `perform` gives
`tap`/`type`/`typeSecret`/`press`/`select`, `swipe` gives `scroll`, `tapAt`
gives `tapAt`, `app.navigate` gives `navigate`); offer a model exactly that
vocabulary, as the built-in agent does, rather than a verb the surface can
only reject. `ctx.vision.tap(description)` and `ctx.vision.look({ question })`
are the pixel path: the harness captures masked pixels, asks the agent's
`visionModel`, and taps or describes on your executor's behalf, counting the
call against the step's model-call budget. The vision-located tap is not a
verb of its own: it rides `tap` when the located point lands on a listed
control and `tapAt` when it does not. `ctx.vision.tainted` says when a secret
fill has closed that path for the attempt, so an executor can leave the pixel
verbs out of its vocabulary.
Secrets in params arrive as name-only placeholders; `actions.typeSecret(target,
name)` performs the authorized fill without the plaintext ever passing through
your code or a model.

### Driving the page yourself

An executor that brings its own browser tooling needs the page e2e opened, not a
second one. `@e2edev/playwright` exports `surfaceOf(handle)` for that: the live
`Page` and `BrowserContext` of the current attempt behind the handle you passed
to the target. Both accessors throw `INVALID_STATE` before an attempt is running
or a page is open. `@e2edev/agent-device` has no equivalent export.

```ts
import { playwright, surfaceOf } from "@e2edev/playwright";

const engine = playwright();
const own: StepExecutor = {
  name: "own-tools",
  version: "1",
  cache: "off",
  async runStep(ctx) {
    const page = surfaceOf(engine)!.page();   // the page app.open() navigated
    await ctx.budgets.runTool({ name: "click", mutates: true }, () =>
      page.getByRole("button", { name: "Save" }).click(),
    );
    return { status: "passed", summary: "saved" };
  },
};
```

What you do there is out of band: the harness still bounds the step, records
the verdict, and keeps the ledger, but it witnesses no actions, records no trace
for replay, and attaches no artifacts. Report tool calls and model calls through
`ctx.budgets` so the step keeps its metrics and provenance.

## The verdict

Whatever the executor, a step ends one of three ways:

- **passed**: the app behaved as the step required, verified on screen.
- **failed**: it did not. An ordinary test failure.
- **blocked**: credentials, the environment, seed data, or budget prevented a
  product verdict. The error code decides the exit: credential, environment,
  and seed-data blocks exit as configuration or infrastructure; budget and
  timeout blocks remain test failures.

The loop chassis also polices itself: guards catch a model repeating the same
call or cycling, and a wind-down forces a conclusion near the turn budget and
the step clock, so slow providers conclude rather than time out.

## Cost

| Call | Model calls | Default timeout |
| --- | --- | --- |
| `act` | up to `agent.maxModelCalls`, default 25 | test `timeout`, 120 s |
| `assert` | 2 | 30 s |
| `extract` | 2 | 30 s |
| `waitFor` | up to `agent.maxModelCalls`, default 25 | 30 s |

Exceeding a budget raises `STEP_BUDGET_EXHAUSTED`; running out of time,
`STEP_TIMEOUT`. Keep suites cheap: assert with `expect` when the check is
mechanical, scope `act` to the step that breaks, and give slow providers
`timeout` room; latency is not a defect.

`act` takes no `schema` and no `vision` option: structured data comes from
`agent.extract({ schema })`, and pixels reach an `act` step through its
`tap_visual` and `look` tools, which the harness answers with `visionModel`
and counts as model calls of the step.

## Inspect a run

`--debug` tells you how long each step took and what it cost. To see *why* —
which tokens went to the system prompt, the tool definitions, or a screen
snapshot that was resent five times — record the run and open it in a trace
viewer:

```bash
npx --no-install e2e run --ai-trace
npx unbox-ai .e2e/ai-trace.json
```

`--ai-trace` writes `.e2e/ai-trace.json` next to the report, in the AI SDK
devtools database shape that [unbox-ai](https://github.com/tester-army/unbox-ai)
reads directly. Every agent step is one run, named after the test and the
step, so `unbox-ai runs .e2e/ai-trace.json` lists your agent steps and
`unbox-ai compare --run 0 --run 1` diffs two of them. Inside a run, every model
round trip is one step: an `agent.act` turn, a `waitFor` poll, a judgment's
repair round. A generation made inside a `defineTool` tool nests under the
step that called it, and a step the trace cache replayed zero-turn makes no
model call and so leaves no run. Each step carries the prompt as sent (system prompt first), the tool
definitions with their JSON schemas, the response, usage, model latency, and
the provider metadata — including the per-request cost where the gateway reports one.

The trace records the model's view and nothing else. Observations are
redacted before the model sees them, so the trace holds no secret the model
did not. Inline bytes and base64 in SDK image and file message parts appear
as decoded byte counts, including media returned through structured tool
outputs. URLs, references, and text are preserved. Encoded strings elsewhere,
including arbitrary tool result JSON, remain in the trace. It is a debugging
aid, not part of the report, and `e2e init` ignores it.

The recorder is an AI SDK telemetry integration, so it also sees calls a
custom executor makes through its own `ai` import. The reverse works too:
calling `registerTelemetry` from `ai` at the top of your config module runs
in every worker, so any AI SDK telemetry integration observes the run, for
example the
[`@ai-sdk/devtools`](https://www.npmjs.com/package/@ai-sdk/devtools) recorder
whose live viewer `npx unbox-ai devtools` replaces. That integration keeps one
database per process and rewrites it whole, so use it with `workers: 1`.
