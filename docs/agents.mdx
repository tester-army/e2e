Define named agents in `agents` to give tests different models, instructions,
or tools. Tests use `default` unless you select another agent.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { createAgent } from 'e2e/agent';
import { web } from '@e2edev/web';
import { gateway } from 'ai';

const vocabulary = 'Plans are called tiers. Billing lives under Settings. "Approve" on an order refunds it.';

export default {
  targets: [{ engine: web({ url: 'http://localhost:3000' }) }],
  agents: {
    default: { model: gateway('openai/gpt-5.6-luna'), context: vocabulary },
    thorough: createAgent({
      model: gateway('anthropic/claude-opus-5'),
      system: 'Verify every claim on screen before concluding a step.',
      context: vocabulary,
    }),
    buyer: createAgent({ model: gateway('openai/gpt-5.6-luna'), system: 'You are a first-time buyer.', context: vocabulary }),
    admin: createAgent({ model: gateway('openai/gpt-5.6-luna'), system: 'You manage orders and approve refunds.', context: vocabulary }),
  },
} satisfies E2EConfig;
```

An entry takes one of three shapes:

- An options object to configure the built-in agent's model, vocabulary, and budgets.
- `createAgent(...)` to add a `system` prompt or [tools](/tools). It takes
  `model`, `system`, and `context` together, so one call is a complete agent.
- A [custom executor](/executors), directly or in an options object with `executor`.

`model` handles acting and judgments unless you set a separate `judge`.
Models that receive screenshots must accept images. See [Models](/models) and
the [config reference](/reference/config#agents).

## Instructions and vocabulary

An agent takes two kinds of text, and they go to different readers.

| | `system` | `context` |
|---|---|---|
| Answers | How should the acting agent work? | What does this app call things? |
| Who reads it | The act loop only | Every model call: act turns and the judges behind `assert`, `waitFor`, and `extract` |
| Belongs here | Persona, caution, what to verify before finishing, how to treat unexpected dialogs | Names of screens and menus, where a feature lives, which button submits a form, domain terms |
| Set on | `createAgent({ system })` | `createAgent({ context })` or the agent's options object, at most `limits.maxAgentContextBytes` |

The split is deliberate. A judge decides whether the screen shows what the
test claims, so it must know the app's words: a judge that does not know
"plans are called tiers" cannot check that a tier was chosen. A judge must
not know the actor's instructions, or a `system` prompt that says "consider a
step done once the form closes" would lower the bar for the verdict too.
Nothing in `system` ever reaches a judge.

A rule of thumb: if the sentence would still be true for a different tester
using the same app, it is `context`. If it would still be true for the same
tester on a different app, it is `system`.

```ts title="e2e.config.ts"
agents: {
  default: {
    executor: createAgent({
      model: gateway('openai/gpt-5.6-luna'),
      // How to work: read by the act loop only.
      system: 'Verify a visible confirmation before completing a step. Close cookie and feedback notices you did not ask for.',
      // What things are called: read by every model call, judges included.
      context: 'Plans are called tiers. Billing lives under Settings. Sales documents are quotes until "Convert to order".',
    }),
    maxSteps: 40,
  },
},
```

Wrapping `createAgent` in an options object, for budgets or `providerOptions`,
needs no second `model` or `context` key. Set the vocabulary in one place, on
`createAgent` or on the options object; two different values for one agent is
`INVALID_CONFIG`, as it is for `model`.

A test or group can add vocabulary of its own with `agentContext`, which is
appended after the agent's `context` for that test: the ids of seeded data,
a feature flag that changes a label, anything only that test knows.

```ts title="tests/billing.e2e.ts"
test.describe('billing', { agentContext: 'The seeded workspace is called "Acme Trial".' }, () => {
  test('upgrades the tier', async ({ agent }) => { /* ... */ });
});
```

Keep instructions out of `agentContext` for the same reason they stay out of
`context`: it reaches the judges.

## Make the agent yours

When a step fails or takes too many calls, inspect its report or run with
`--debug` to see the transcript. Start with the instruction, then adjust the
agent if the problem affects several tests:

1. Use the labels on screen in the goal.
2. Put shared vocabulary in `context`, or in `agentContext` for one test.
3. Put instructions for the actor, such as verifying a visible confirmation
   before completing a step, in `system` through `createAgent`.
4. Add [tools](/tools) for operations such as seeding a cart through a test API.
5. Compare models or `providerOptions` by running the same tests with
   `--agent <name>`.

Named agents can use the [trace cache](/cache). Custom tools and executors
have their own replay constraints, described on their pages.

## Pick an agent per run

Use `--agent` to choose the agent for tests that do not specify one:

```bash
npx e2e run --agent thorough tests/checkout.e2e.ts
```

Several names run each unpinned test once per agent:

```bash
npx e2e run --agent buyer,admin
```

## Pin an agent in the suite

A test, describe block, or individual call can select an agent. The closest
setting wins, in this order: call, test, enclosing groups, run.

The abbreviated tests below show how to select an agent at each level.

```ts title="tests/checkout.e2e.ts"
import { test } from 'e2e';

test.describe('checkout as a first-time buyer', { agent: 'buyer' }, () => {
  test('pays for one item', async ({ app, agent }) => { /* ... */ });

  test.describe('refunds', { agent: 'admin' }, () => {
    test('refunds the order', async ({ agent }) => { /* ... */ });
  });

  test('reorders, and the admin approves', async ({ app, agent }) => {
    await app.open('/orders');
    await agent.act('reorder the most recent order');
    // The admin's act call receives the earlier steps in the ledger.
    await agent.act('approve the pending reorder', { agent: 'admin' });
    await agent.assert('the reorder shows as approved');
  });
});
```

`--agent` does not replace an explicitly selected agent. An unknown agent
on a test or group fails during collection. An unknown agent on a call raises
`INVALID_ARGUMENT`. Reports record the agent for each step.

## One flow, several personas

Select several agents to run the same test once with each:

```ts title="tests/checkout.e2e.ts"
import { test } from 'e2e';

test.describe('checkout', { agent: ['buyer', 'admin'] }, () => {
  test('pays for one item', async ({ app, agent }) => { /* runs once per persona */ });
  test('applies a promo code', async ({ app, agent }) => { /* ... */ });
});
```

Each agent gets a separate result and artifact directory. Terminal and JUnit
test names include the agent, such as `[admin]`.

For the list above, `--agent admin` selects only `admin`. A flag with no
matching name, such as `--agent thorough`, leaves both selected agents in place.

A serial group runs as one unit per agent, so its members share the group's
pin. A setup test pins at most one agent.

Selecting an agent does not switch the signed-in user. For signed-in personas,
pair each agent with a `session` in a separate describe block.
[Signing in](/authentication#several-signed-in-users) shows how to create the
sessions and run the tests.
