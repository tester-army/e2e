An agent is a named entry in `agents` with its own model, instructions,
and tools. Tests use `default` unless you select another agent. Name more
agents to compare models or to run one flow as several personas.

## Define named agents

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';

const vocabulary = 'Plans are called tiers. Billing lives under Settings. "Approve" on an order refunds it.';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  agents: {
    default: { model: gateway('openai/gpt-6-luna-fast'), context: vocabulary },
    thorough: {
      model: gateway('anthropic/claude-opus-5'),
      system: 'Verify every claim on screen before concluding a step.',
      context: vocabulary,
    },
    buyer: { model: gateway('openai/gpt-6-luna-fast'), system: 'You are a first-time buyer.', context: vocabulary },
    admin: { model: gateway('openai/gpt-6-luna-fast'), system: 'You manage orders and approve refunds.', context: vocabulary },
  },
} satisfies E2EConfig;
```

An entry holds the `model`, an optional `judge`, the `system` prompt, the
app's `context`, [tools](/tools), budgets, and `providerOptions`. `maxSteps`
caps the actions of one step and `maxModelCalls` its model calls. Both
default to 25 and go up to 100.

Each entry starts from the built-in defaults, never from `default`. Give
each entry its model and context, for example from a shared constant as
above. `model` acts and judges, unless you set a separate `judge`. A model
that gets screenshots must accept images. See [Models](/models) and the
[config reference](/reference/config#agents).

A [custom executor](/executors) goes under `executor`. The model, judge,
context, and budgets still apply. `system` and `tools` are rejected there,
because the executor brings its own prompt and tools.

## Instructions and vocabulary

An agent takes two kinds of text. `system` tells the acting agent how to
work. `context` tells every model call what the app calls things.

| | `system` | `context` |
|---|---|---|
| Answers | How should the acting agent work? | What does this app call things? |
| Who reads it | The act loop only | Every model call: act turns and the judges behind `assert`, `waitFor`, and `extract` |
| Belongs here | Persona, caution, what to verify before finishing, how to treat unexpected dialogs | Names of screens and menus, where a feature lives, which button submits a form, domain terms |
| Set on | `agents.<name>.system` | `agents.<name>.context`, at most 16 KiB |

A judge that doesn't know plans are called tiers can't check that a tier
was chosen. A judge never sees `system`, so "a step is done once the form
closes" can't lower the bar for a verdict. Rule of thumb: true for any
tester on this app goes in `context`, true for this tester on any app goes
in `system`.

```ts title="e2e.config.ts"
agents: {
  default: {
    model: gateway('openai/gpt-6-luna-fast'),
    // How to work: read by the act loop only.
    system: 'Verify a visible confirmation before completing a step. Close cookie and feedback notices you did not ask for.',
    // What things are called: read by every model call, judges included.
    context: 'Plans are called tiers. Billing lives under Settings. Sales documents are quotes until "Convert to order".',
    maxSteps: 40,
  },
},
```

A test or group adds its own vocabulary with `agentContext`. e2e appends it
after the agent's `context` for that test. Use it for facts only that test
knows, such as seeded data or a feature flag that changes a label:

```ts title="tests/billing.e2e.ts"
import { describe, test } from 'e2e';

describe('billing', { agentContext: 'The seeded workspace is called "Acme Trial".' }, () => {
  test('upgrades the tier', async ({ agent }) => { /* ... */ });
});
```

Keep instructions out of `agentContext`. Like `context`, it reaches the
judges.

## Pick an agent per run

`--agent` chooses the agent for tests that don't select one. Several names
run each of those tests one time per agent:

<CodeGroup>
```bash npm
npx e2e run --agent thorough tests/checkout.e2e.ts
npx e2e run --agent buyer,admin
```

```bash pnpm
pnpm exec e2e run --agent thorough tests/checkout.e2e.ts
pnpm exec e2e run --agent buyer,admin
```

```bash bun
bunx e2e run --agent thorough tests/checkout.e2e.ts
bunx e2e run --agent buyer,admin
```
</CodeGroup>

## Pin an agent in the suite

A test, a describe block, or one call can select an agent. The closest
setting wins: call, then test, then enclosing groups, then run.

```ts title="tests/checkout.e2e.ts"
import { describe, test } from 'e2e';

describe('checkout as a first-time buyer', { agent: 'buyer' }, () => {
  test('pays for one item', async ({ app, agent }) => { /* ... */ });

  describe('refunds', { agent: 'admin' }, () => {
    test('refunds the order', async ({ agent }) => { /* ... */ });
  });

  test('reorders, and the admin approves', async ({ app, agent }) => {
    await app.open('/orders');
    await agent.act('reorder the most recent order');
    // The admin's act call sees what the earlier steps of this test did.
    await agent.act('approve the pending reorder', { agent: 'admin' });
    await agent.assert('the reorder shows as approved');
  });
});
```

`--agent` doesn't replace an agent that a test selects. An unknown agent on
a test or group fails during collection. An unknown agent on a call raises
`INVALID_ARGUMENT`. Reports record the agent of each step.

## One flow, several personas

Select several agents to run the same test one time with each:

```ts title="tests/checkout.e2e.ts"
import { describe, test } from 'e2e';

describe('checkout', { agent: ['buyer', 'admin'] }, () => {
  test('pays for one item', async ({ app, agent }) => { /* runs once per persona */ });
  test('applies a promo code', async ({ app, agent }) => { /* ... */ });
});
```

Each agent gets its own result and artifact directory. Terminal and JUnit
test names include the agent, such as `[admin]`.

`--agent` selects among the pinned agents and never adds one. Here,
`--agent admin` runs only `admin`. `--agent thorough` matches neither, so
both still run.

A serial group runs as one unit per agent, and its members share the
group's pin. A setup test pins at most one agent.

Each agent records its own [replay cache](/cache) entries, keyed by its name
and its context. So `buyer` never replays the steps of `admin`, and a
changed `agentContext` records again. [Project tools](/tools) and
[custom executors](/executors#replay-cache) have their own replay rules.

An agent is not a signed-in user. For signed-in personas, pair each agent
with a `session` in a separate describe block. See
[Signing in](/authentication#several-signed-in-users).

## Make the agent yours

When a step fails or uses too many calls, open its report, or run with
`--debug` to see the transcript. Fix the instruction first. Change the agent
when the problem affects several tests:

1. Use the labels on screen in the goal.
2. Put shared vocabulary in `context`, or in `agentContext` for one test.
3. Put instructions for the actor in `system`.
4. Add [tools](/tools) for operations such as seeding a cart through a test API.
5. Compare models or `providerOptions`: run the same tests with
   `--agent <name>`.
