---
title: Models and credentials
description: Which model an agent uses, which package constructs it, and where its key comes from.
---

An agent runs on one model, and that model is an AI SDK model instance your
config constructs. The runner takes the instance as it is: it constructs no
model of its own, has no default gateway, and reads no model or key variable.
Everything about who serves the model and how it authenticates is decided by
the line in `e2e.config.ts` that builds it.

## Pick a gateway or a provider

A gateway reaches every vendor's models with one key. A provider package calls
one vendor directly. Either way the constructor comes from that package, and
`e2e init` writes the one you chose.

<Tabs>
  <Tab title="Vercel AI Gateway">

```ts title="e2e.config.ts"
import { createAgent } from '@e2edev/e2e/agent';
import { gateway } from 'ai';

export default {
  agents: { default: createAgent({ model: gateway('anthropic/claude-sonnet-4.5') }) },
} satisfies E2EConfig;
```

`gateway()` ships with `ai`, so no extra package. It reads `AI_GATEWAY_API_KEY`.

  </Tab>
  <Tab title="OpenRouter">

```ts title="e2e.config.ts"
import { createAgent } from '@e2edev/e2e/agent';
import { openrouter } from '@openrouter/ai-sdk-provider';

export default {
  agents: { default: createAgent({ model: openrouter('anthropic/claude-sonnet-4.5') }) },
} satisfies E2EConfig;
```

`npm i -D @openrouter/ai-sdk-provider`. It reads `OPENROUTER_API_KEY`.

  </Tab>
  <Tab title="OpenAI-compatible endpoint">

```ts title="e2e.config.ts"
import { createAgent } from '@e2edev/e2e/agent';
import { createOpenAICompatible } from '@ai-sdk/openai-compatible';

const local = createOpenAICompatible({
  name: 'ollama',
  baseURL: 'http://127.0.0.1:11434/v1',
  // apiKey: process.env.LLM_API_KEY, // when the endpoint needs one
});

export default {
  agents: { default: createAgent({ model: local.chatModel('llama3.2') }) },
} satisfies E2EConfig;
```

`npm i -D @ai-sdk/openai-compatible`. Ollama, vLLM, LiteLLM, and most vendors'
own APIs speak this protocol. There is no default URL and no default variable;
you pass both.

  </Tab>
  <Tab title="A provider directly">

```ts title="e2e.config.ts"
import { openai } from '@ai-sdk/openai';
import { createAgent } from '@e2edev/e2e/agent';

export default {
  agents: { default: createAgent({ model: openai('gpt-5.4-mini') }) },
} satisfies E2EConfig;
```

Any AI SDK provider package works the same way: `@ai-sdk/anthropic`,
`@ai-sdk/google`, `@ai-sdk/amazon-bedrock`, a community provider, a local one.
Each reads its own variable (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, ...).

  </Tab>
</Tabs>

| You want | Constructor | Package | Key variable |
| --- | --- | --- | --- |
| One key for every vendor, billed by Vercel | `gateway('vendor/model')` | `ai` | `AI_GATEWAY_API_KEY` |
| One key for every vendor, billed by OpenRouter | `openrouter('vendor/model')` | `@openrouter/ai-sdk-provider` | `OPENROUTER_API_KEY` |
| A local or self-hosted server, or a vendor's OpenAI-shaped API | `createOpenAICompatible({ name, baseURL }).chatModel('model')` | `@ai-sdk/openai-compatible` | whatever you pass as `apiKey` |
| One vendor, your own account | `openai('model')`, `anthropic('model')`, ... | `@ai-sdk/<vendor>` | the vendor's own |

The model id is whatever the package you chose accepts. Gateways take
`vendor/model` (`openai/gpt-5.4-mini`); a direct provider takes the vendor's
bare id (`gpt-5.4-mini`); a local server takes the name it serves the model
under (`llama3.2`).

## Where the key comes from

The provider package reads its key, not the runner. Every AI SDK provider does
the same two things: it accepts `apiKey` at construction, and when none is
passed it reads its own environment variable on the first request. So these
are equivalent for OpenRouter:

```ts
import { createOpenRouter, openrouter } from '@openrouter/ai-sdk-provider';

// Reads OPENROUTER_API_KEY when the first model call is made.
openrouter('openai/gpt-5.4-mini');

// The same, with the key named in the config. Any variable, any source.
createOpenRouter({ apiKey: process.env.MY_TEAM_MODEL_KEY }).chat('openai/gpt-5.4-mini');
```

Three consequences worth knowing:

- **The key is read late.** Constructing `gateway('...')` in a config does not
  need the variable to be set. Deterministic suites, `e2e run --list`, and
  config loading all work without a key; only the first `agent.*` step asks the
  provider for one.
- **There is no `E2E_*` key variable.** The runner never sees the key, so it has
  nothing to name it. One variable for "all providers" would also need the
  runner to know which provider it is forwarding to, and could not serve a
  config that uses two providers. Set the variable the package you imported
  documents, the same one its dashboard and the AI SDK docs name.
- **The runner never logs it.** The key lives in your config module and the
  provider's request headers. It does not enter the report, the trace, the
  AI trace, or the environment of the app process the runner starts.

## Several models in one config

Each model slot is its own instance, so they can come from different packages:

```ts title="e2e.config.ts"
import { createAgent } from '@e2edev/e2e/agent';
import { openai } from '@ai-sdk/openai';
import { gateway } from 'ai';

export default {
  agents: {
    default: {
      executor: createAgent({ system: 'You are a thorough QA agent.' }),
      model: gateway('openai/gpt-5.4-mini'),
      // Pixels go to a model that grounds well, called directly.
      visionModel: openai('gpt-5.4'),
    },
    careful: { model: gateway('anthropic/claude-opus-5'), context: 'Read every label twice.' },
  },
} satisfies E2EConfig;
```

Both keys must be set for that config: `AI_GATEWAY_API_KEY` for the two
gateway models and `OPENAI_API_KEY` for the vision one. Two agents that hold
the same instance share one adapter; two instances of the same id are two
models as far as the runner can tell.

## In CI

The secret is named after the variable the provider reads, and the job passes
it through `env`. Nothing else is needed:

```yaml
      - run: npx --no-install e2e run --config e2e.agent.config.ts
        env:
          AI_GATEWAY_API_KEY: ${{ secrets.AI_GATEWAY_API_KEY }}
```

To switch models per run without editing the config, read a variable of your
own in the config and keep it in a non-secret CI variable:

```ts
model: gateway(process.env.MODEL ?? 'openai/gpt-5.4-mini'),
```

## What fails, and where

| Symptom | Code | Cause |
| --- | --- | --- |
| The run stops before any test with exit 2 and names `agents.default.model` | `INVALID_CONFIG` | A string in a model slot (`model: 'openai/gpt-5.4-mini'`). Write the constructor: `gateway('openai/gpt-5.4-mini')`. |
| The run stops when the first test asks for `agent`, exit 2 | `MODEL_UNAVAILABLE` | No model anywhere: neither `createAgent({ model })` nor `agent.model` holds an instance. |
| The first agent step fails with an authentication message | `MODEL_PROVIDER_FAILED` | The provider rejected or could not find its key. The message names the variable the package reads. |
| The first agent step fails with `ai` not found | `MODEL_UNAVAILABLE` | `ai` is an optional peer dependency; `npm i -D ai`. |

A missing model is checked once per run, so a suite without one reports one
run-level error rather than one blocked step per test. A missing key is not
checked ahead of time: the runner does not know which variable to look for,
so the provider reports it on the first call.
