title: Caching
description: Replay verified agent actions without model calls, and let the agent take over when the app changes.

The replay cache records the actions of an `agent.act()` step after a later
check verifies the result. On the next run, the runner replays those
actions without a model call. When a control or the expected end state no
longer matches, the agent takes over from the current screen.

`agent.assert`, `agent.waitFor`, and `agent.extract` always run live. The
run summary counts the outcomes:

```text
           AI  4.1k tokens · 2 model calls · anthropic/claude-sonnet-4.5
        Cache  4 replayed · 1 handed off · 1 missed
```

## When a recording is written

Follow each `act` with a check of its outcome. In `read-write` mode, the
runner saves the recording at the end of the attempt when a later
verification step passed.

```ts title="tests/cart.e2e.ts"
import { expect, test } from 'e2e';

test('adds an item', async ({ app, agent, screen }) => {
  await app.open('/cart');
  await agent.act('add one item to the cart');
  await expect(screen.getByRole('status')).toHaveText('1 item');
});
```

| Counts as verification | Does not count |
| --- | --- |
| `expect(locator).toHaveText(...)` and other locator matchers | `expect(value).toBe(...)` on a plain value |
| `expect(browser).toHaveURL(...)` and other engine assertions | `expect.poll(...)` |
| `locator.waitFor()`, `browser.waitForURL()` | `locator.textContent()` and other reads |
| `agent.assert(...)`, `agent.waitFor(...)` | `agent.extract(...)`, another `act`, the attempt passing |

`step.cache.write`, in the report only, says what happened to the recording
when the attempt ended:

| `step.cache.write` | Meaning |
| --- | --- |
| `saved` | Recorded for the next run. |
| `kept` | The entry stays as it is. |
| `unconfirmed` | Not saved: no check passed after the step. Follow it with a locator assertion or `agent.assert`. |
| `evicted` | The entry was deleted: its replay ended in a failure or a repair, or no check confirmed it before the attempt failed. |
| `no-change` | Nothing recorded: no control appeared, went away, or changed state, and the route stayed the same. A step that took no action records nothing either. |
| `not-written` | Not saved: the store didn't write the recording, for example one over the file store's size limit. |

A failing attempt still saves the steps verified before the failure. It
deletes unverified entries and the replays involved in the failure. A custom store needs a `delete` method for this. Cancelling
a run leaves the cache unchanged.

<Accordion title="Failures where no model answered">
An attempt whose only failures are ones where no model answered evicts
nothing, since these say nothing about the app:

- `MODEL_UNAVAILABLE`: no model is configured.
- `MODEL_PROVIDER_FAILED`: the provider returned an error, such as a
  missing or rejected key, a rate limit, or a 5xx, or a request got no
  response within 120 seconds.

So a `read-write` run without model access keeps its recordings, including
a step that replayed before an `agent.assert` that could not reach its
model.

These count as a failure of the flow: an unusable model answer
(`MODEL_OUTPUT_INVALID`, `CONTEXT_OVERFLOW`), `STEP_TIMEOUT` (even with a
request still open), and any other failure in the same attempt, such as an
`afterEach` assertion.
</Accordion>

## What must match

A cache entry belongs to one test, target, instruction, set of params, and
agent. Each of these changes causes a miss:

- renaming the test or the target,
- changing the instruction or an ordinary param,
- running with another configured agent (`agent: ['buyer', 'admin']`
  records one entry each), or changing the agent's `context` or the test's
  `agentContext` (a secret in it enters the key as its name only),
- switching to another engine, or changing the project id or the app's
  identity.

Changing the model doesn't cause a miss, and neither does upgrading the
engine: a node the new version resolves differently misses at replay.

A timestamp or a fresh email address would miss on every run. Wrap such
values in `unique()`, and the runner puts in the current value at replay:

```ts
import { unique } from 'e2e';

const name = `E2E ${Date.now()} Company`;
await agent.act('create a company named {name}', { params: { name: unique(name) } });
await expect(screen.getByRole('heading', { name })).toBeVisible();
```

Use `unique()` for data the flow enters or checks, and ordinary params for
choices that change the flow, such as a plan name. The substitution also
covers the value as a URL spells it (`%20`, `+`). When a `unique()` value
equals or sits inside another param's value, the step isn't recorded:
`step.cache.notRecorded` reads `param-collision`, and the next run records
it.

For preview URLs that change on each deploy, set
[`app.identity`](/reference/config#the-app-under-test) to keep one cache
identity. On devices, replay uses the
[screen title](/reference/mobile#replay-cache-on-a-device) as the path.

## How a replay works

1. Check the starting screen: it must be the same route.
2. Find each recorded control by role, name, test id, and surrounding
   context, and repeat its action. The runner waits for missing controls and
   stops when a match is ambiguous.
3. Check the final route and what the original step changed: the controls
   that appeared, with their checked, selected, expanded, or pressed state,
   and the ones that went away.
4. Finish without a model call, or let the agent continue with a record of
   what ran and why replay stopped.

Typed values replay as recorded. A secret fill resolves the current value
by name and goes through authorization again.

<Accordion title="What counts as the same route">
A route is the origin, the path, and the query. The record id and the
fragment don't count. Ids, tokens, timestamps, and cache busters in the
path or the query read as an id placeholder, so `/orders/42?t=1727780000`
and `/orders/7?t=1727780999` are one route.

Every other query value is part of the route: `?mode=safe` and
`?mode=unsafe` differ, and so do `/companies` and `/companies?tab=notes`, or
a new tracking parameter. `/products/summer-sneaker` and
`/products/winter-boot` are different routes too.

A location on the app's own origin is compared by its path, so a recording
follows the app to a preview deployment that shares its `app.identity`. A
page on any other origin is another route.
</Accordion>

<Accordion title="How the end check reads the screen">
- At least one recorded change must happen during the replay. An outcome
  already on screen before the actions proves nothing. When the step's last
  action moved to another route, that move is the evidence.
- An alert that the replay raised and the recording never saw stops the
  replay.
- Text that differs on every run, such as a date, a duration, or an id,
  isn't used. In an alert, it reads as a placeholder.
- A count that names what it counts, such as `3 records imported`, must read
  the same on replay when the step made it appear on the screen it acted
  on. A count that only moved (`41 items` to `42 items`), one on a screen the
  step navigated to, and a bare number such as a badge are never used.
- A control with no name is found by its place among the unnamed controls
  of its kind inside the same named row, list item, or group.
</Accordion>

## Why a step was not replayed

Each `act` step reports `step.cache`, absent when caching is off for the
step. `agent.act()` returns it as `result.cache`, without `write`, and the
[trace page](/debugging#traces) shows it under the step.

| Run summary | `step.cache.mode` | Meaning |
| --- | --- | --- |
| `replayed` | `self-finalized` | The recording completed without a model call. |
| `handed off` | `agent-concluded` | Replay started, then the agent took over. |
| `missed` | `missed` | The agent ran the step from the beginning. |

Both carry `step.cache.reason`, and `step.cache.detail` says where the
replay stopped and why (`at action 2 of 3, tap button "Apply": ...`).
`step.cache.entry` is the entry's key and its file name (`<entry>.json`) in
the file store.

| Reason | What happened | What to do |
| --- | --- | --- |
| `no-entry` | No recording matches this step and its params. | The next verified pass records it. |
| `retry` | Retries never replay, except under `--strict-cache` or `cache.strict`. | Nothing. |
| `invalid-entry` | The file is unreadable, over 1 MiB, or from another schema version. | `npx e2e cache clear`. |
| `truncated` | The recording hit a limit, see [below](#limits-and-gaps). | Split the step, or pass the secret as a `Secret`. |
| `wrong-context` | The app was on another route than when the step was recorded. See [How a replay works](#how-a-replay-works). | Open the same screen before the step. |
| `target-not-found` | A recorded control did not appear within 15 seconds, or it has no name and no named container to tell it from its twins. | The UI changed: the next passing run records it again. For an unnamed control, give it a label or put it in a named row or group. |
| `target-ambiguous` | The number of matching controls changed. | Give repeated controls distinct names or use unique test data. |
| `gap` | An action can't be replayed, see [below](#limits-and-gaps). | The agent does this part live. Put stable values in `params`. |
| `action-failed` | The app rejected a replayed action. | Check the app. |
| `action-uncertain` | A replayed action failed, and it's unknown whether it took effect. The agent is told to check before it acts again. | Check the app. |
| `viewport-changed` | A bare-point tap or hover was recorded on a viewport of another size. | Keep the viewport fixed. |
| `end-mismatch` | Every action ran, but the [end check](#how-a-replay-works) failed. | Leftover data from an earlier run, a banner that comes and goes, or a regression. Unique test data and cleanup in `afterEach` help. |

To rule the cache out of a failure, run one time without it:

<CodeGroup>
```bash npm
npx e2e run --no-cache
```

```bash pnpm
pnpm exec e2e run --no-cache
```

```bash bun
bunx e2e run --no-cache
```
</CodeGroup>

### Limits and gaps

A recording is `truncated` when the step:

- took more than 50 actions, which is possible only with `maxSteps` above 50,
- typed a value or URL over 4,096 characters, or one that holds a
  registered secret,
- acted on a control with no usable description.

A `gap` is an action the cache can't repeat: a mutating
[project tool](/tools), or a value the agent read off the screen, typed
after it saw a screenshot, or worked out from the date. `step.cache.derived`
names the rule: `whole-node` (a control's whole name or text),
`minted-token` (a code or id the app showed as its own word), `date`, or
`pixels`. Values from the instruction or `params`, and values the agent
composed itself, replay.

## What a recording holds

Each entry is a JSON file under `.e2e/cache/`, named by a hash of its key.
It holds actions, target descriptions, typed text, a step summary, and the
end checks: the route and up to eight controls that appeared and eight that
went away. Entries hold no prompts, conversations, screenshots, observed
trees, or secret values. A secret fill stores only the secret's name.

<Warning>
Other typed values are stored as typed. Review recordings before you share
them. See [cache trust](/reference/security#cache-trust).
</Warning>

## Modes

| Mode | Replays | Records | Default |
| --- | --- | --- | --- |
| `'read-write'` | yes | yes | locally |
| `'read-only'` | yes | no | in CI when `cache` is unset |
| `'off'` | no | no | `--no-cache` for one run |

```ts title="e2e.config.ts fragment"
cache: 'off',
// or
cache: { mode: 'read-write', dir: '.e2e/cache' },
```

`--no-cache` overrides the config. In `read-only` mode, stale entries stay
until a `read-write` run replaces them. A custom `cache.store` replaces the
file store and doesn't default to `read-only` in CI. `e2e explore` and
`e2e mcp` don't use the cache.

## Commit the replay cache

<span id="commit-your-traces" />

`e2e init` adds `.e2e/cache/` to `.gitignore`, so each machine records its
own and CI starts with none. To share replays, remove that line and commit
the directory. CI stays `read-only` unless you set `cache: 'read-write'`.
Treat committed entries as test data, and review them in the pull request
that recorded them again.

Local runs leave a committed directory clean unless something changed. A
replayed step never rewrites its entry, and a live recording with the same
actions, paths, and anchors isn't written. So an entry for a UI that drifts
is repaired only when a control can no longer be found. A file changes when:

- a step records for the first time, or after a hand-off,
- a step fails after a replay, ends in an `end-mismatch` the agent had to
  repair, passes with nothing to record, or isn't confirmed by the end of the attempt, which deletes the
  entry,
- an `e2e` upgrade changes how entries are matched, which gives every entry
  a new key, so the next run records them again.

## Fail on a stale recording

By default, a committed recording that stops replaying fails nothing: the
agent takes the step over, and every CI run pays for model calls until
someone records it again. With `--strict-cache` (or
`cache: { strict: true }`), the step fails with `REPLAY_STALE` and makes no
model call:

<CodeGroup>
```bash npm
CI=1 npx e2e run --strict-cache
```

```bash pnpm
CI=1 pnpm exec e2e run --strict-cache
```

```bash bun
CI=1 bunx e2e run --strict-cache
```
</CodeGroup>

`REPLAY_STALE` exits 2 and is not retried.

| Fails under strict | Still runs live |
| --- | --- |
| `invalid-entry`, `wrong-context`, `target-not-found`, `target-ambiguous`, `viewport-changed`, `action-failed`, `action-uncertain`, `end-mismatch`: the app or the entry changed | A step never recorded (a new or edited instruction or params) |
| `no-entry`, when the cache directory holds a recording of the same step under another key | A `gap` or a `truncated` recording |
| | A step whose store read fails |

A recording under another key comes from an `e2e` upgrade that changed the
keys, or a change to the project id, the app's identity, or the agent's
context. The message names that file and, for a recording made by a
current version, what changed. Delete the file when nothing replays it. This check doesn't cover a
custom `cache.store`.

A strict run never writes or deletes an entry, even in `read-write` mode, so
a new step records only on a run without strict. Prefer `--strict-cache` in
CI over `cache.strict` in the config. To fix a stale entry:

1. Run the test in `read-write` mode without the flag. Turn `cache.strict`
   off if the config sets it.
2. Commit the changed entry. A custom `cache.store` gets the new entry from
   that run instead.

## Inspect the cache

<CodeGroup>
```bash npm
npx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
npx e2e cache stats   # entry count and size
npx e2e cache clear   # delete every entry
```

```bash pnpm
pnpm exec e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
pnpm exec e2e cache stats   # entry count and size
pnpm exec e2e cache clear   # delete every entry
```

```bash bun
bunx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
bunx e2e cache stats   # entry count and size
bunx e2e cache clear   # delete every entry
```
</CodeGroup>

<Note>
The `cached` percentage in AI usage is the provider's prompt cache. It
lowers the cost of a model call. The replay cache skips the call.
</Note>
