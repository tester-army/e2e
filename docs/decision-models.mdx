description: Run bounded actions with a decision model and a small text model instead of a full LLM agent.

`@e2e-dev/decision` runs `agent.act` and `agent.assert` through a decision
model instead of an LLM. For each action the decision model answers two
requests: which operation, then which element for it when the operation has
more than one, chosen from what the executor builds out of the latest
semantic tree. Every question states the goal and the recent actions in its
own text, with the page as evidence. It never generates free text: when the
choice is `type`, a small language model writes the field value. Both models are
plain AI SDK models, so any decision model provider that answers `choice`
questions with probability distributions (TypeSafe Jev, OpenAI `gpt-6-luna`)
and any language-model provider works; the runner still authorizes every
dispatched action.

## Install and configure

<CodeGroup>
```bash npm
npm install -D @e2e-dev/decision
```

```bash pnpm
pnpm add -D @e2e-dev/decision
```

```bash bun
bun add -d @e2e-dev/decision
```
</CodeGroup>

The decision model answers `choice` questions with probability
distributions; the text model writes field values. Each installs as its
own package. Decision models need `ai` 7, version 7.0.128 or later:

<CodeGroup>
```bash npm
npm install -D @ai-sdk/typesafe-ai @openrouter/ai-sdk-provider
```

```bash pnpm
pnpm add -D @ai-sdk/typesafe-ai @openrouter/ai-sdk-provider
```

```bash bun
bun add -d @ai-sdk/typesafe-ai @openrouter/ai-sdk-provider
```
</CodeGroup>

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { decisionExecutor } from '@e2e-dev/decision';
import { typeSafeAi } from '@ai-sdk/typesafe-ai';
import { openrouter } from '@openrouter/ai-sdk-provider';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  agents: {
    default: {
      executor: decisionExecutor({
        model: typeSafeAi.decisionModel('jev-latest'),
        textModel: openrouter('inception/mercury-2.5'),
      }),
    },
  },
} satisfies E2EConfig;
```

OpenAI's Decisions API works the same way. `openaiDecisionModel()` from this
package talks to it directly, reads `OPENAI_API_KEY`, and also takes the
screenshot that `vision` sends; `openai.decisionModel('gpt-6-luna')` from
`@ai-sdk/openai` 4.0.86 or later works too, text only:

<CodeGroup>
```bash npm
npm install -D @ai-sdk/openai
```

```bash pnpm
pnpm add -D @ai-sdk/openai
```

```bash bun
bun add -d @ai-sdk/openai
```
</CodeGroup>

```ts title="e2e.config.ts"
import { openaiDecisionModel } from '@e2e-dev/decision';
import { openai } from '@ai-sdk/openai';

const executor = decisionExecutor({
  model: openaiDecisionModel(),
  textModel: openai('gpt-5.4-mini'),
  vision: true,
});
```

`evaluationModel()` instances still work. A model id string or a language
model in `model` fails config load with `INVALID_CONFIG`.

Tests stay plain natural language, with no params needed:

```ts title="tests/todos.e2e.ts"
import { test, expect } from 'e2e';

test('adds a todo', async ({ app, screen, agent }) => {
  await app.open('/todos');
  await agent.act('Add a todo named Buy coffee, and verify it is listed.');
  await expect(screen.getByTestId('todo')).toContainText('Buy coffee');
  await agent.assert('The todo list contains Buy coffee.');
});
```

## What the model can do

Each turn offers the operations the engine declares on the elements of the
newest screen: `tap`, `type`, `typeSecret`, `submit`, `select`, `check`,
`upload`, `hover`, `secondary_tap` (a right-click), `double_tap`,
`long_press`, `drag` with a separate destination question, `scroll_to` for
an element outside the viewport, plus `scroll_up`, `scroll_down`, and
`back`. Hover, right-click, drag, and scroll-to also reach labeled nodes
that are no control: a card that opens a menu on hover, a file row, a
paragraph. Every target question carries a `none` option, so a provider
that finds no target for an operation the step will not take answers
`none` instead of refusing; `none` for the operation the model did choose
blocks the step.

## Vision

`vision: true` asks the engine for masked pixels on every observation.
Assertions and completion checks see the screenshot beside the page, so
the model judges drawn content a tree cannot show; the operation and
target questions read the tree alone, where a screenshot was measured to
hurt. It also offers `tap_at` for a control the tree does not list: the
text model names the control to tap next from the goal and the taps so
far ("the 3 key on the keypad"), and the decision model locates it with two
pairs of score questions, column and row on the full screenshot, then
again on a zoomed crop with a grid drawn on it. A tap that changed the
page is remembered for its control, so the same key again needs no new
looks. `agent.assert(..., { vision: true })` and `vision: 'only'` reach the
executor the same way. The model must take images and answer score
questions: `openaiDecisionModel()` does, the AI SDK's `openai.decisionModel()`
sends text only. Pixels are withheld once a secret has been filled in the
attempt, as everywhere in the runner.

Measured on gpt-6-luna over the playground: a vision assert on a drawn
chart, a drawn map pin, and a five-digit code on a drawn keypad pass; a
ten-digit code mislocated one key. Each point tap costs four model calls
plus the text model's one.

## How text gets typed

The decision model only ever names an element index. When it picks `type`,
the text model writes the value from the goal, the field's label, and the
page text, and the executor types exactly that string. When it picks
`upload`, the text model lists the project-relative paths the goal or params
name, and the runner authorizes each path before the engine sees it. Model output never
becomes a selector, a URL, or a key. When the goal supplies no value,
nothing is typed and the decision model picks another action. Password
fields never reach the text model; secrets stay declared handles that only
`typeSecret` fills.

The text model is also the agent's judgment tier: it is exposed as the
executor's `model`, so `waitFor` and `extract` use it too. It can come
from the agents entry's `model` instead. Without either, `type` is never
offered.

## Finishing a step

When the decision model answers `done` or `failed`, the executor checks
the claim on a fresh screen with one question: is the step's task complete?
It sees the step's non-secret params, the actions taken with the non-secret
values typed, and the page, including the text of named status regions, but
no model reasoning or secret. A confirmed `done` passes the
step and a confirmed `failed` fails it with `ACTION_FAILED`. An
unconfirmed claim goes back to the decision model as history; the second one
ends the step, as `ACTION_FAILED` when the screen contradicts the goal and
as `blocked` (`AUTOMATION_UNSUPPORTED`) otherwise.

## Gates

Both gates are off by default: the executor follows the most probable
choice. Set `minProbability` or `minConfidence` to block weaker actions,
reject weaker completion checks, and fail weaker assertions as
inconclusive instead:

```ts title="Executor setup"
const executor = decisionExecutor({ model, minProbability: 0.9, minConfidence: 0.8 });
```

Probability and confidence are different provider fields: probability is the
selected option's share of the answer distribution, confidence is the
provider's separate statistic. A threshold is a policy choice; measure
accuracy on your own tests before changing it. Providers round: OpenAI
reports both to two decimals, so a gate between two hundredths acts as the
next hundredth.

## Provider options

`providerOptions` go with every decide call, the completion checks
included. Use them for options of the decision model's provider, such as
zero data retention on Vercel AI Gateway:

```ts title="Executor setup"
import { gateway } from 'ai';

const executor = decisionExecutor({
  model: gateway.decisionModel('typesafe-ai/jev'),
  textModel: gateway('openai/gpt-4.1-nano'),
  providerOptions: { gateway: { zeroDataRetention: true } },
});
```

They reach the decision model only. The text model takes the agents
entry's `providerOptions`, so a gateway setting meant for one model, such as
a fallback list, never reaches the other.

## Limits

- No `navigate`: in-app navigation is a `tap` on a link. URLs belong in
  test code (`browser.goto`, `app.open`).
- No multi-select `listbox`, no `scrollUntil`, no keyboard typing at a
  point (`type_at`).
- The text model that names a drawn control reads the page text and the
  goal, not the pixels: an instruction that exists only as drawn text (a
  wizard that paints "tap the circle") is out of its reach.
- A question the provider refuses to answer fails the step with
  `MODEL_OUTPUT_INVALID`.
- The choice cap is 255 options per question (TypeSafe's limit; OpenAI
  documents none). Larger
  screens list viewport nodes first and count the rest as omitted, so the
  model can scroll; the step never blocks just for being large.
- `waitFor` and `extract` use the text model through the runner's
  built-in judgment tier.
