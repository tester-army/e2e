title: Testing iOS and Android
description: Set up a simulator or emulator target, write a device test, and know what differs from the web.
---

`@e2e-dev/mobile` runs tests on iOS simulators and Android emulators.
Tests use the same `agent`, `screen`, and `expect` APIs as browser tests.
A test launches the configured app with `app.open()`, as a Maestro flow does
with `launchApp`; between tests the app stays where the last one left it.

## Set up

Install Xcode with an iOS simulator runtime, or the Android SDK with an
emulator. Check your setup with:

```bash
npx agent-device doctor
```

Follow the [Quickstart](/quickstart) and choose **Mobile (iOS/Android)**.
The wizard selects iOS on macOS and Android elsewhere. It starts with the
Settings app and one worker:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

export default {
  // Replace Settings with your app's bundle id.
  targets: [{ name: 'ios', engine: mobile({ platform: 'ios', app: 'Settings' }) }],
  workers: 1,
} satisfies E2EConfig;
```

The runner boots the device before test timing starts. Boot time does not
count toward `launchTimeout`.

## Point at your app

Replace `Settings` with your app's bundle id or package name. Setting `app`
gives `app.open()` an app to launch and enables `app.restart()` and
`app.clearState()`. Add `appPath` to install a build first:

```ts
mobile({
  platform: 'ios',
  app: 'com.example.app',
  appPath: process.env.E2E_APP_PATH, // path to the iOS .app bundle
})
```

The engine installs nothing on its own: `appPath` names the build, and the
suite installs it where it says so, once per device, with `device.installApp()`
(no path installs `appPath`), for example in a fixture every test takes. Use an `.app` bundle for iOS or an
`.apk` for Android. Optional values accept `undefined`, so environment
variables can be passed directly.

Without `app`, the engine observes whichever app is in the foreground and
`app.open()` has nothing to launch. Set it when possible so tests start
consistently and cached steps can replay.

### Launch arguments and permissions

`launchArguments` reach the app on every fresh launch the engine performs
(`app.open()`, `app.restart()`, `app.clearState()`): the process arguments on
iOS, `am start` arguments on Android. `permissions` are set before each of
those launches, so the app starts holding them and no system prompt appears;
`app.clearState()` puts them back after it reset them with the data. `deny`
differs by platform: iOS records the refusal and the app is told no without
a prompt, Android revokes the permission and the OS asks again when the app
requests it. The warm-up in `prepare` opens the app once with neither, to
bring the runner up and put the worker's session on the app; the process a
test sees comes from `app.open()`. Arguments that select a build mode change
what the app is: give each mode its own `identity` so their recordings stay
apart.

```ts
mobile({
  platform: 'ios',
  app: 'com.example.app',
  launchArguments: ['-e2e', 'YES'],
  permissions: { camera: 'grant', notifications: 'deny', location: 'reset' },
})
```

One test launches with its own through `device.openApp`:

```ts
await device.openApp('com.example.app', { relaunch: true, permissions: { camera: 'deny' } });
```

## Several devices

Add a target for each platform:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

const iphone = mobile({ platform: 'ios', app: 'com.example.app' });
const pixel = mobile({ platform: 'android', app: 'com.example.app' });

export default {
  targets: [
    { name: 'iphone', engine: iphone },
    { name: 'pixel', engine: pixel },
  ],
  workers: 1,
} satisfies E2EConfig;
```

Tests run on both targets. Use `platforms: ['ios']` or
`platforms: ['android']` for tests with platform-specific labels or behavior.

To run files in parallel, provide a device pool and set `workers` to at
least the pool's size. Each device gets one worker:

```ts
mobile({ platform: 'ios', app: 'com.example.app', device: ['iPhone 17', 'iPhone 17 Pro'] })
```

Without `device`, the engine uses booted devices up to the worker limit.
If none are booted, it boots one. Two workers never drive the same device.

## Hosted devices

A `device` can also be a `DeviceProvider`: an object that leases one hosted
device per worker slot when the run starts and releases it when the run
ends. The engine drives each lease through the agent-device daemon the lease
names instead of the local one, so any service that runs an agent-device
daemon next to a simulator, an emulator, or a physical device works. Nothing
in the framework knows a vendor; a provider is a few dozen lines in your
project.

```ts
export interface DeviceProvider {
  /** Label in progress lines and error messages. */
  readonly name: string;
  /** Called once per worker slot, for every slot at once, in the runner process. */
  acquire(request: DeviceRequest): Promise<DeviceLease>;
  /** Called once per lease when the run ends, on every exit path. */
  release(lease: DeviceLease, context: DeviceReleaseContext): Promise<void>;
}

export interface DeviceLease {
  /** The provider's handle (a session id), handed back to `release`. */
  readonly id: string;
  /** The agent-device daemon the worker connects to; a lease names this, `client`, or both. */
  readonly daemon?: { readonly baseUrl: string; readonly authToken?: string };
  /** agent-device client configuration the worker's client is created with: a lease scope, a `stateDir`. */
  readonly client?: DeviceClientConfig;
  /** Device to select inside that daemon, when it hosts more than one. */
  readonly device?: string;
  /** Bundle id or package the provider installed itself; skips `appPath`. */
  readonly installedApp?: string;
}
```

`acquire` receives the platform, run id, target, slot, the `app` and resolved
`appPath` options, the run's environment, an interrupt signal, and a `log`
that reaches the reporter. Read tokens from `request.env`, not
`process.env`. A target with nothing to run leases nothing. Every lease
granted is held by the engine, one it then refuses included: a slot that
fails to lease ends the run before any test, and the leases that succeeded
are still released. Release happens after the last worker exits, on every
exit path including failure, interrupt, and a `prepare` that threw, within
`cleanupTimeout`. `release` receives the object `acquire` returned, so a
provider can keep its own fields on it; only `daemon`, `client`, `device`,
and `installedApp` travel to the workers. Report `installedApp` only for a
request that carried `appPath`.
Leased devices are warmed like local ones: booted and opened once before
the run's clock starts.

`client` is agent-device client configuration, JSON data the worker's client
is created with on top of the session name and the `daemon` address (the
engine owns `session`, `daemonBaseUrl`, `daemonAuthToken`, and
`daemonTransport`, and refuses a lease that sets them). It is how a device reached through agent-device's own
device-cloud runtimes is told apart: the daemon resolves a hosted device from
the lease scope on each command (`tenant`, `runId`, `leaseId`, `leaseBackend`,
`leaseProvider`, as `leases.allocate` returned it), and a command without one
falls back to the local inventory. A `stateDir` in it points the worker at a
daemon the provider started, so such a provider needs no `daemon` address at
all.

A provider against a typical session API has three requests: create a
session, poll it until the daemon is reachable, stop it.

```ts title="device-provider.ts"
import type { DeviceProvider } from '@e2e-dev/mobile';

/**
 * Leases devices from a service that starts an agent-device daemon per
 * session. Replace the three requests with your service's API.
 */
export function hostedDevices(options: { serviceUrl: string; image: string }): DeviceProvider {
  return {
    name: 'hosted-devices',
    async acquire(request) {
      const token = request.env['DEVICE_SERVICE_TOKEN'];
      if (token === undefined || token === '') throw new Error('DEVICE_SERVICE_TOKEN is not set');
      const headers = { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' };
      // 1. Ask for a device; name the session after the run so it can be found later.
      const created = await fetch(`${options.serviceUrl}/sessions`, {
        method: 'POST',
        headers,
        body: JSON.stringify({
          platform: request.platform,
          image: options.image,
          name: `e2e ${request.runId} ${request.targetName} ${request.slot + 1}/${request.slots}`,
        }),
        signal: request.signal,
      });
      if (!created.ok) throw new Error(`device service: HTTP ${created.status}`);
      const { id } = (await created.json()) as { id: string };
      // 2. Wait until the session exposes its agent-device daemon.
      for (;;) {
        const response = await fetch(`${options.serviceUrl}/sessions/${id}`, { headers, signal: request.signal });
        const session = (await response.json()) as { status: string; daemonUrl?: string; daemonToken?: string; viewerUrl?: string };
        if (session.status === 'ready' && session.daemonUrl !== undefined) {
          if (session.viewerUrl !== undefined) request.log(`watch at ${session.viewerUrl}`);
          return { id, daemon: { baseUrl: session.daemonUrl, authToken: session.daemonToken } };
        }
        if (session.status !== 'starting') throw new Error(`device service: session ${id} is ${session.status}`);
        await new Promise((resolve) => setTimeout(resolve, 5_000));
      }
    },
    async release(lease, context) {
      // 3. Stop the session; the run waits for this within cleanupTimeout.
      const token = context.env['DEVICE_SERVICE_TOKEN'] ?? '';
      await fetch(`${options.serviceUrl}/sessions/${lease.id}/stop`, {
        method: 'POST',
        headers: { Authorization: `Bearer ${token}` },
        signal: context.signal,
      });
    },
  };
}
```

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';
import { hostedDevices } from './device-provider.ts';

export default {
  targets: [
    {
      name: 'ios',
      engine: mobile({
        platform: 'ios',
        app: 'com.example.app',
        device: hostedDevices({ serviceUrl: 'https://devices.example.com', image: 'ios-18-iphone-17' }),
      }),
    },
  ],
  workers: 2,
} satisfies E2EConfig;
```

Two workers lease two sessions in parallel. Hosted sessions are billed while
they run, so keep `workers` at what the suite can fill. The trace cache keys
on `app`, so traces recorded locally replay on hosted devices.

A device cloud agent-device speaks to itself needs no session API of your
own: the provider allocates a lease through a daemon it starts for the run and
hands the worker the lease scope as `client`.

```ts title="device-cloud-provider.ts"
import { createAgentDeviceClient } from 'agent-device';
import type { DeviceProvider } from '@e2e-dev/mobile';

/**
 * Leases devices from a device cloud agent-device itself speaks to, through
 * a daemon started for the run. The daemon's runtime for the cloud creates
 * the instance when the lease is allocated and deletes it when the lease is
 * released; the worker's client carries the lease, so every command lands on
 * that instance. `provider` is agent-device's name for the cloud; its runtime
 * reads the credentials from the environment the daemon starts with.
 */
export function cloudDevices(options: { provider: string; stateDir: string }): DeviceProvider {
  const scopes = new Map<string, { tenant: string; runId: string; leaseId: string; leaseBackend: 'ios-instance' | 'android-instance'; leaseProvider: string }>();
  return {
    name: options.provider,
    async acquire(request) {
      // One daemon per run, under a directory of its own.
      const stateDir = `${options.stateDir}/${request.runId}`;
      const client = createAgentDeviceClient({ stateDir, session: `lease-${request.slot}` });
      const leaseBackend = request.platform === 'ios' ? ('ios-instance' as const) : ('android-instance' as const);
      const lease = await client.leases.allocate({
        tenant: options.provider,
        runId: request.runId,
        leaseBackend,
        leaseProvider: options.provider,
        platform: request.platform,
        target: 'mobile',
      });
      request.log(`leased ${lease.leaseId}`);
      const scope = { tenant: lease.tenantId, runId: lease.runId, leaseId: lease.leaseId, leaseBackend, leaseProvider: options.provider };
      scopes.set(lease.leaseId, scope);
      // The worker's client is created with these fields; the daemon resolves the device from them.
      return { id: lease.leaseId, client: { stateDir, ...scope } };
    },
    async release(lease) {
      const scope = scopes.get(lease.id);
      if (scope === undefined) return;
      const client = createAgentDeviceClient({ stateDir: `${options.stateDir}/${scope.runId}`, session: 'release' });
      await client.leases.release(scope);
    },
  };
}
```

## Writing a device test

`screen` maps native controls to common roles such as `button`, `textbox`,
`listitem`, and `switch`. Use `getByTestId` for native element identifiers.

```ts
import { test } from '@e2e-dev/mobile';
import { expect } from 'e2e';

test('shows the version offline in dark mode', async ({ agent, device, screen }) => {
  await device.setAppearance('dark');
  await device.setNetwork('offline');
  await agent.act('go to General, then About');
  await expect(screen.getByRole('button', { name: /^iOS Version/ })).toBeVisible();
  await expect(device.locator('role=NavigationBar id=About')).toBeVisible();
});
```

`selectOption`, `setInputFiles`, `scrollIntoView`, `secondaryTap`, and
`modifiers` on a tap are unsupported on devices. Use taps and swipes to interact with native controls.

### The `device` fixture

Use `device` to manage network state, permissions, appearance, app installs,
and other device settings without a model call. Each call appears as a
`device.<method>` step in the report.

`device.locator('...')` accepts an agent-device selector for controls that
`screen` queries cannot identify:

```ts
await expect(device.locator('role=NavigationBar id=About')).toBeVisible();
await device.locator('id=SW_VERSION_SPECIFIER role=Button').tap();
```

Use `device.installApp` within a test to check upgrades or fresh installs; with no path it installs the engine's `appPath`:

```ts
const { app } = await device.installApp('./build/MyApp.app', { reinstall: true });
await device.openApp(app);
```

`device.openApp` takes a bundle id, package, or display name, never a link.
`device.openLink` opens a deep link or a web link into the pinned app, or
into the `app` named in its options, for magic-link sign-in and deep-link
routes:

```ts
await device.openLink('myapp://orders/42');
await expect(screen.getByText('Order #42')).toBeVisible();
```

`device.clearKeychain()` resets the simulator's keychain, which
`app.clearState()` leaves alone, so a stored session token is gone on the
next launch. iOS only; Android has no keychain to reset.

Every method is in the [mobile engine reference](/reference/mobile#device).

### Agent tools

The agent already has basic actions such as `tap`, `type`, and `scroll`.
Add `mobileTools` for app switching, device gestures, and system alerts:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { createAgent } from 'e2e/agent';
import { mobile } from '@e2e-dev/mobile';
import { mobileTools } from '@e2e-dev/mobile/tools';
import { gateway } from 'ai';

const iphone = mobile({ platform: 'ios', app: 'com.example.app' });
const pixel = mobile({ platform: 'android', app: 'com.example.app' });

export default {
  targets: [
    { name: 'iphone', engine: iphone },
    { name: 'pixel', engine: pixel },
  ],
  workers: 1,
  agents: {
    default: createAgent({
      model: gateway('openai/gpt-6-luna-fast'),
      tools: mobileTools(iphone, pixel),
    }),
  },
} satisfies E2EConfig;
```

Pass each configured device engine to `mobileTools`. Calls go to the
engine running the current attempt. Tools that change device state require
the agent to take over during cache replay; the read-only `screenshot` tool
does not interrupt replay.

## What differs from the web

| On the web | On a device |
| --- | --- |
| `app.open('/path')` and the agent's `navigate` verb | No app URL. `app.open()` launches the pinned `app` fresh, `device.openLink(url)` opens a deep link or web link into it, and there is no `navigate` |
| `test.setup` saves a session, `session:` restores it | Not available. A simulator has no portable session snapshot; sign in per test or seed the app |
| Secret input | `type_secret` and `screen.getByLabel(...).fill(secret)` fill declared secrets into secure fields |
| Playwright trace per attempt | No Playwright trace; screenshots mask secure fields |
| `--video` writes a WebM screencast | `--video` writes an MP4 of the device screen with taps shown |
| The cache anchors on the page path | The cache anchors on the location `<bundle id> / <screen title>`, the title read off the navigation bar |
| `getByPlaceholder`, `getAttribute('placeholder')`, `toHaveAttribute('placeholder', ...)` | Work on Android, where a field's hint is the node's `placeholder` attribute whether or not it is showing. An iOS node carries no placeholder yet (agent-device reports only whether one is showing), so query an iOS field by role and name, test id, or display value. `placeholder` is the only attribute a device node has |
| `getByRole('checkbox')`, `getByRole('radio')`, `check()`, `toBeChecked` on a custom control | Work on both platforms. iOS has no trait for a React Native view with `accessibilityRole="checkbox"` or `"radio"`, so React Native spells the role and state into the accessibility value and the engine reads them back; Android reports the `checked` state of a switch, checkbox, or radio button. `accessibilityRole="tab"` gets neither an iOS trait nor that spelling, so an iOS tab is `other` with a `selected` state: query tabs by test id or label and assert `toBeSelected`. On Android the role description React Native writes makes it a `tab` |
| `filter({ has })`, a query scoped to a container (`getByTestId('row').getByText(...)`) | Match nothing when the container is a plain React Native `View`: iOS reports it as a leaf beside its children, whatever its `testID`. `ScrollView`, `TextInput`, and `Text` hosts do nest, so scope to the screen's `ScrollView` (`device.locator('role=ScrollView')`), or give the children their own test ids |
| `display: none` keeps the element in the DOM, `toBeAttached` sees it | Absent from the tree: `toBeAttached` fails, `toHaveCount(0)` is what a device shows, and `toBeHidden` holds either way |
| `doubleTap()` is one gesture | Two presses, 284 to 285 ms apart on iOS: agent-device's native double tap reaches a React Native `Pressable` as one press, so the engine sends two. A detector with a window of 300 ms or less can read them as two single taps; give a double-tap detector 350 ms or more |
| `toBeFocused` | Never passes on iOS: agent-device reads XCTest's `hasFocus` (the tvOS focus engine), not `hasKeyboardFocus`, so a text field with the keyboard up carries no focused state. Assert on what the app shows for focus, or on the keyboard |
| `device.foregroundApp()` after `device.home()` | On iOS still names the app the session opened: agent-device's `appstate` answers from the session there. `closeApp` terminates the app and ends the session, so the next `openApp` launches it fresh |

## Troubleshooting

A device failure reaches the report with agent-device's own message. Under
the agent, an engine fault with no more specific code reports as
`APP_UNREACHABLE`; on a device, read the message before the code, because
the app is often not the part that failed.

**The iOS automation runner is busy or wedged.** An accessibility capture on
a heavy or animating screen can overrun the runner's watchdog. The runner
keeps finishing that capture after the step gave up on it, and every command
until it drains fails with `RUNNER_BUSY`; one stuck for 120 s becomes
`RUNNER_WEDGED`, and agent-device restarts the runner. A run killed
mid-attempt (Ctrl-C) can hand a draining runner to the next run. The report
reads:

```text
APP_UNREACHABLE: agent.act failed: snapshot failed: the iOS automation runner is still
finishing a command that overran its watchdog (session e2e-ios-0 on iPhone 17 Pro):
The iOS runner is still finishing a previous command that exceeded its execution
watchdog (usually an accessibility capture on a heavy or animating screen). The app
is fine. Wait a few seconds and rerun. If the next run meets it again, stop the
daemon (`npx agent-device daemon stop`) and reboot the simulator
(`xcrun simctl shutdown <udid>`, then `boot`).
```

Do what it says. A runner that is still busy or wedged when `prepare` warms
the device ends the run there, with the same message, instead of opening the
app and failing the first observation; the sessions warm-up opened are
closed when the run ends, so the next run does not resume them by name with
that runner state. The wedge itself is agent-device's:
0.21.4 stops a runner that reports draining work instead of handing it to the
next `open`, so a current engine meets it only after a run that never reached
cleanup.

**A snapshot the runner could not present.** `regular iOS snapshot
presentation requires a valid viewport` is a per-capture check inside the
runner, not a property of the screen; so are the payload checks (`regular iOS
snapshot payload refers to a parent outside the payload`, a malformed graph).
The engine takes the snapshot once more before failing the step, as it does
for a sparse one; a second failure propagates with the same recovery.

**A timeout the device reports.** A simulator boot, the runner connecting, or
an app launch that agent-device times out is an `ENGINE_FAILURE` whose
message and hint are agent-device's (`Retry simulator boot and inspect simctl
bootstatus logs; in CI reduce parallel jobs or use a larger runner`). The
harness's own budgets are the `LAUNCH_TIMEOUT`, `ACTION_FAILED`, and
`STEP_TIMEOUT` codes; a device-side timeout never reports as one of them.

```bash
npx agent-device doctor          # the toolchain, the daemon, the booted devices
npx agent-device daemon stop     # after a wedge: drops every session, the next run starts the daemon
xcrun simctl shutdown <udid> && xcrun simctl boot <udid>
```
