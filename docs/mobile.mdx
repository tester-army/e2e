`@e2e-dev/mobile` runs tests on iOS simulators, Android emulators, and
phones connected to your machine. It is built on
[agent-device](https://github.com/callstack/agent-device). Tests use the
same `agent`, `screen`, and `expect` APIs as browser tests.

## Set up

Install Xcode with an iOS simulator runtime, or the Android SDK with an
emulator. Then check your setup:

<CodeGroup>
```bash npm
npx agent-device doctor
```

```bash pnpm
pnpm exec agent-device doctor
```

```bash bun
bunx agent-device doctor
```
</CodeGroup>

Follow the [Quickstart](/quickstart) and choose **Mobile (iOS/Android)**.
The wizard selects iOS on macOS and Android elsewhere. Its config targets
the Settings app with one worker, so you can run a test before you point it
at your app.

The runner boots the device and starts the iOS automation runner before
test timing starts. Boot time doesn't count toward `launchTimeout`.

For a finished setup, see the [example projects](/example-projects) for Expo,
SwiftUI, Jetpack Compose, Kotlin Multiplatform, and Flutter.

## Point at your app

The app under test is the target's `app`. Set `app.bundleId` to your app's
bundle id or package name. `app.open()`, `app.restart()`, and
`app.clearState()` launch that app. Add `appPath` to name a build:

```ts
{
  name: 'ios',
  engine: mobile({ platform: 'ios' }),
  app: {
    bundleId: 'com.example.app',
    appPath: './build/MyApp.app', // the iOS .app bundle
  },
}
```

A device target needs `bundleId`, `appPath`, or both. Use an `.app` bundle
for iOS or an `.apk` for Android.

The engine installs nothing on its own. Call `device.installApp()` once per
device where the suite needs it, for example in a fixture every test takes.
With no path, it installs `app.appPath`. Without `bundleId`, `app.open()`
launches the app the build installed.

To run the suite in CI, see [Mobile jobs](/ci#mobile-jobs). There are
workflows for [GitHub Actions](/ci/github-actions#ios-and-android),
[EAS Workflows](/ci/eas-workflows), [Bitrise](/ci/bitrise), and
[Codemagic](/ci/codemagic).

### Launch arguments and permissions

`app.launchArguments` and `app.permissions` apply to every fresh launch:
`app.open()`, `app.restart()`, and `app.clearState()`.

```ts
app: {
  bundleId: 'com.example.app',
  launchArguments: ['-e2e', 'YES'],
  permissions: { camera: 'grant', notifications: 'deny', location: 'reset' },
},
```

- Launch arguments are the process arguments on iOS and `am start`
  arguments on Android.
- The runner sets permissions before the launch, so no system prompt
  appears. `app.clearState()` resets them with the data, then sets them
  again.
- `deny` on iOS records a refusal: the app is told no without a prompt.
  `deny` on Android revokes the permission: the OS asks again when the app
  requests it.
- The warm-up before the run passes neither. Start each test with
  `app.open()` to get them.
- Arguments that select a build mode change what the app is. Give each mode
  its own `app.identity` so its recordings stay apart.

To launch one test with its own, use `device.openApp`:

```ts
await device.openApp('com.example.app', { relaunch: true, permissions: { camera: 'deny' } });
```

### Expo development builds

A development build (`expo-dev-client`) opens on the dev launcher and loads
its JavaScript from a dev server. On an iOS simulator, launch arguments open
the server directly. They also turn off the dev menu, its onboarding sheet,
and its floating action button, so nothing covers the app. `app.command`
starts the server for the run:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

export default {
  targets: [
    {
      engine: mobile({ platform: 'ios' }),
      app: {
        bundleId: 'com.example.app',
        launchArguments: [
          '--initialUrl', 'http://localhost:8081',
          '-EXDevMenuShowsAtLaunch', 'NO',
          '-EXDevMenuIsOnboardingFinished', 'YES',
          '-EXDevMenuShowFloatingActionButton', 'NO',
        ],
        command: { executable: 'npx', args: ['expo', 'start', '--port', '8081'] },
        readyUrl: 'http://localhost:8081/status',
      },
    },
  ],
} satisfies E2EConfig;
```

- Start each test with `app.open()`. The warm-up passes no launch
  arguments, so it leaves the app on the dev launcher.
- The first launch waits for the dev server to bundle the app. Give the
  test's first check a longer timeout.
- A test that relaunches with its own `launchArguments` replaces the
  target's, so list these arguments again.
- On Android, expo-dev-launcher doesn't read `--initialUrl`. Open the server
  with `device.openLink` and the build's
  `exp+<slug>://expo-development-client/?url=<encoded server URL>` link.

## Write a device test

`screen` maps native controls to common roles such as `button`, `textbox`,
`listitem`, and `switch`. Use `getByTestId` for native element identifiers.

```ts
import { test } from '@e2e-dev/mobile';
import { expect } from 'e2e';

test('shows the version offline in dark mode', async ({ agent, app, device, screen }) => {
  await device.setAppearance('dark');
  await device.setNetwork('offline');
  await app.open();
  await agent.act('go to General, then About');
  await expect(screen.getByRole('button', /^iOS Version/)).toBeVisible();
  await expect(device.locator('role=NavigationBar id=About')).toBeVisible();
});
```

Between tests, the app stays where the last test left it. Devices don't
support `selectOption`, `setInputFiles`, `scrollIntoView`, `secondaryTap`,
or `modifiers` on `tap` and `doubleTap`. Use taps and swipes on native
controls.

### Test ids by framework

`getByTestId` reads the accessibility identifier on iOS and the resource id
on Android. Each UI framework sets them its own way. Each example project
has the same three locator tests on one greeting screen:

| Framework | Set the id with | Example |
| --- | --- | --- |
| React Native | `testID` | [with-expo](https://github.com/tester-army/e2e/tree/main/examples/with-expo) |
| SwiftUI | `.accessibilityIdentifier()` | [with-swiftui](https://github.com/tester-army/e2e/tree/main/examples/with-swiftui) |
| Jetpack Compose | `Modifier.testTag()` | [with-compose](https://github.com/tester-army/e2e/tree/main/examples/with-compose) |
| Compose Multiplatform | `Modifier.testTag()` | [with-kotlin-multiplatform](https://github.com/tester-army/e2e/tree/main/examples/with-kotlin-multiplatform) |
| Flutter | `Semantics(identifier:)` | [with-flutter](https://github.com/tester-army/e2e/tree/main/examples/with-flutter) |

- On Android, Compose hides test tags until a root composable sets
  `Modifier.semantics { testTagsAsResourceId = true }`. Without it,
  `getByTestId` finds nothing. iOS reads a Compose Multiplatform tag as is,
  so a shared screen sets the flag in its Android activity.
- In Flutter, wrap a button's `Semantics` in `MergeSemantics` so the id and
  the button role land on one node.

## The device fixture

`device` changes device settings without a model call: network,
permissions, appearance, app installs, and more. Each call is a
`device.<method>` step in the report. Every method is in the
[mobile engine reference](/reference/mobile#device).

`device.locator` takes an agent-device selector, for controls that `screen`
queries can't name:

```ts
await expect(device.locator('role=NavigationBar id=About')).toBeVisible();
await device.locator('id=SW_VERSION_SPECIFIER role=Button').tap();
```

`device.installApp` checks upgrades and fresh installs inside a test. With
no path, it installs the target's `app.appPath`:

```ts
const { app } = await device.installApp('./build/MyApp.app', { reinstall: true });
await device.openApp(app);
```

`device.openApp` takes a bundle id, package, or display name, never a link.
`device.openLink` opens a deep link or a web link into the pinned app, or
into the `app` in its options. Use it for magic-link sign-in and deep-link
routes:

```ts
await device.openLink('myapp://orders/42');
await expect(screen.getByText('Order #42')).toBeVisible();
```

`device.clearKeychain()` resets the simulator's keychain, which
`app.clearState()` leaves alone. A stored session token is then gone on the
next launch. It is iOS only, since Android has no keychain to reset.

<Accordion title="Foldable iOS simulators">
`device.fold(pose)` puts the iPhone Duo simulator in a hinge pose. `closed`
lights the outer display. `half-open` (a 130° book) and `open` light the
inner one. The call returns when the simulator reports the hinge at that
angle, typically after 10 to 16 seconds. Keep `actionTimeout` at 20 seconds
or more. The next observation reads the app on the other display.

The engine never resets the pose. A retry and the next test start in the
pose the last test left. Fold back in `afterEach`, which also runs when the
test fails:

```ts
import { afterEach, test } from '@e2e-dev/mobile';

afterEach(async ({ device }) => {
  await device.fold('closed');
});

test('the list and the detail split across the fold', async ({ agent, app, device }) => {
  await app.open();
  await device.fold('half-open');
  await agent.assert('the list and the detail sit on either side of the fold', { vision: true });
});
```
</Accordion>

## Several devices

Add a target for each platform:

```ts title="e2e.config.ts"
const app = { bundleId: 'com.example.app' };

export default {
  targets: [
    { name: 'iphone', engine: mobile({ platform: 'ios' }), app },
    { name: 'pixel', engine: mobile({ platform: 'android' }), app },
  ],
  workers: 1,
} satisfies E2EConfig;
```

Tests run on both targets. Set `platforms: ['ios']` or
`platforms: ['android']` on a test with platform-specific labels or
behavior.

To run files in parallel, give a device pool. Set `workers` to at least the
pool's size. Each device gets one worker:

```ts
mobile({ platform: 'ios', device: ['iPhone 17', 'iPhone 17 Pro'] })
```

Without `device`, the engine uses booted devices, up to the worker limit.
If none are booted, it boots one. Two workers never drive the same device.

## Agent tools

The agent already has basic actions such as `tap`, `type`, and `scroll`.
Add `mobileTools` for app switching, free-form swipes, and system alerts.
Pass every device engine in the config to one call:

```ts title="e2e.config.ts"
import { mobileTools } from '@e2e-dev/mobile/tools';

const iphone = mobile({ platform: 'ios' });
const pixel = mobile({ platform: 'android' });

export default {
  targets: [
    { name: 'iphone', engine: iphone, app },
    { name: 'pixel', engine: pixel, app },
  ],
  agents: { default: { model: gateway('openai/gpt-6-luna-fast'), tools: mobileTools(iphone, pixel) } },
} satisfies E2EConfig;
```

Calls go to the engine that runs the current attempt. `open_app`, `swipe`,
and `alert` change device state, so the agent runs them live during a cache
replay. To add your own tools beside the pack, see
[Project tools](/tools). The
[mobile engine reference](/reference/mobile#agent-tools) describes each
tool.

## Physical devices

agent-device drives a phone plugged into your machine as it drives a
simulator. A phone needs no other engine or option. List the devices
agent-device sees:

<CodeGroup>
```bash npm
npx agent-device devices --platform ios
```

```bash pnpm
pnpm exec agent-device devices --platform ios
```

```bash bun
bunx agent-device devices --platform ios
```
</CodeGroup>

Then name the phone in `device` as it is listed:

```ts
mobile({ platform: 'ios', device: 'QA iPhone' })
```

Name a phone by its name, not its id. The engine reads a `device` string as
an id only when it is a simulator UDID or an `emulator-<port>` serial. The
first device with a matching name wins, so give each phone a unique name.
Two phones both called `iPhone` would bind one phone to two workers.
Without `device`, a connected phone counts as booted and joins the pool
beside booted simulators. Name it to be sure a run lands on it.

Set the phone up one time:

<Tabs>
  <Tab title="iOS">
  - Pair and trust the phone, unlock it, and turn on Developer Mode.
  - agent-device builds and signs its XCTest runner onto the phone. Set
    `AGENT_DEVICE_IOS_TEAM_ID` to your team id and
    `AGENT_DEVICE_IOS_BUNDLE_ID` to a unique reverse-DNS id, such as
    `com.example.agentdevice.runner`. The signing profile must allow that id
    and `<id>.uitests`. The first run builds the runner and takes longer.
  - A running daemon keeps the environment it started with. After you
    change these variables, run `npx agent-device daemon stop`.
  - `app.appPath` must be a signed device build. A simulator `.app` doesn't
    install on a phone.

  `npx agent-device help physical-device` covers iOS signing in detail.
  </Tab>
  <Tab title="Android">
  - Turn on USB debugging and authorize the phone. `adb devices` lists it
    as `device`.
  - `app.appPath` is the same `.apk` as on an emulator.
  </Tab>
</Tabs>

`npx agent-device doctor` checks the setup. A phone isn't this machine, so
`localhost` in the app is the phone itself. Point the app at your machine's
network address. On Android, you can forward the port with
`adb reverse tcp:<port> tcp:<port>`.

<Accordion title="What doesn't work on a phone">
Some device controls need a simulator or emulator. On a phone, they fail
with agent-device's message.

- On an iPhone, every device setting is simulator-only: `app.permissions`,
  `device.setPermission`, `app.clearState()`, `device.setNetwork`,
  `device.setAirplaneMode`, `device.setLocation`, `device.clearLocation`,
  `device.setAppearance`, the biometric methods, and
  `device.clearKeychain`. So are `device.clipboard`, `device.setClipboard`,
  and `device.fold`.
- For a fresh start on an iPhone, reinstall with
  `device.installApp(path, { reinstall: true })`. Set `app.bundleId` on the
  target or `app` in the options, so agent-device knows which app to
  remove.
- agent-device drives an older iPhone without CoreDevice when
  `xcrun devicectl list devices` doesn't list it. Taps, typing, and the
  screen work. Installs, `--video`, `device.openLink`, and
  `app.launchArguments` fail. Install the build from Xcode and pin
  `app.bundleId`.
- On an Android phone, `device.setLocation` is emulator-only.
  `device.setBiometrics('fingerprint', ...)` works only where the phone
  exposes `cmd fingerprint`.
- `--video` on an iPhone is built from screenshots at about 15 frames a
  second, and drops frames.
</Accordion>

To run on phones in a device farm, see [Hosted devices](#hosted-devices).

## Hosted devices

Set `device` to a `DeviceProvider` to run on devices a service hosts. The
provider leases one device per worker slot when the run starts, and
releases it when the run ends. The engine drives each lease through the
agent-device daemon the lease names, instead of the local one. Any service
that runs an agent-device daemon next to a simulator, an emulator, or a
phone works.

For [EAS Simulators](/integrations/eas), use `easSimulators()` from
`@e2e-dev/eas`. For another service, write a provider of a few dozen lines
in your project, such as `hostedDevices` in the example below:

```ts
mobile({
  platform: 'ios',
  device: hostedDevices({ serviceUrl: 'https://devices.example.com', image: 'ios-18-iphone-17' }),
})
```

- With `workers: 2`, two workers lease two sessions in parallel. A service
  bills a session while it runs, so keep `workers` at what the suite can
  fill.
- The replay cache keys on `app.bundleId`, so recordings made locally
  replay on hosted devices.
- The runner warms leased devices like local ones. It boots them, starts
  the iOS runner, and opens the app one time before test timing starts.

<Accordion title="The DeviceProvider contract">
```ts
export interface DeviceProvider {
  /** Label in progress lines and error messages. */
  readonly name: string;
  acquire(request: DeviceRequest): Promise<DeviceLease>;
  release(lease: DeviceLease, context: DeviceReleaseContext): Promise<void>;
  record?(lease: DeviceLease, context: ProviderRecordContext): Promise<ProviderRecording>;
}

export interface DeviceLease {
  /** The provider's handle (a session id), handed back to `release`. */
  readonly id: string;
  /** The agent-device daemon the worker connects to; a lease names this, `client`, or both. */
  readonly daemon?: { readonly baseUrl: string; readonly authToken?: string };
  /** agent-device client configuration the worker's client is created with: a lease scope, a `stateDir`. */
  readonly client?: DeviceClientConfig;
  /** Device to select inside that daemon, when it hosts more than one. */
  readonly device?: string;
  /** Device to select inside that daemon by the id agent-device lists it under: a simulator UDID or an Android serial. */
  readonly deviceId?: string;
  /** Bundle id or package the provider installed itself; skips the target's `app.appPath`. */
  readonly installedApp?: string;
}
```

**`acquire`** runs once per worker slot, for every slot at once, in the
runner process. It gets the platform, the run id, the target, the slot, the
target's `app.bundleId` as `app`, and its resolved `app.appPath` as
`appPath`. It also gets `agentDeviceVersion`, the agent-device version the
engine's client speaks, for a service that starts a daemon of a chosen
version. The rest is `projectRoot`, the run's `env`, an interrupt `signal`,
and a `log` that reaches the reporter.

- Read tokens from `request.env`, not `process.env`. Read project files
  under `request.projectRoot`, not `process.cwd()`.
- A target with nothing to run leases nothing.
- Set `installedApp` only when the request has an `appPath`. Otherwise the
  run fails.

**`release`** runs after the last worker exits, within `cleanupTimeout`, on
every exit path: a failure, an interrupt, or a `prepare` that threw. It gets
the object `acquire` returned, so a provider can keep its own fields on it.
Only `id`, `daemon`, `client`, `device`, `deviceId`, and `installedApp` go
to the workers. The engine holds every lease it got, including one it then
refuses. When one slot fails to lease, the run ends before any test, and
the engine still releases the leases that succeeded.

**`client`** is agent-device client configuration, as JSON data. The
worker's client starts with it, on top of the session name and the `daemon`
address. The engine refuses a lease that sets `session`, `daemonBaseUrl`,
`daemonAuthToken`, or `daemonTransport`. For agent-device's own device-cloud
runtimes, `client` carries the lease scope that `leases.allocate` returned:
`tenant`, `runId`, `leaseId`, `leaseBackend`, and `leaseProvider`. The
daemon finds the hosted device from it on each command. A command without a
scope falls back to the local devices. A `stateDir` in `client` points the
worker at a daemon the provider started, so that provider needs no `daemon`
address.

**`record`** is optional. When an attempt records video, the worker calls
it with its lease, instead of agent-device's screen recording. The worker
may be another process, so `record` gets only the lease fields that travel
there, and no state `acquire` kept.
`record` returns a `ProviderRecording` (import the type from `e2e/engine`).
When the attempt's video ends, its `stop` either writes a file into the
directory it gets and returns `{ file }`, or returns `{ url, mediaType }`
for a recording the service keeps. The runner keeps a file as
`video/<file>` beside the attempt's other artifacts. The report links a
URL. A `record` that fails fails the attempt's launch, named after the
provider and the lease. A `stop` that fails is tried one more time when the
attempt ends. Without `record`, the engine records with agent-device.
</Accordion>

<Accordion title="Example: a provider for a session API">
A typical session API needs three requests: create a session, poll it until
the daemon is reachable, and stop it.

```ts title="device-provider.ts" expandable
import type { DeviceProvider } from '@e2e-dev/mobile';

/**
 * Leases devices from a service that starts an agent-device daemon per
 * session. Replace the three requests with your service's API.
 */
export function hostedDevices(options: { serviceUrl: string; image: string }): DeviceProvider {
  return {
    name: 'hosted-devices',
    async acquire(request) {
      const token = request.env['DEVICE_SERVICE_TOKEN'];
      if (token === undefined || token === '') throw new Error('DEVICE_SERVICE_TOKEN is not set');
      const headers = { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' };
      // 1. Ask for a device; name the session after the run so it can be found later.
      const created = await fetch(`${options.serviceUrl}/sessions`, {
        method: 'POST',
        headers,
        body: JSON.stringify({
          platform: request.platform,
          image: options.image,
          name: `e2e ${request.runId} ${request.targetName} ${request.slot + 1}/${request.slots}`,
        }),
        signal: request.signal,
      });
      if (!created.ok) throw new Error(`device service: HTTP ${created.status}`);
      const { id } = (await created.json()) as { id: string };
      // 2. Wait until the session exposes its agent-device daemon.
      for (;;) {
        const response = await fetch(`${options.serviceUrl}/sessions/${id}`, { headers, signal: request.signal });
        const session = (await response.json()) as { status: string; daemonUrl?: string; daemonToken?: string; viewerUrl?: string };
        if (session.status === 'ready' && session.daemonUrl !== undefined) {
          if (session.viewerUrl !== undefined) request.log(`watch at ${session.viewerUrl}`);
          return { id, daemon: { baseUrl: session.daemonUrl, authToken: session.daemonToken } };
        }
        if (session.status !== 'starting') throw new Error(`device service: session ${id} is ${session.status}`);
        await new Promise((resolve) => setTimeout(resolve, 5_000));
      }
    },
    async release(lease, context) {
      // 3. Stop the session; the run waits for this within cleanupTimeout.
      const token = context.env['DEVICE_SERVICE_TOKEN'] ?? '';
      await fetch(`${options.serviceUrl}/sessions/${lease.id}/stop`, {
        method: 'POST',
        headers: { Authorization: `Bearer ${token}` },
        signal: context.signal,
      });
    },
  };
}
```
</Accordion>

<Accordion title="Example: a device cloud that agent-device supports">
A device cloud that agent-device itself speaks to needs no session API of
your own. The provider allocates a lease through a daemon it starts for the
run, and gives the worker the lease scope as `client`.

```ts title="device-cloud-provider.ts" expandable
import { createAgentDeviceClient } from 'agent-device';
import type { DeviceProvider } from '@e2e-dev/mobile';

/**
 * Leases devices from a device cloud agent-device itself speaks to, through
 * a daemon started for the run. The daemon's runtime for the cloud creates
 * the instance when the lease is allocated and deletes it when the lease is
 * released; the worker's client carries the lease, so every command lands on
 * that instance. `provider` is agent-device's name for the cloud; its runtime
 * reads the credentials from the environment the daemon starts with.
 */
export function cloudDevices(options: { provider: string; stateDir: string }): DeviceProvider {
  const scopes = new Map<string, { tenant: string; runId: string; leaseId: string; leaseBackend: 'ios-instance' | 'android-instance'; leaseProvider: string }>();
  return {
    name: options.provider,
    async acquire(request) {
      // One daemon per run, under a directory of its own.
      const stateDir = `${options.stateDir}/${request.runId}`;
      const client = createAgentDeviceClient({ stateDir, session: `lease-${request.slot}` });
      const leaseBackend = request.platform === 'ios' ? ('ios-instance' as const) : ('android-instance' as const);
      const lease = await client.leases.allocate({
        tenant: options.provider,
        runId: request.runId,
        leaseBackend,
        leaseProvider: options.provider,
        platform: request.platform,
        target: 'mobile',
      });
      request.log(`leased ${lease.leaseId}`);
      const scope = { tenant: lease.tenantId, runId: lease.runId, leaseId: lease.leaseId, leaseBackend, leaseProvider: options.provider };
      scopes.set(lease.leaseId, scope);
      // The worker's client is created with these fields; the daemon resolves the device from them.
      return { id: lease.leaseId, client: { stateDir, ...scope } };
    },
    async release(lease) {
      const scope = scopes.get(lease.id);
      if (scope === undefined) return;
      const client = createAgentDeviceClient({ stateDir: `${options.stateDir}/${scope.runId}`, session: 'release' });
      await client.leases.release(scope);
    },
  };
}
```
</Accordion>

## What differs from the web

| On the web | On a device |
| --- | --- |
| `app.open('/path')` and the agent's `navigate` verb | No app URL. `app.open()` launches the target's `app.bundleId` fresh, `device.openLink(url)` opens a deep link or web link into it, and there is no `navigate` |
| `test.setup` saves a session, `session:` restores it | Not available. A simulator has no portable session snapshot; sign in per test or seed the app |
| Secret input | `type_secret` and `screen.getByLabel(...).fill(secret)` fill declared secrets into secure fields |
| `--video` writes a WebM screencast | `--video` writes an MP4 of the device screen with taps shown (`videoTouches: false` hides them), or keeps a device provider's own recording |
| The cache anchors on the page path | The cache anchors on the location `<bundle id> / <screen title>`, the title read off the navigation bar on iOS and the toolbar on Android |

### Known device limitations

- `placeholder` is the only attribute a device node has.
- A React Native tab (`accessibilityRole="tab"`) on iOS has role `other`.
  Query it by test id or label and assert `toBeSelected`. Checkboxes,
  radios, and `toBeChecked` work on both platforms.
- On iOS, a plain React Native `View` has no children in the tree. So
  `filter({ has })` on it and queries scoped to it match nothing. Scope to
  the screen's `ScrollView` (`device.locator('role=ScrollView')`), or give
  the children test ids.
- A Jetpack Compose clickable drawn smaller than 48dp reports a 48dp touch
  area but its role node at the drawn size. The tree shows two buttons, and
  a tap fails with `has no parent-owned touch point`. Make the control at
  least 48dp, Android's minimum touch target.
- An element hidden with `display: none` isn't in the tree, so
  `toBeAttached` fails. Assert `toHaveCount(0)` or `toBeHidden`.
- `doubleTap()` on iOS is two taps about 285 ms apart. Give a double-tap
  detector a window of 350 ms or more.
- On iOS, `device.foregroundApp()` still names the session's app after
  `device.home()`. Check the screen instead.
- On an iPhone Duo, `--video` records the display that was lit when the
  recording started. After `device.fold` moves the app to the other display,
  the rest of the video is black.

## Troubleshooting

A device failure shows agent-device's own message. Under the agent, an
engine fault with no more specific code reports as `APP_UNREACHABLE`. Read
the message before the code: often the app isn't the part that failed.

**The iOS automation runner is busy, wedged, or can't present a
snapshot.** A heavy or animating screen can overrun the runner. A run
stopped with Ctrl-C can leave it busy for the next run. The message tells
you what to do:

```text
APP_UNREACHABLE: agent.act failed: snapshot failed: the iOS automation runner is still
finishing a command that overran its watchdog (session e2e-ios-0 on iPhone 17 Pro):
The iOS runner is still finishing a previous command that exceeded its execution
watchdog (usually an accessibility capture on a heavy or animating screen). The app
is fine. Wait a few seconds and rerun. If the next run meets it again, stop the
daemon (`npx agent-device daemon stop`) and reboot the simulator
(`xcrun simctl shutdown <udid>`, then `boot`).
```

**`device.installApp()` on Android reports no bundle id or package.** The
build installed, but agent-device couldn't tell which package it is, so
`app.open()` has nothing to launch. When agent-device can't read the APK's
manifest, it falls back to the Android SDK's `aapt`. It looks for the SDK
under `ANDROID_SDK_ROOT`, `ANDROID_HOME`, `~/Library/Android/sdk` on macOS,
and `~/Android/Sdk`. Without `aapt`, it names only a package the install
added, and a build already on the emulator adds none. Set the target's
`app.bundleId`. Or export `ANDROID_HOME`, then stop the agent-device daemon
so the next run starts it with the variable.

**A timeout on the device.** A simulator boot, runner connection, or app
launch that times out on the device is `ENGINE_FAILURE`, with
agent-device's message and hint. It is never one of e2e's own timeout codes
(`LAUNCH_TIMEOUT`, `ACTION_FAILED`, `STEP_TIMEOUT`).
