e2e runs on each CI service that can run Node 24.8 or later (22.22.3 or
later on Node 22). Each job installs the dependencies, starts the app or a
device, runs `npx e2e run`, and uploads `.e2e/`. Only the syntax of the job
file changes from one service to the next.

## Upload the reports

Upload `.e2e/` at the end of each job, also when a test fails. It holds:

| Path | What it holds |
| --- | --- |
| `report.json` | The run report, from each run that reaches its tests |
| `junit.xml` | With the `junit` reporter (`--reporter list,junit`): the results, and startup failures such as `APP_UNREACHABLE` in a `run` suite |
| `results/` | The trace pages, screenshots, and screen dumps of each test. With `--video`, also a video for each target whose engine can record |

Point the test-report integration of your CI service at `.e2e/junit.xml`.
On GitHub, add the [GitHub reporter](/github) to post the results on the
pull request. The [`output`](/reference/config#output) option moves `.e2e/`.

## Model credentials

Give the job the credential that your provider needs, such as
`AI_GATEWAY_API_KEY`. See [Models](/models) for provider setup. Tests that
never use `agent` need no model credentials.

<Warning>
Each job that has the key gives it to the code it runs: tests, config, and
dependencies. Give the key only to builds of branches that you trust. Run
untrusted pull request code with no secrets and no write tokens. See the
[Security](/security) guide.
</Warning>

Keep keys in CI secrets, and set spending limits where you can. GitHub does
not give secrets to pull requests from forks.

## What CI changes

CI mode is on when `CI` has a value other than an empty string, `0`, or
`false`. To get these defaults locally, run `CI=1 npx e2e run`:

| Setting | Local | CI |
| --- | --- | --- |
| `retries` | `0` | `1` |
| `workers` | half your cores | `1` |
| `cache` when unset | `read-write` | `read-only` |
| `.only` | allowed | rejected with `ONLY_IN_CI` |
| `command.reuseExisting` | honored | ignored, with a notice |

To change the worker and retry defaults, use flags:

<CodeGroup>
```bash npm
npx e2e run --workers 4 --retries 0
```

```bash pnpm
pnpm exec e2e run --workers 4 --retries 0
```

```bash bun
bunx e2e run --workers 4 --retries 0
```
</CodeGroup>

To send no [telemetry](/telemetry#in-ci) from CI, add
`E2E_TELEMETRY_DISABLED: '1'` to the `env` of the job.

## Mobile jobs

A mobile job builds the app, boots a device, installs the build, and runs
`npx e2e run`. A hosted device service needs no Mac and no KVM; see
[Hosted devices](/mobile#hosted-devices).

| | iOS | Android |
| --- | --- | --- |
| Machine | macOS with Xcode and a simulator runtime | Linux with KVM (nested virtualization) |
| Build | Release simulator `.app`, no signing | Release `.apk` |
| Device | A booted simulator | A booted emulator |

Make a Release build on both platforms. A React Native or Expo debug build
loads its JavaScript from Metro, and no job on these pages starts Metro. A
debug build opens on an error screen. The examples use a React Native
project with `ios/` and `android/` in the repository. For an Expo project
without these directories, run `npx expo prebuild` first.

Install the build, then run the suite:

<CodeGroup>
```bash npm
# iOS
xcrun simctl install booted path/to/MyApp.app
npx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
npx e2e run --target android --reporter list,junit
```

```bash pnpm
# iOS
xcrun simctl install booted path/to/MyApp.app
pnpm exec e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
pnpm exec e2e run --target android --reporter list,junit
```

```bash bun
# iOS
xcrun simctl install booted path/to/MyApp.app
bunx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
bunx e2e run --target android --reporter list,junit
```
</CodeGroup>

<Accordion title="Example mobile config">
The config names the app by its bundle id or package name.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

export default {
  targets: [
    { name: 'ios', engine: mobile({ platform: 'ios' }), app: { bundleId: 'com.example.app' } },
    { name: 'android', engine: mobile({ platform: 'android' }), app: { bundleId: 'com.example.app' } },
  ],
  workers: 1,
} satisfies E2EConfig;
```

To let the suite install the build, set `app.appPath` and call
`device.installApp()`. See [Point at your app](/mobile#point-at-your-app).
</Accordion>

These rules apply on each service:

- **One job for each platform.** Run `--target ios` on a Mac and
  `--target android` on Linux with KVM. Hosted Macs use Apple Silicon,
  which can't nest virtualization, so the Android emulator doesn't start
  on them.
- **Boot the device in its own step.** When no device is booted, the
  engine tells agent-device to boot one. But a new Linux runner has no
  emulator image until you install one. A separate step also shows a slow
  or failed boot apart from a failed test.
- **Pin the iOS runtime.** A simulator selected by name (`iPhone 17`) runs
  the default iOS of the image. The accessibility tree changes between iOS
  releases, so a runner image update can fail a locator assertion with no
  change in your code. The examples create a simulator on a named runtime
  and boot it by UDID. Replace `iOS-26-5` with a runtime the image has
  (`xcrun simctl list runtimes`).
- **Cache `~/.agent-device`.** agent-device builds its XCUITest runner
  there the first time it drives a simulator.
- **Replay local recordings.** The replay cache key holds the app, not the
  device, so a step recorded on your simulator replays on the CI
  simulator. See [Gate pull requests](#gate-pull-requests).

## Gate pull requests

Each non-zero exit fails the job, a failed agent step included. To block
merges on a failed run, make the e2e job a required check of your
repository. [Debugging a run](/debugging#read-the-failure) lists each exit
code and tells you if a retry of the job can help.

To keep the checks predictable:

- Give each `agent.act` one goal. Then check its result with a locator
  assertion or `agent.assert`.
- [Commit the replay cache](/cache#commit-the-replay-cache). A replayed
  `agent.act` makes no model call. A cache miss, a hand-off, and every agent
  judgment (`agent.assert`, `agent.waitFor`, `agent.extract`) call the model.
- Watch for flaky tests. CI retries a failed test one time, and a test that
  passes only on the retry is reported as flaky.
- Add `--max-failures <n>` to stop the run after that many failed tests, so
  a broken deploy doesn't spend a model call on each remaining step. Tests
  that didn't start are skipped with cause `failure-limit`. Running tests
  end as `interrupted`, counted apart from the failures. The job exits 1.

## Sharding

`--shard <index/total>` runs one slice of the suite in each job. Each job
runs the same command with its own index, and the suite shards the same way
on each machine. A shard with no test fails with `NO_TESTS`. If a matrix can
have more shards than tests, add `--pass-with-no-tests`. The
[CLI reference](/reference/cli#flags) has the slicing rules.

On GitHub Actions, a matrix runs one job for each shard:

```yaml
jobs:
  e2e:
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3]
    steps:
      # ...
      - run: npx e2e run --shard ${{ matrix.shard }}/3 --reporter list,junit
```

Each shard writes its own `report.json` and `junit.xml`. Upload them under
a name that includes the shard index. e2e can't merge the shard reports
into one yet.

## Rerunning failures

`--last-failed` runs only the tests that didn't pass in the previous run. It
reads them from `report.json` in the output directory. Run it in the same
step as the first run:

```yaml
      - run: npx e2e run || npx e2e run --last-failed
```

The rerun keeps the artifacts the first report names and writes its own
under `rerun-<n>/` in each test's directory. One upload after the step holds
the evidence of both runs. A test that another filter keeps out of the rerun
stays owed, and the next `--last-failed` runs it. The
[CLI reference](/reference/cli#flags) lists what counts as not passed.

In a separate job, the report is not on the runner. Download it into the
output directory before the rerun, or run the failed job again.
