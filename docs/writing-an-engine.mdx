An engine connects `screen`, `app`, and agent calls to a UI platform through
the `e2e/engine` contract. Write one to test a desktop app, a TV, or another
platform. `@e2e-dev/web` and `@e2e-dev/mobile` use the same public
`defineEngine` API, so read them as complete examples.

Engines drive user interfaces only. For a supporting service, such as an
inbox, a database, or a test API, write a fixture with
[`test.extend`](/reference/test#your-own-fixtures).

## The ownership boundary

The runner manages tests and policy. The engine observes and controls the UI.

| Concern | Owner |
| --- | --- |
| Collection, targets, retries, hooks, sessions | runner |
| Query polling and strict single-match cardinality | runner |
| Assertion polling, step recording, timeouts | runner |
| One immediate query, one node read | engine |
| One node's actionability and input dispatch | engine |
| Agent planning, prompts, budgets, ledger | runner |
| Tool authorization and secret resolution | runner |
| Process, page, and device mechanics | engine |
| Source masking of secure observations | engine |
| Defense-in-depth redaction | runner |

`locate` returns the current matches at once, or an empty array when
nothing matches. Don't retry queries or reject multiple matches. The runner
does the polling and the single-match checks.

## The shape of an engine

Return a handle from `defineEngine`. It validates the manifest and computes
the engine's capabilities when the config loads.

<Note>
Import types and helpers from `e2e/engine` only. Declare `e2e` as a peer
dependency, so the engine and the runner share one set of error classes.
The exports include errors, text and URL matching, assertion polling, JSON
validation, and cancellation helpers. There is no internal subpath.
</Note>

This skeleton assumes a `createClient` adapter for your platform. Its nodes
must follow the [semantic tree rules](#nodes-and-refs).

```ts title="src/index.ts" expandable
import { ConfigurationError, defineEngine, resolveExpression, type EngineHandle } from 'e2e/engine';

export function hyperdrive(options: { device: string }): EngineHandle {
  const client = createClient(options);
  let bundleId = '';
  return defineEngine({
    name: 'hyperdrive',
    version: '1.0.0',
    spiVersion: 1,
    platform: 'ios',
    validateApp(app, { targetName }) {
      if (app.bundleId === undefined) {
        throw new ConfigurationError('INVALID_CONFIG', `target "${targetName}" needs app.bundleId`);
      }
    },
    async init(info) {
      bundleId = info.app.bundleId!;
      await client.boot();
    },
    async dispose(context) { await client.shutdown({ signal: context.signal }); },
    async observe() {
      const screen = await client.snapshot();
      return {
        location: screen.title,
        // One root with a stable id: `perform(root, swipe)` is the viewport swipe.
        root: { ref: { id: 'root', revision: '' }, role: 'window', children: screen.nodes },
        viewport: screen.viewport,
      };
    },
    async locate(expression) {
      const screen = await client.snapshot();
      return resolveExpression(expression, screen.nodes);
    },
    actions: ['tap', 'fill', 'swipe'],
    async perform(ref, action) {
      switch (action.kind) {
        case 'tap': return client.tap(ref.id);
        case 'fill': return client.type(ref.id, action.value);
        case 'swipe': return client.scroll(ref.id === 'root' ? undefined : ref.id, action.direction);
      }
    },
    session: {
      async back() { await client.back(); },
      async restart() { await client.relaunch(bundleId); },
    },
  });
}
```

```ts title="e2e.config.ts"
targets: [{ name: 'phone', engine: hyperdrive({ device: 'iPhone 16' }), app: { bundleId: 'com.example.app' } }],
```

- `version` is required. Reports name it, and a saved session restores only
  under the version that saved it. The replay cache doesn't key on it,
  because a recording finds its nodes again at replay.
- `locate` answers `screen` queries. The exported `resolveExpression`
  applies the standard query rules to a semantic tree.
- The app under test is the target's `app`, not an engine option.
  `validateApp` checks it at config load. `prepare` and `init` receive it as
  `info.app`.

## Capabilities

The optional methods you implement set the engine's capabilities. Calls to
a missing one fail with `UNSUPPORTED_CAPABILITY`. Start with these:

| Member | Unlocks |
| --- | --- |
| `observe(context, options?)` | Agent observations and the replay cache |
| `perform(ref, action, context)` + `actions` | Node actions of the declared kinds, including viewport scrolling through `swipe` |
| `locate(expression, context)` | `screen`, `Locator`, and `expect(locator)` |
| `validateApp(app, info)` | A config-load check of the target's `app`. Throw `INVALID_CONFIG` naming `info.targetName` for a field the platform needs or can't drive. [Reference](/reference/engine#app) |
| `session.{open?,back?,restart?,reset?}` | `app.open()`, `app.back()`, `app.restart()`, `app.clearState()`, and the agent's `navigate` and `back` verbs |

Pointer actions, the keyboard, saved state, artifacts, and contributed
fixtures are optional capabilities too. `actions`, `location`, `pointer`,
and `keyboard` require `observe`. The
[engine reference](/reference/engine#capabilities) lists every member, and
which action kind unlocks which agent tool.

The agent gets only the tools the engine supports and the step's declared
credentials. Each action kind you declare unlocks its verb: `hover` the
`hover` tool, `dragTo` the `drag` tool, `setInputFiles` the `upload` tool,
`check` with `uncheck` the `check` tool.

Agent actions and locator actions both reach `perform` as a
`LocatorAction`. When one node can't do a declared action, throw
`UNSUPPORTED_CAPABILITY`.

`session.open` receives a URL that the runner already resolved. After
`restart` or `reset`, the runner opens the configured address again through
`open`. If your engine has no `open`, relaunch the app in those hooks.

## Lifecycle

The hooks, in the order they run:

| Hook | When | Use it to |
| --- | --- | --- |
| `prepare` | One time per target, in the runner process | Install runtimes. The `env` it returns reaches every worker |
| `init` | One time per worker, before its first attempt | Boot devices. It must also work on an engine that was disposed |
| `startAttempt` | Before each attempt | Create the test's UI |
| `settleAttempt` | After the body, and again after teardown | Throw the error of a test callback no step awaited, such as a dialog handler |
| `endAttempt` | After each attempt, also after a failed start | Clean up the test's UI. Make it idempotent |
| `dispose` | At worker shutdown, even if `init` never ran | Release the worker's resources |
| `finish` | One time per target, after the last worker is gone, whenever `prepare` ran | Release what `prepare` acquired |

Use `info.env` for the processes you start and `info.log` to report
progress. The [engine reference](/reference/engine#lifecycle) has each
hook's arguments and budgets.

## Nodes and refs

`observe` returns a `SemanticNode` tree, and `locate` returns the nodes that
match an expression. Give each node an id that stays unique for the UI's
lifetime. The runner assigns revisions and checks staleness.

- Keep the root id stable across observations. The agent's `scroll` and
  `screen.swipe()` call `perform(root, { kind: 'swipe' })`. A swipe on
  another node scrolls inside that node.
- When `perform` receives `{ id, revision }`, look up the id. Throw
  `NODE_STALE` when the node no longer exists.
- When a match leaves the UI while `locate` reads it, throw a retryable
  `NODE_STALE`. Never return a node read from what is gone: a removed
  element has no size, so `toBeHidden` would pass while its replacement is
  on screen. The runner resolves again within the caller's deadline.
- Limit the snapshot size if the platform can return an unbounded tree. Set
  `truncated` when the limit cuts off nodes, so the runner knows the list is
  incomplete.
- Use the platform's accessible names for nodes.
- Put test identifiers in `testId`: a document attribute, an iOS
  accessibility identifier, an Android resource id, or a desktop automation
  id. The `testId` query matches only that field.

An observation can include `location`, such as a URL, a screen title, or a
window name. The runner shows it to the model and in the report, and
anchors replay cache entries on it.

## Keyboard

Implement `keyboard` to type into a control after the agent focuses it.
`keyboard.type` must type through the platform's keyboard path, so the app
gets the key events a person's typing makes. A browser engine sends
`keydown`, `keypress`, `input`, and `keyup` for each character. A device
engine uses the device keyboard. Setting the value without keystrokes
doesn't comply.

- Throw `NOT_ACTIONABLE` when no editable control has focus.
- Leave out `dismiss` on platforms without an on-screen keyboard.
- `locator.pressSequentially` uses the same hook after a `focus` action.
  It needs nothing more.

For `press`, read keys such as `Enter` or `ControlOrMeta+a` with the
exported `parseKey`. The runner rejects invalid spellings with
`INVALID_ARGUMENT`. Map valid keys to your platform, and throw
`UNSUPPORTED_CAPABILITY` for keys it can't send. See the
[key grammar](/reference/engine#keys).

## Vision-only surfaces

For a UI without a semantic tree, return a `root` with no children, plus
`pixels`, from `observe`. Implement `performAt` and declare its kinds in
`pointerActions`.

The agent gets the screenshot and acts through tools such as `tap_at`. The
runner passes a point to `performAt` when no listed node is at it.
Coordinate actions replay only at the recorded viewport size, and the
runner checks the recorded end state before it accepts a replay.

## Handle secrets

A secret fill reaches the engine as a `fill` action with
`sensitive: true`. There is no separate capability flag for it. The runner
first checks the declared credential, the current observation, and a
compatible editable field. Handle the fill securely, or throw
`UNSUPPORTED_CAPABILITY`. After it, the runner takes
[no more screenshots](/reference/security#screenshots-after-a-secret-fill).

An engine option can take a secret too, such as a password the engine sends
to the app:

1. Accept `string | Secret`. Tell them apart with `isSecret` from
   `e2e/engine`.
2. List each handle in the engine's `secrets`. The config load rejects a
   name that no secret has.
3. Read the value in `startAttempt` with `context.resolveSecret(secret)`.

Until a run exists, the handle is only a name. The runner redacts the value
from the moment it resolves. When the app sees the value in another form,
such as an encoded header, return that form from
`resolveSecret(secret, { derived })` to redact it under the same name. This
protects text only: a session whose engine resolved a secret keeps its
screenshots.

## State is a credential

A `state` snapshot can hold authentication data such as cookies and tokens.
The runner encrypts it with a key for each run. It binds the snapshot to
the run, target, engine, and app identity, and deletes it after the run.

Don't persist, cache, or log snapshots, or put them in errors. `restore`
must replace the app's whole persisted state, not merge into it.

## Errors

Throw `EngineError` with a code from the
[engine reference](/reference/engine).

- Only `NODE_STALE` and `FRAME_NOT_FOUND` can be retryable.
- Use `ACTION_MAY_HAVE_COMMITTED` when an action may already have taken
  effect, so the runner doesn't repeat it.
- `INVALID_STATE` becomes `APP_NOT_OPEN`, and `UNSUPPORTED_CAPABILITY` is a
  configuration error.
- Unknown errors become infrastructure failures.

## Contributed fixtures

An engine can contribute fixtures such as `browser` or `device`. Wrap their
methods with `context.fixture` to record each call as a `<fixture>.<method>`
step, with its own artifacts and failures.

```ts
fixtures: {
  device: (context) => context.fixture('device', {
    async setNetwork(state: 'online' | 'offline') { await client.network(state); },
    async home() { await client.home(); },
  }, {
    setNetwork: { kind: 'resource', label: (state) => state },
    home: { kind: 'resource' },
  }),
},
```

```ts title="tests/fixtures.ts"
import { test as base } from 'e2e';
import type { Device } from 'e2e-engine-hyperdrive';

export const test = base.extend<{ device: Device }>();
```

The fixture context gives URL policy checks, timeouts, operation budgets,
artifact attachment, and factories for locators and assertions. For
example, `expectable(target, factory)` adds matchers for `expect(fixture)`.
See the [engine reference](/reference/engine) for the full context.

## Ship a tool pack

For platform operations that the action set lacks, ship a pack of
[project tools](/tools) built with `defineTool`. Set `platforms` so each
tool shows only on compatible targets. `@e2e-dev/mobile/tools` is one
example.

## Verify it

Run a test file against your engine. Check the lifecycle order,
observations, actions, errors, and unsupported capabilities.
[`engine-contract.test.ts`](https://github.com/tester-army/e2e/blob/main/packages/e2e/tests/integration/engine-contract.test.ts)
tests the runner's side of the contract and has examples of these checks.
