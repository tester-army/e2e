title: Writing an engine
description: Implement the e2e engine contract for another UI platform.
---

An engine connects `screen`, `app`, and agent calls to a UI platform through
the `e2e/engine` contract. Use it to support a desktop app, a TV, or another
platform.

The existing `@e2edev/web` and `@e2edev/mobile` packages use the
same public `defineEngine` API. Read their implementations alongside this
guide for complete examples.

## The ownership boundary

The runner manages tests and policy. The engine observes and controls the UI.

| Concern | Owner |
| --- | --- |
| Collection, targets, retries, hooks, sessions | runner |
| Query polling and strict single-match cardinality | runner |
| Assertion polling, step recording, timeouts | runner |
| One immediate query, one node read | engine |
| One node's actionability and input dispatch | engine |
| Agent planning, prompts, budgets, ledger | runner |
| Tool authorization and secret resolution | runner |
| Process, page, and device mechanics | engine |
| Source masking of secure observations | engine |
| Defense-in-depth redaction | runner |

`locate` must return the current matches immediately, including an empty
array when nothing matches. Do not add query retries or reject multiple
matches. The runner handles polling and single-match checks.

## The shape of an engine

Return a handle from `defineEngine`. It validates the manifest and determines
the engine's capabilities when the config loads.

This skeleton assumes a `createClient` adapter for your platform. Its nodes
must follow the semantic tree contract described below.

```ts title="src/index.ts"
import { defineEngine, type EngineHandle } from 'e2e/engine';

export function hyperdrive(options: { device: string; app: string }): EngineHandle {
  const client = createClient(options);
  return defineEngine({
    name: 'hyperdrive',
    version: '1.0.0',
    spiVersion: 1,
    platform: 'ios',
    app: { identity: options.app },
    async init(info) { await client.boot(); },
    async dispose(context) { await client.shutdown({ signal: context.signal }); },
    async observe() {
      const screen = await client.snapshot();
      return {
        location: screen.title,
        // One root with a stable id: `perform(root, swipe)` is the viewport swipe.
        root: { ref: { id: 'root', revision: '' }, role: 'window', children: screen.nodes },
        viewport: screen.viewport,
      };
    },
    actions: ['tap', 'fill', 'swipe'],
    async perform(ref, action) {
      switch (action.kind) {
        case 'tap': return client.tap(ref.id);
        case 'fill': return client.type(ref.id, action.value);
        case 'swipe': return client.scroll(ref.id === 'root' ? undefined : ref.id, action.direction);
      }
    },
    session: {
      async back() { await client.back(); },
      async restart() { await client.relaunch(options.app); },
    },
  });
}
```

```ts title="e2e.config.ts"
targets: [{ name: 'phone', engine: hyperdrive({ device: 'iPhone 16', app: 'com.example.app' }) }],
```

`version` is required and forms part of the trace cache key. Change it when
engine behavior changes. With `perform`, also declare `actions` to list the
supported action kinds. `app` describes the app under test; `session`
provides methods to open or restart it.

## What an engine is not

Engines drive user interfaces. Use fixtures for supporting services such as
an inbox, a database, or a test API. Add those through
[`test.extend`](/reference/test#your-own-fixtures).

<Note>
Import shared types and helpers from `e2e/engine`, and declare `e2e` as a
peer dependency so the engine and runner share their error classes.
The public exports include errors, text and URL matching, assertion polling,
JSON validation, and cancellation helpers. There is no internal subpath.
</Note>

## Capabilities

Implement the optional methods your platform supports. Their presence
determines the available capabilities. Calls to unsupported capabilities
fail with `UNSUPPORTED_CAPABILITY`.

| Member | Capability | Unlocks |
| --- | --- | --- |
| `observe(context, options?)` | `observation` | Agent observations and trace replay |
| `perform(ref, action, context)` + `actions` | `actions` | Node actions supported by the declared kinds, including viewport scrolling through `swipe` |
| `locate(expression, context)` | `location` | `screen`, `Locator`, and `expect(locator)` |
| `performAt(point, action, context)` + `pointerActions` | `pointer` | Coordinate actions supported by the declared kinds |
| `keyboard.{type,press,dismiss?}` | `keyboard` | Typing and key presses into the focused control; optional keyboard dismissal |
| `state.{capture,restore}` | `state` | `test.setup` and the `session` option |
| `artifacts.{screenshot,startTrace?,stopTrace?,startVideo?,stopVideo?}` | `artifacts` | Screenshots, plus traces and video when their start and stop hooks exist |
| `app` | | App address, identity, environment, and process settings. [Reference](/reference/config#the-app-under-test). |
| `session.{open?,back?,restart?,reset?}` | | `app.open()` and the agent's `navigate` verb, `app.back()`, `app.restart()`, `app.clearState()` |
| `fixtures.<name>` | `<name>` | a contributed fixture, typed through `test.extend` |

`actions`, `location`, `pointer`, and `keyboard` require `observe`. The agent
receives only tools supported by the engine and the step's declared
credentials. Agent and locator actions both reach `perform` as a
`LocatorAction`. Throw `UNSUPPORTED_CAPABILITY` if a particular node cannot
support an otherwise declared action.

The agent's `scroll` and `screen.swipe()` call
`perform(root, { kind: 'swipe' })`. Keep the root id stable across observations.
A swipe on another node scrolls within that node.

Use the exported `parseKey` to interpret `press` keys such as `Enter` or
`ControlOrMeta+a`. The runner rejects invalid spellings with `INVALID_ARGUMENT`.
Map valid keys to your platform and throw `UNSUPPORTED_CAPABILITY` for keys
it cannot send. See the [key grammar](/reference/engine#keys).

An observation may include `location`, such as a URL, screen title, or window
name. The runner uses it for trace replay and applies origin checks when it
parses as a URL.

`session.open` receives a URL already resolved by the runner. After `restart`
or `reset`, the runner reopens the configured address through `open`. If your
engine has no `open` method, relaunch the app within those hooks.

There is no separate secure-fill capability flag. Before dispatching a
secret fill, the runner checks the declared credential, current
observation, and compatible editable field. The engine receives a
`fill` action with `sensitive: true` and must handle it securely or throw
`UNSUPPORTED_CAPABILITY`. Screenshots are withheld after a secret fill;
`app.screenshot()` then raises `POLICY_DENIED`.

### Lifecycle

- `prepare` runs once per target in the runner process, before the run's
  clock starts. Install runtimes here and report progress through `info.log`.
- `finish` runs once per target in the runner process after the last worker
  is gone, on every exit path, whenever `prepare` was called. Release what
  `prepare` acquired for the run (a leased cloud device). It has the cleanup
  budget and is never cancelled by an interrupt; a failure is recorded as a
  cleanup error.
- `init` runs once per worker before its first attempt. Boot devices here.
  It receives the app's site, project root, worker slot, and headed setting.
  Its `info.log` reaches the reporter like `prepare`'s, prefixed with the
  target and worker slot (`ios worker 1: ...`): the place for a fact that
  only exists once the worker is up, such as the URL where a hosted browser
  or device can be watched, or which simulator the slot got.
- `startAttempt` and `endAttempt` surround each attempt. Create and clean up
  the test's UI here. If startup fails or exceeds `launchTimeout`, the runner
  aborts its signal and calls `endAttempt`, so cleanup must be idempotent.
- `dispose` runs at worker shutdown, even if `init` never ran. The same handle
  can later receive another `init`.

Use `info.env` for spawned processes. Return environment additions from
`prepare` in its `env` field; each worker receives them in `init`.

### Nodes and refs

`observe` returns a `SemanticNode` tree. `locate` returns the nodes matching
an expression. Assign ids that stay unique for the UI's lifetime and keep
the root id stable. The runner assigns revisions and checks staleness.
When `perform` receives `{ id, revision }`, look up the id and throw
`NODE_STALE` if the node no longer exists.

Limit snapshot size if the platform can return an unbounded tree. Set
`truncated` when the limit cuts off nodes so the runner knows the listing
is incomplete. Use the platform's accessible names for nodes.

Report `states.hidden` by one predicate in `observe` and `locate`: a node
the tree walk skips must read as hidden when located on its own, or
`toBeVisible()` passes on a node the snapshot never shows. When the cause is
not layout (`aria-hidden` on a document, a view's accessibility-hidden flag),
name it in `hiddenBy`; the failure message then reads `hidden by aria-hidden`
instead of marking text a person can see hidden with no reason.

Put test identifiers in `testId`, whether they come from a document attribute,
an iOS accessibility identifier, an Android resource id, or a desktop
automation id. The `testId` query matches only that field.

### Vision-only surfaces

For a UI without a semantic tree, return a childless `root` and `pixels`
from `observe`. Implement `performAt` and declare the supported kinds in
`pointerActions`.

The agent receives the screenshot and can act through tools such as `tap_at`.
The runner passes points to `performAt` when no listed node occupies them.
Coordinate actions replay only at the recorded viewport size, and the runner
checks the recorded end state before accepting a replay.

Implement `keyboard` to type into a control after the agent focuses it.
`keyboard.type` must deliver the text as a person typing would, through the
platform's keyboard path, so that key events reach the app where the platform
has them: a browser engine dispatches `keydown`, `keypress`, `input`, and
`keyup` per character; a device engine sends the text through the device
keyboard. Inserting the value without keystrokes is not a compliant
implementation. It must throw `NOT_ACTIONABLE` when no editable control has
focus. Omit `dismiss` on platforms without an on-screen keyboard. The same
hook, after the `focus` action, is what `locator.pressSequentially` types
through; the harness composes the two and asks nothing more of the engine.

### State is a credential

A `state` snapshot can contain authentication data such as cookies and tokens.
The runner encrypts it with a per-run key, binds it to the run, target,
engine, and app identity, and deletes it after the run.

Do not persist, cache, log, or include snapshots in errors. `restore` must
replace the app's entire persisted state instead of merging into it.

### Errors

Throw `EngineError` with a code from the
[engine reference](/reference/engine). Only `NODE_STALE` and `FRAME_NOT_FOUND`
can be retryable. Use `ACTION_MAY_HAVE_COMMITTED` when an action may already
have taken effect so the runner does not repeat it.

`INVALID_STATE` maps to `APP_NOT_OPEN`, and `UNSUPPORTED_CAPABILITY` is a
configuration error. Unknown errors become infrastructure failures.

## Contributed fixtures

Engines can contribute fixtures such as `web` or `device`. Wrap their methods
with `context.fixture` to record calls as `<fixture>.<method>` steps with
their own artifacts and failures.

```ts
fixtures: {
  device: (context) => context.fixture('device', {
    async setNetwork(state: 'online' | 'offline') { await client.network(state); },
    async home() { await client.home(); },
  }, {
    setNetwork: { kind: 'resource', label: (state) => state },
    home: { kind: 'resource' },
  }),
},
```

```ts title="tests/fixtures.ts"
import { test as base } from 'e2e';
import type { Device } from 'e2e-engine-hyperdrive';

export const test = base.extend<{ device: Device }>();
```

The fixture context provides URL policy checks, timeouts, operation budgets,
artifact attachment, and factories for locators and assertions. For example,
`expectable(target, factory)` adds matchers for `expect(fixture)`. See the
[engine reference](/reference/engine) for the full context.

## Scoping agent tools to a platform

Add [project tools](/tools) with `defineTool` on the agent. Use `platforms`
to offer a tool only on compatible targets:

```ts
const swipe = defineTool(swipeTool(client), {
  mutates: true,
  platforms: ['ios', 'android'],
});
```

## Verify it

Run a test file against your engine. Check lifecycle order, observations,
actions, errors, and unsupported capabilities. The repository's
`packages/e2e/tests/integration/engine-contract.test.ts` demonstrates the
runner's contract and provides examples for these checks.
