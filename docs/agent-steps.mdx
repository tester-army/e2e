---
title: How agent steps work
description: What the model sees, what it may do, how a step ends, and what it costs.
---

Each `agent.*` call has a deadline and a model-call budget. The runner
observes the screen, checks requested actions against its policy, and
records the result.

## Two sides of the contract

The runner handles redaction, action authorization, budgets, secrets, and
reporting. The executor decides which actions to request and returns a
verdict. `createAgent()` provides the built-in executor.

[Custom executors](/executors) get the same redacted observations and checked
action methods. Their own code runs with the test process's OS permissions.

## What the model sees

For `act`, the opening prompt includes the instruction, params, completed
steps, and a redacted text snapshot of the screen's roles, names, text, and
states. It excludes raw HTML, cookies, headers, and environment values.
Password fields are masked. Configured secret values found on screen are
replaced with `<secret:name>`.

After an action, the model receives the changes to the screen. If most of
the screen changed, it receives a new full snapshot. Node ids remain stable
while their elements exist.

The runner waits up to two seconds for an action to change the screen before
capturing the result. A failed action also returns the current screen so the
model can choose what to do next.

Judgments from `assert`, `waitFor`, and `extract` see the instruction and
current screen. They do not see completed steps or the acting agent's
summaries. You can configure a separate [judge model](/models#a-judge-of-its-own).

Use `vision: true` to include a masked screenshot or `vision: 'only'` to
judge the screenshot alone. Pixels are withheld after a secret is filled.
The [agent reference](/reference/agent#vision) lists the modes.

## What the model may do

The agent receives tools supported by the target's engine, such as `tap`,
`type`, `press`, `select`, `scroll`, and `navigate`. A step with declared
credentials can also receive `type_secret`.

Keyboard-capable engines support typing and key presses into the focused
control. Pixel tools let the agent request a screenshot and act at a point
when the text snapshot cannot describe a control. These tools are unavailable
after a secret fill. See the
[tool reference](/reference/agent#pixel-tools-screenshot-and-the-point-verbs).

The runner checks each built-in action and counts it against the budget.
A targeted action has a maximum timeout of 15 seconds. Secret fills also
require a declared secret and a compatible field.
[Project tools](/tools) add your own operations with declared budgets and
platform support.

The loop detects repeated calls and cycles. After three consecutive failed
actions, it asks the model to change approach; after five, it asks for a
verdict. It also requests a verdict as the budget or deadline approaches.

## How a step ends

An agent step returns one of three verdicts:

- `passed`: the screen provides evidence that the step succeeded.
- `failed`: the required condition is false or cannot be established.
  Insufficient evidence produces `ASSERTION_INCONCLUSIVE`.
- `blocked`: a prerequisite, environment problem, or execution limit
  prevented a product verdict. The error code determines the exit code.

| Blocked by | Codes | Exit |
| --- | --- | ---: |
| A credential the app rejected, or one that is not configured | `AUTH_CREDENTIAL_INVALID`, `AUTH_CREDENTIAL_UNAVAILABLE` | 2 |
| An environment that is down | `ENVIRONMENT_UNAVAILABLE` | 3 |
| Seed data or a prerequisite outside the product that is not there | `SEED_DATA_MISSING`, `TEST_SETUP_FAILED` | 2 |
| A budget or the clock | `STEP_BUDGET_EXHAUSTED`, `STEP_TIMEOUT` | 1 |
| An interaction the toolset cannot perform | `AUTOMATION_UNSUPPORTED` | 1 |

Configuration and infrastructure blocks exit 2 and 3 respectively. Budget
exhaustion, timeouts, and unsupported automation still count as test failures
and exit 1, even though the agent could not reach a product verdict.

## Cost

Defaults for the built-in agent:

| Call | Model calls | Default timeout |
| --- | --- | --- |
| `act` | up to `maxModelCalls`, default 25 | test `timeout`, 120 s |
| `assert` | 2 | the agent's `timeout`, 30 s |
| `extract` | 2 | the agent's `timeout`, 30 s |
| `waitFor` | up to `maxModelCalls`, default 25 | the agent's `timeout`, 30 s |

`assert` and `extract` make one judgment, with one repair call if needed.
`waitFor` skips model calls while the observation is unchanged, including
the screenshot when vision is enabled. Exceeding a budget raises
`STEP_BUDGET_EXHAUSTED`; reaching the deadline raises `STEP_TIMEOUT`.

`act` requests screenshots when needed. After the first screenshot, action
results include fresh pixels while policy allows them. Images add input
tokens on each call.

With a [custom executor](/executors), `agent.assert` uses `runStep` with the
same budgets as `act` and defaults to `config.timeout`.

Use `expect` for exact checks and keep each `act` focused on one goal.
The [trace cache](/cache) can replay passing `act` steps without model calls.

When the provider supports prompt caching, `--debug` shows the cached share
of input tokens per step.

## Where secrets go

For a `Secret` param, the model receives only its name and purpose. The
runner authorizes and fills the value, as it does for `locator.fill`.
The value never enters prompts, transcripts, reports, or AI traces.

After a secret fill, screenshots are withheld from the model and assertion
evidence for the rest of the attempt. The app could echo the value anywhere
on screen.
