A fixture is a value a test receives in its parameter list, set up before
the test and torn down after it. Define your own with `test.extend` to
create test data or start a service, with cleanup that runs even when the
test fails.

To sign in, use a [saved session](/authentication), not a fixture. A session
holds cookies and storage, not server data. Fixtures create that data.

## Define fixtures in one file

Put your fixtures in one file and export the extended `test` from it. Start
from your engine's `test`, so fixtures and tests can use `browser` or
`device`.

A fixture gets the same fixtures as a test, `agent` included. So it can
create its data through the app with `agent.act`, and needs no test API:

```ts title="tests/fixtures.ts" expandable
import { test as base } from '@e2e-dev/web';
import { expect, unique } from 'e2e';

export { expect };

/** A fresh project for each test, created and deleted through the app. */
export const test = base.extend<{ project: string }>({
  project: async ({ app, agent, screen }, use) => {
    const name = `Launch plan ${Date.now()}`;
    await app.open('/projects');
    await agent.act('create a project named {name}', { params: { name: unique(name) } });
    await expect(screen.getByRole('heading', name)).toBeVisible();
    await use(name);
    await app.open('/projects');
    await agent.act('delete the project {name}', { params: { name: unique(name) } });
    await expect(screen.getByRole('link', name)).toBeHidden();
  },
});

/** One task in that project. Deleting the project deletes it too. */
export const taskTest = test.extend<{ task: string }>({
  task: async ({ agent, screen }, use) => {
    const title = 'Write the announcement';
    await agent.act('add a task {title}', { params: { title } });
    await expect(screen.getByRole('checkbox', title)).toBeVisible();
    await use(title);
  },
});
```

Code before `await use(value)` is the setup. The test receives `value`. Code
after `use` is the teardown, and it runs after the test passes or fails.

Write fixture goals like goals in a test. Keep each one atomic and check it
with `expect`. Give a value that changes on each run with `unique()`, so the
[cache can replay the step](/cache#what-must-match). See
[Goals](/core-concepts#goals).

Import `test` and `expect` from this file in your test files. The saved
session is restored before the fixtures run, so they work signed in. The
test starts on the project page the fixtures left open:

```ts title="tests/tasks.e2e.ts"
import { expect, taskTest as test } from './fixtures.ts';

test('completes a task', { session: 'admin' }, async ({ screen, task }) => {
  await screen.getByRole('checkbox', task).check();
  await expect(screen.getByRole('checkbox', task)).toBeChecked();
});
```

The report lists the fixture's steps in phase `beforeEach` and `afterEach`.

<Note>
Every agent step in a fixture runs for every test that uses it. Where the
cache can't replay a step, it costs model calls each time. When your app
has a test API, a `fetch` call in the fixture is faster.
</Note>

## Build one fixture on another

A definition sees the fixtures of the `test` it extends, not the other
definitions in the same call. To use one fixture in another, extend in a
second call. Above, `task` runs after `project` because `taskTest` extends
`test`.

Setup runs in declaration order, after the engine's fixtures. Teardown runs
in reverse order: a fixture's teardown runs before the teardown of the
fixture it builds on.

## Give each setup its own test

Every fixture in a chain sets up for every test registered through it,
whether the test names the fixture or not. A test that needs no task
still creates one when it uses `taskTest`.

So export one `test` for each setup. In `tests/fixtures.ts`, `test` sets
up `project`, and `taskTest` sets up `project`, then `task`. For a test
that needs neither, import `test` from `@e2e-dev/web` directly.

## Read fixtures in hooks

Register hooks on your extended `test` to read its fixtures:

```ts
taskTest.beforeEach(async ({ screen, project }) => {
  await expect(screen.getByRole('heading', project)).toBeVisible();
});
```

The top-level `beforeEach` and `afterEach` exports from `e2e` and the engine
packages are typed with only the core and engine fixtures. At run time, a
hook reads the fixtures of the test it runs around. If that test was
registered through another `test` without `project`, the hook fails with
`UNSUPPORTED_CAPABILITY`.

## When a fixture fails

Setup counts against the test `timeout`. Each teardown gets its own
`cleanupTimeout`.

- An error before `use` fails the attempt in phase `beforeEach`. The hooks
  and the body don't run.
- An error after `use` fails a passing attempt in phase `afterEach`. After a
  failed body, it joins `secondaryErrors`.
- A definition that returns without calling `use`, or calls it twice, fails
  with `TEST_SETUP_FAILED`.

For name clashes and the rest, see the
[full list of mistakes](/reference/test#your-own-fixtures).

<Accordion title="Share one resource across a worker's tests">
A fixture runs per attempt. For work that only needs to happen one time per
worker, such as installing an app on a device, cache the promise on
`globalThis`. It lasts as long as the worker process. Clear it when the work
fails, so a retry can try again.

```ts
const INSTALLS = Symbol.for('my-suite.installs');

export const test = base.extend<{ build: undefined }>({
  build: async ({ device }, use) => {
    const holder = globalThis as { [INSTALLS]?: Promise<unknown> };
    holder[INSTALLS] ??= device.installApp().catch((error: unknown) => {
      delete holder[INSTALLS];
      throw error;
    });
    await holder[INSTALLS];
    await use(undefined);
  },
});
```

No hook runs when the worker stops, so keep this for work that needs no
cleanup.
</Accordion>
