`@e2e-dev/web` runs tests in a browser against your app's URL. This page
covers getting the app running for a run and testing it at different
sizes. For routes, cookies, dialogs, downloads, and the rest of the
`browser` fixture, see [Working with the browser](/browser).

## Starting your app

Set your app's URL in the target's `app`. If you also provide a start
command, the runner starts the app, waits until it is ready, and stops it
when the run ends.

### Point at a running app

Import `web` from `@e2e-dev/web` and put this in the exported
config object:

```ts title="e2e.config.ts"
export default {
  targets: [{
    engine: web(),
    app: { url: process.env.APP_URL ?? 'http://localhost:3000' },
  }],
} satisfies E2EConfig;
```

`app.open('/path')` resolves against `app.url`. This config reads `APP_URL`, so
you can change the address for a run without editing the file. URLs without
a scheme use HTTPS, or HTTP for loopback hosts.

### Let the runner start it

Add `app.command` and the runner spawns the dev server, waits until `app.url`
answers, and stops it when the run ends, fails, or is interrupted:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';

export default {
  agents: {
    default: {
      model: gateway('openai/gpt-6-luna-fast'),
      system: 'You are a thorough QA agent. Verify every outcome.',
    },
  },
  targets: [{
    engine: web(),
    app: {
      url: process.env.APP_URL ?? 'http://localhost:3000',
      command: {
        executable: 'npm',
        args: ['run', 'dev'],
        reuseExisting: true,
        log: '.e2e/logs/app.log',
      },
    },
  }],
} satisfies E2EConfig;
```

```text
 ✓ target "web" command ready 1.20s
```

The main command options are:

| Option | Purpose |
| --- | --- |
| `reuseExisting: true` | Use an already-running server locally. CI ignores this and reports `APP_ALREADY_RUNNING`. |
| `log` | Save the app's stdout and stderr to a project-relative file. Startup errors include the last 20 lines, with `command.env` values redacted. The log file itself is unredacted. |
| `env` | Environment variables for the app. The child inherits `PATH`, `HOME`, and the temp-directory variables, plus these. |
| `startupTimeout` | How long to wait for readiness, 60 seconds by default. |

To probe a health endpoint instead of the base URL, set `readyUrl` beside
`command`: `app: { url, command, readyUrl: 'http://localhost:3000/health' }`.

The command runs without a shell. `executable` is resolved on `PATH` and
`args` are passed as written. The child inherits only `PATH`, `HOME`, the
temp-directory variables, and `env`, so pass what the app needs explicitly.
See the
[command reference](/reference/config#command) for all options.

#### Let the runner pick the port

Use port `0` to run multiple checkouts without a port conflict. The runner
chooses a free port and replaces `{port}` in the command's `args` and `env`.
Your app command must use that value:

```ts
engine: web(),
app: {
  url: 'http://127.0.0.1:0',
  command: { executable: 'pnpm', args: ['dev', '--port', '{port}'], env: { PORT: '{port}' } },
},
```

Tests can read the allocated URL from `app.baseUrl`. Cache entries remain
valid when the port changes. Use `127.0.0.1` or `[::1]`, matching the address
the command binds; `localhost:0` is rejected. See
[free ports](/reference/config#free-ports) for details.

#### Next.js dev targets

Next.js 16 blocks cross-origin requests to its dev resources. A target that
opens `127.0.0.1` or `[::1]` while `next dev` identifies as `localhost`
renders and never hydrates. Locators resolve and clicks land, but no React
handler runs, so the test fails and every retry fails the same way.

Add the host the target opens to `allowedDevOrigins`:

```ts title="next.config.ts"
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  allowedDevOrigins: ['127.0.0.1'],
};

export default nextConfig;
```

Use `'[::1]'` in the list when `app.url` opens `http://[::1]:0`.

A target on `localhost` needs no entry, because `next dev` identifies as
`localhost`. A production `next start` target is unaffected either way.

### Dependencies

<Note>
This version starts only `app.command` (one process for every target that
declares the same command). Databases, mocks, and other processes the app
needs are not started by the runner yet: bring them up before the run, or
have `app.command` start a script that brings them up and serves the app. A
services API returns in a later release.
</Note>

### Several targets

Two browsers on one app are two targets that each name it:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';

const app = { url: 'http://localhost:3000' };

export default {
  targets: [
    { name: 'chromium', engine: web(), app },
    { name: 'webkit-mobile', engine: web({ browser: 'webkit', viewport: { width: 390, height: 844 } }), app },
  ],
} satisfies E2EConfig;
```

Two targets that declare the same `app.command` share one process. Every
test runs on every target unless it is scoped with `platforms` or
`requires`; `--target <name>` selects at run time. A device target sits
beside a browser target in the same list; see the
[Mobile engine reference](/reference/mobile). One target per screen size is
how a suite runs at several [viewports](#viewports).

### Protected previews

Use `headers` to access protected previews or skip a tunnel's interstitial
page. For example, a Vercel preview can use a protection bypass header:

```ts title="Target fragment"
engine: web({
  headers: {
    'x-vercel-protection-bypass': process.env.VERCEL_AUTOMATION_BYPASS_SECRET ?? '',
  },
}),
app: {
  url: process.env.PREVIEW_URL ?? 'http://localhost:3000',
  identity: 'storefront',
},
```

`headers` apply to requests on the target's site, determined by its hostname.
The check also includes subdomains and treats shared suffixes such as
`vercel.app` as one site. See [header scope](/reference/security#site-check)
before using a bypass secret. For ngrok, use
`'ngrok-skip-browser-warning': '1'`.

`app.identity` gives the app a stable cache identity when its preview URL changes.

Use `basicAuth` for HTTP basic authentication. The browser sends these
credentials when any origin requests them with a `401` challenge:

```ts title="Target fragment"
engine: web({
  basicAuth: { username: 'preview', password: process.env.PREVIEW_PASSWORD ?? '' },
}),
app: { url: 'https://staging.example.com' },
```

To keep the password out of reports, logs, and what the agent reads, declare
it under `secrets` and pass `secrets.get(name)`. The engine resolves it when
each attempt starts, and the runner redacts it like any configured secret; a
name that `secrets` does not declare fails the config load with `INVALID_CONFIG`:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { secrets } from 'e2e';
import { web } from '@e2e-dev/web';

export default {
  targets: [
    {
      engine: web({
        basicAuth: { username: 'preview', password: secrets.get('previewPassword') },
      }),
      app: { url: 'https://staging.example.com' },
    },
  ],
  secrets: { previewPassword: () => process.env.PREVIEW_PASSWORD ?? '' },
} satisfies E2EConfig;
```

<Note>
Setting `headers` disables the browser's HTTP cache and blocks service
workers.
</Note>

## Viewports

Set a viewport on the target to run a suite at that size. Use
`browser.setViewport()` to resize during a test. The agent uses the current size
and cannot resize it.

### One size per target

`viewport` sets the initial size of each attempt, in pixels. The default is
1280 by 720. Add one target for each size you want to test:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';

const app = { url: 'http://localhost:3000' };

export default {
  targets: [
    { name: 'desktop', engine: web(), app },
    { name: 'tablet', engine: web({ viewport: { width: 820, height: 1180 } }), app },
    { name: 'phone', engine: web({ browser: 'webkit', viewport: { width: 390, height: 844 } }), app },
  ],
} satisfies E2EConfig;
```

Each test runs once per target, with a separate result labeled `desktop`,
`tablet`, or `phone`. Run one size with `npx e2e run --target phone`, or list
the selected test-target pairs with `npx e2e list`.

To have the runner start one dev server for every size, give every target
the same `app.command`: targets declaring one command share one process; see
[several targets](#several-targets). Every retry starts at
the target's configured size.

### Fill the window

`viewport: null` sets no size, so the page fills the browser window. The
agent, screenshots, and videos use that size. Use it in a headed run, or
with a hosted browser whose live view would show a fixed 1280 by 720 page
in one corner:

```ts title="e2e.config.ts"
{ name: 'window', engine: web({ viewport: null }), app }
```

The page takes the window's size, minus the toolbar in a headed browser. A
local headed launch opens a small window; a hosted browser uses the window
size you requested from the service. `browser.setViewport` still works.

### Resize inside a test

`browser.setViewport` resizes the page for the rest of the attempt, through
`app.restart()` and `app.clearState()`:

```ts
import { test } from '@e2e-dev/web';
import { expect } from 'e2e';

test('the menu collapses on a narrow screen', async ({ app, screen, browser }) => {
  await app.open('/');
  await expect(screen.getByRole('navigation')).toBeVisible();

  await browser.setViewport({ width: 390, height: 844 });
  await expect(screen.getByRole('button', 'Menu')).toBeVisible();
  await expect(screen.getByRole('navigation')).toBeHidden();
});
```

Use this when one test needs to check a layout before and after resizing.
For a whole suite, configure separate targets instead.

Call it before `app.open` to load the first page at that size, so the app
never renders its desktop layout first:

```ts
await browser.setViewport({ width: 390, height: 844 });
await app.open('/');
```

The resize appears as a step in the report. To check the exact width, read
it from the page:

```ts
const width = await browser.evaluate(() => window.innerWidth);
expect(width).toBe(390);
```

### What the agent sees

The agent receives the current viewport size with each observation.
Screenshots cover that viewport. Off-screen elements can still appear in
the tree, and tapping them scrolls them into view. The agent can scroll to
reveal lazy-loaded content.

A sentence that contains a link, bold or italic text, or code reaches the
agent whole, as it reads on screen, and the link is also listed as a
control the agent can tap. The agent reads the first 512 characters of each
block of text; in a longer one, the links and emphasized text are also
listed on their own.

Resize before calling `agent.act`:

```ts
test('the mobile menu reaches pricing', async ({ app, agent, browser }) => {
  await browser.setViewport({ width: 390, height: 844 });
  await app.open('/');
  await agent.act('open the navigation menu and go to Pricing');
  await expect(browser).toHaveURL('/pricing');
});
```

### Scoping a test to one size

`platforms` and `requires` cannot select a viewport; all Playwright targets
use platform `web`. To skip a test at some sizes, check the width in the
test:

```ts
test('the sidebar stays open', async ({ app, screen, browser }) => {
  await app.open('/');
  test.skip((await browser.evaluate(() => window.innerWidth)) < 768, 'desktop layout only');
  await expect(screen.getByRole('complementary')).toBeVisible();
});
```

To keep a whole group of size-specific tests apart, give them their own
config and run it with `--config`.

### Limits

A narrow viewport tests responsive layout. It still uses a desktop browser
with a scale factor of 1, desktop pointer behavior, and its usual user agent.
It does not emulate touch, color scheme, or reduced-motion preferences.
Use the [device engine](/mobile) for tests on a simulator or emulator.

A video keeps the size the page had when it started recording; set
`web({ screencast: { size } })` for one fixed size. A browser provider that
records, such as [Kernel](/integrations/kernel#recordings), records the whole
screen instead.
