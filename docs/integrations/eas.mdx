`easSimulators()` from `@e2e-dev/eas` is a
[device provider](/mobile#hosted-devices) for
[EAS Simulators](https://expo.dev/services/simulators). The run gets hosted
iOS simulators or Android emulators, started when it starts and stopped when
it ends, and the engine drives them through the agent-device daemon EAS runs
beside each one. No Mac, Xcode, or Android SDK on the machine that
runs `e2e`. Tests, config, and CI stay the same.

## Setup

```bash
npm install --save-dev @e2e-dev/eas
```

EAS Simulators is in limited access; check yours with
`npx eas-cli@latest simulator:availability`.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';
import { easSimulators } from '@e2e-dev/eas';

export default {
  targets: [
    {
      name: 'ios',
      engine: mobile({
        platform: 'ios',
        app: 'com.example.app',
        device: easSimulators({
          projectId: '<your-expo-project-id>',
          buildId: process.env.EAS_BUILD_ID,
        }),
        videoTouches: false,
      }),
    },
  ],
  workers: 2,
} satisfies E2EConfig;
```

`projectId` is the Expo project's id, `extra.eas.projectId` in the app
config, not its slug. Set `EXPO_TOKEN`, an
[access token](https://expo.dev/settings/access-tokens) of an account or robot
with access to the project, in the environment `e2e run` starts in, such as a
CI secret. The package calls Expo's API with `fetch`, so there is no SDK to
install.

## Install the app

The simulator boots with no apps. Pick one way to put yours on it:

- **An EAS Build**: `buildId` names a simulator build (`"ios": { "simulator": true }`
  in `eas.json`) or an APK, and EAS installs and launches it before the
  session is ready. Leave the engine's `appPath` out, and keep `app` so
  `app.open()` knows what to launch. The build never leaves EAS.
- **A URL**: `applicationArchiveUrl` names an app archive EAS downloads and
  installs the same way.
- **A local build**: the engine's `appPath` and a fixture that calls
  `device.installApp()`, as with a [local simulator](/mobile). The build
  uploads through the session's daemon to each simulator. Leave `buildId`
  and `applicationArchiveUrl` out.

```ts
// EAS installs the build.
mobile({ platform: 'ios', app: 'com.example.app', device: easSimulators({ projectId, buildId }) })

// A fixture uploads the build with device.installApp().
mobile({ platform: 'ios', app: 'com.example.app', appPath: 'build/App.app', device: easSimulators({ projectId }) })
```

## Options

| Option                  | Default     | Meaning |
| ----------------------- | ----------- | ------- |
| `projectId`             | required    | The Expo project the sessions belong to. |
| `buildId`               | none        | EAS Build EAS installs and launches on every simulator. |
| `applicationArchiveUrl` | none        | App archive URL EAS installs in place of a build. Excludes `buildId`. |
| `device`                | EAS's pick  | iOS device name or UDID (`'iPhone 17 Pro'`), or an Android AVD hardware profile (`'pixel_9'`). |
| `maxIdleTimeMinutes`    | `10`        | Minutes without an agent-device command after which EAS stops the session. EAS wants it below `maxDurationMinutes`, so a shorter duration lowers the default to one less. See [What the provider does](#what-the-provider-does). |
| `maxDurationMinutes`    | account cap | Minutes a session may run once ready. EAS caps it at 40, or 115 on a high-priority plan. |
| `agentDeviceVersion`    | the engine's | The agent-device version EAS starts the session's daemon at. Defaults to the one `@e2e-dev/mobile` pins, so the remote daemon answers as the engine's client expects; without it EAS starts the latest. |
| `tags`                  | `[]`        | Tags on every session, beside the run's own. |

An option not in this table, `buildId` and `applicationArchiveUrl` together, or
a `maxIdleTimeMinutes` not below a `maxDurationMinutes` passed with it fails the
config load with `INVALID_CONFIG`.

## Sessions

Each target starts up to `workers` sessions (`--workers` overrides it),
fewer when it has fewer test files, and tests start once all are ready.
A session takes about three minutes from request to ready (queue, boot,
build install), all in parallel, before the run's clock starts.

A run must fit in one session's lifetime: EAS stops a session
`maxDurationMinutes` after it is ready, 40 minutes by default on a
normal-priority plan and 115 on a high-priority one. Split a longer suite
across more workers or across CI jobs.

EAS runs as many sessions at once as the Expo account allows, and queues
the rest until one ends. None ends before the run does, so keep `workers`
times the number of EAS targets within that number. Every session queues
for a few seconds; one still queued after two minutes logs `still queued at
EAS after two minutes`. Targets prepare one after another, so the sessions of a target
that is ready wait idle while the next target's queue and boot. A session
still queued once another session of the run has been ready for
`maxIdleTimeMinutes` fails the lease, and the run stops every session: EAS
is stopping the idle one.

## Watch a run

The provider logs each session's expo.dev page as it is created:

```text
ℹ leasing 2 ios device(s) from eas-simulators
ℹ eas-simulators (1 of 2): simulator session 01a0…, https://expo.dev/accounts/acme/projects/shop/simulator-sessions/01a0…
ℹ eas-simulators: leased 01a0…
```

A browser preview that opens without a token is logged too, as
`watch at <url>`. A preview that needs one is not: the token would give
anyone who reads the CI log control of the simulator.

Sessions are named `e2e <target> <n> of <total>` and tagged `e2e`,
`e2e-run:<run id>`, and `e2e-target:<target>`, so
`eas simulator:list --tag e2e-run:<run id>` finds a run's sessions.

## Recordings

An attempt that records [video](/reference/config#video) records through
agent-device on the simulator, as it does locally, and saves
`video/video.mp4` under the attempt's artifact directory.

Set the mobile engine's `videoTouches: false`, as the setup above does.
agent-device draws its touch indicator into a recording when the recording
stops, and on an EAS iOS simulator that takes minutes, so every attempt that
records video runs out its `cleanupTimeout` stopping it and keeps no file.
Without the indicator, stopping takes about two seconds.

## What the provider does

- Starts each `agent-device` session and waits until its daemon is
  reachable, then hands the engine the daemon's URL and token.
- Defaults `maxIdleTimeMinutes` to 10. A run that dies before the engine
  stops its sessions leaves them idle, and EAS stops them after that long.
- Starts each daemon at the agent-device version `@e2e-dev/mobile` pins.
- Stops a session that errors, is cancelled, stays queued while another
  session of the run idles to `maxIdleTimeMinutes`, or is still booting 15
  minutes after leaving the queue, and treats one EAS no longer knows as
  already stopped.
- Cancels the job of a session it stops while the job is still queued:
  EAS would otherwise start it later and count it against the account's
  concurrent sessions.
- Rides out up to three failed status polls in a row, a blip at
  api.expo.dev, before giving a session up.

A missing `EXPO_TOKEN`, an account without EAS Simulators, or a session that
fails to start fails the lease with EAS's message. That ends the run before
any test, and the run's other sessions, started or queued, are still stopped.
