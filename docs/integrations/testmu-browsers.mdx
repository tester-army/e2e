`testmuBrowsers()` from `@e2e-dev/testmu/web` is a
[browser provider](/browser#hosted-browsers) for
[TestMu AI](https://www.lambdatest.com) (formerly LambdaTest). Each worker
slot gets its own hosted Chrome or Edge session for the run. Tests stay the
same. Only the target's `browser` changes.

## Setup

Install the integration alongside the web engine:

<CodeGroup>
```bash npm
npm install --save-dev e2e @e2e-dev/web @e2e-dev/testmu
```

```bash pnpm
pnpm add -D e2e @e2e-dev/web @e2e-dev/testmu
```

```bash bun
bun add -d e2e @e2e-dev/web @e2e-dev/testmu
```
</CodeGroup>

Set the target's `browser` to `testmuBrowsers()`:

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { testmuBrowsers } from '@e2e-dev/testmu/web';

export default {
  targets: [
    {
      name: 'testmu-web',
      engine: web({ browser: testmuBrowsers(), viewport: null }),
      app: { url: 'https://staging.example.com' },
    },
  ],
} satisfies E2EConfig;
```

Set `LT_USERNAME` and `LT_ACCESS_KEY` in the environment that `e2e run`
starts in, such as CI secrets. Copy them from **Account Settings → Password
& Security → Username and Access Key**
([accounts.lambdatest.com/security/username-accesskey](https://accounts.lambdatest.com/security/username-accesskey)).
They travel only in each session's CDP URL, never in a log line. Without
them the lease fails, and the run ends before any test.

Every attempt gets a new browser context in its worker's session, as in a
local run, so a test never sees another test's cookies, storage, or
permissions. The dashboard shows one session per worker slot, named
`e2e-<run id>-<target>-<slot>`, in a build named after the run id.

## Options

| Option | Default | Meaning |
| ------ | ------- | ------- |
| `browserName` | `'Chrome'` | `'Chrome'` or `'MicrosoftEdge'`. The web engine attaches over CDP, so any other browser fails the config. |
| `capabilities` | none | `browserVersion`, sent next to `browserName`, and TestMu AI's `LT:Options` fields, such as `platform`, `geoLocation`, `timezone`, `video`, `network`, or `tunnel` and `tunnelName` for [TestMu AI Tunnel](https://www.lambdatest.com/support/docs/testing-locally-hosted-pages/). |

The provider sends `platform` (`Windows 11`, since TestMu AI refuses a
session without one), `build` (the run id), `project` (`e2e`), and
`idleTimeout` (600 seconds) unless `capabilities` sets them. Edge sessions get
`--user-data-dir=remote-debug-profile-edge` in `browserOptions` unless
`capabilities` set one. It sets `user`, `accessKey`, and `name` itself, so
`capabilities` that set any of them fail the config with `INVALID_CONFIG`.
So do a nested `LT:Options`, a `browserName` (use the option), a value JSON
cannot carry, and a misspelled option.

```ts
testmuBrowsers({
  browserName: 'MicrosoftEdge',
  capabilities: { browserVersion: '140', platform: 'Windows 10', build: `checkout ${process.env.GITHUB_SHA}`, video: true },
})
```

## Limits

- **Parallel sessions.** `workers` sets how many sessions run at once. Keep
  it within your TestMu AI plan: a session beyond it waits in TestMu AI's
  queue.
- **60-second connect.** The web engine waits at most 60 seconds for a
  session to accept the CDP connection. A shorter `launchTimeout` ends the
  wait sooner, but a longer one does not extend it. A session still queued
  or provisioning after that fails with `LAUNCH_TIMEOUT`.
- **Dropped connections.** A session cannot be resumed, so a dropped
  connection fails the attempt.

## Recordings

TestMu AI records the session's screen when you pass
`capabilities: { video: true }`; watch it in the TestMu AI dashboard. An
attempt that records [video](/reference/config#video) gets the web engine's
screencast of the page, as a local run does.

## Downloads

TestMu AI's browsers save downloads on their own machines, so
`browser.waitForDownload` fails with `ENGINE_FAILURE`. Assert on the
download link or the request instead.
