In an EAS workflow, a `build` job makes the simulator `.app` or the `.apk`.
A custom job then downloads the build, boots a device, and runs the suite.
Before you start, read [Mobile jobs](/ci#mobile-jobs). That section tells
you what each job needs on every CI service.

<Note>
This page is about EAS Workflows, the CI service. To run tests on hosted
simulators and emulators from EAS, see [EAS Simulators](/integrations/eas).
</Note>

## Build profile

Add a build profile that needs no credentials:

```json title="eas.json"
{
  "build": {
    "e2e": {
      "withoutCredentials": true,
      "ios": { "simulator": true },
      "android": { "buildType": "apk" }
    }
  }
}
```

## Workflow

The iOS job runs on a macOS runner. The Android job needs a
`nested-virtualization` Linux runner. Only these EAS machines can run the
emulator.

```yaml title=".eas/workflows/e2e.yml" expandable
name: e2e

on:
  pull_request:
    branches: ['*']
  push:
    branches: [main]

defaults:
  tools:
    node: '22'

jobs:
  build_ios:
    type: build
    params:
      platform: ios
      profile: e2e

  build_android:
    type: build
    params:
      platform: android
      profile: e2e

  e2e_ios:
    needs: [build_ios]
    runs_on: macos-medium
    environment: preview
    env:
      CI: '1'
    steps:
      - uses: eas/checkout
      - uses: eas/install_node_modules
      - uses: eas/download_build
        id: download_build
        with:
          build_id: ${{ needs.build_ios.outputs.build_id }}
          extensions: [app]
      - name: Boot a simulator and install the app
        run: |
          UDID=$(xcrun simctl create e2e "iPhone 17" com.apple.CoreSimulator.SimRuntime.iOS-26-5)
          xcrun simctl bootstatus "$UDID" -b
          xcrun simctl install "$UDID" "${{ steps.download_build.outputs.artifact_path }}"
      - name: Run e2e
        run: npx e2e run --target ios --reporter list,junit
      - uses: eas/upload_artifact
        if: ${{ always() }}
        with:
          type: other
          name: e2e-ios
          path: .e2e

  e2e_android:
    needs: [build_android]
    runs_on: linux-medium-nested-virtualization
    environment: preview
    env:
      CI: '1'
    steps:
      - uses: eas/checkout
      - uses: eas/install_node_modules
      - uses: eas/download_build
        id: download_build
        with:
          build_id: ${{ needs.build_android.outputs.build_id }}
          extensions: [apk]
      - uses: eas/start_android_emulator
        with:
          system_image_package: system-images;android-35;google_apis;x86_64
      - name: Install the app
        run: adb install -r "${{ steps.download_build.outputs.artifact_path }}"
      - name: Run e2e
        run: npx e2e run --target android --reporter list,junit
      - uses: eas/upload_artifact
        if: ${{ always() }}
        with:
          type: other
          name: e2e-android
          path: .e2e
```

## Notes

- **Secrets.** Keep `AI_GATEWAY_API_KEY` (or the key of your provider) in an
  [EAS environment variable](https://docs.expo.dev/eas/environment-variables/)
  with secret visibility. `environment:` sets the EAS environment that a job
  reads. Set it in each job, because a custom job reads `production` by
  default. Each job that reads the environment can read the key, including
  a job that runs the code of an untrusted pull request. Give the key only
  to builds of branches that you trust. See [Mobile jobs](/ci#mobile-jobs).
- **CI mode.** `CI: '1'` turns on the [CI defaults](/ci#what-ci-changes),
  also on a runner that does not set it.
- **Emulator function.** `eas/start_android_emulator` is an EAS build
  function. Its documentation is under
  [custom builds](https://docs.expo.dev/custom-builds/schema/), not on the
  Workflows syntax page. It downloads the system image that you name with
  `sdkmanager`. The iOS job creates its simulator with `xcrun simctl` to pin
  the runtime.
- **Fewer builds.** A `fingerprint` job with `get-build` and `repack` reuses
  the last native build and bundles only the JavaScript. The
  [agent-device EAS template](https://github.com/callstackincubator/eas-agent-device/blob/main/.eas/workflows/agent-qa-mobile.yml)
  does this for the two platforms.

EAS Workflows also has a built-in `maestro` job type. That job boots the
device and runs Maestro flows. For e2e, use a custom job, as above.
