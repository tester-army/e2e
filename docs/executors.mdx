Use a custom executor when a `system` prompt and [project tools](/tools) are
not enough. There are two options:

1. `createToolLoopExecutor` keeps the built-in loop: budgets, repeated-call
   detection, verdicts, usage accounting, and debug transcripts. Your tools
   replace the built-in actions; the loop adds only `complete_step`.
2. `StepExecutor` lets you implement `runStep(ctx)` yourself. A model and
   the AI SDK are optional; the `e2e` and `e2e/engine` types compile with no
   `ai` package installed.

Both receive a deadline, redacted observations, and checked action methods.
For a provider that returns bounded choices instead of generated text, see
the [Clef and Jev decision executor](/decision-models).
The runner records their verdicts. Either goes under `executor` in an agents
entry, beside the options that still apply: `model`, `judge`, `context`, and
the budgets. An entry with `executor` rejects `system` and `tools`; pass
them to `createToolLoopExecutor` instead.

## Keep the loop, change the vocabulary

This example gives the agent two tools: one reads the screen, one taps a
node by its id.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { createToolLoopExecutor } from 'e2e/agent';
import { web } from '@e2e-dev/web';
import { gateway, tool } from 'ai';
import { z } from 'zod';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  agents: {
    default: {
      model: gateway('openai/gpt-6-luna-fast'),
      maxModelCalls: 15,
      executor: createToolLoopExecutor({
        name: 'tap-only',
        system: 'Read the screen before acting. Tap controls by their id from the latest read.',
        buildPrompt: (ctx) => ctx.step.instruction,
        tools: (ctx, { guard }) => ({
          read_screen: tool({
            description: 'Read the screen as text, one node per line as #id role "name"',
            inputSchema: z.object({}),
            execute: () => guard(async () => (await ctx.observe()).text),
          }),
          tap: tool({
            description: 'Tap a node by its id from the latest read_screen',
            inputSchema: z.object({ id: z.string() }),
            execute: ({ id }) =>
              guard(async () => {
                await ctx.actions.tap({ id: id.replace(/^#/, '') });
                return `Tapped ${id}.`;
              }),
          }),
        }),
      }),
    },
  },
} satisfies E2EConfig;
```

The loop reads the entry's `model` unless `createToolLoopExecutor({ model })`
brings its own, and its model turns per step are the entry's `maxModelCalls`.
`buildPrompt` returns a string or message history. Use `prepareMessages`
between turns to shorten the history or return `{ messages, stop }` when
the step is not progressing.

`guard()` stops new tool calls once the step is concluding and hands a
failure back to the model as text. `ctx.actions` authorizes, counts, and
records each action, so these steps replay from the [cache](/cache) like the
built-in agent's and run on any engine that supports `tap`.

A tool that works outside `ctx.actions`, such as a call to your test API,
wraps its body in `ctx.budgets.runTool({ name, mutates })` to take an action
slot and record the outcome. Never call `ctx.actions` or `ctx.observe` inside
`runTool`: the call queues behind its own operation and deadlocks. Keep tool
bodies short and support cancellation. The step deadline cannot cancel an
underlying operation that ignores its signal.

A custom executor can bring its own `model` or `judge`, as
`createToolLoopExecutor({ model })` does. If the agents entry sets one too,
they must name the same provider and model, or the config load fails with
`INVALID_CONFIG`.

## Replace the executor

This model-free executor supports one assertion,
`agent.assert('the screen says Ready')`. Other instructions return a blocked
verdict so the executor cannot claim to have checked something it does not
understand.

```ts title="e2e.config.ts"
import type { E2EConfig, StepExecutor } from 'e2e';
import { web } from '@e2e-dev/web';

const scripted: StepExecutor = {
  name: 'scripted',
  version: '1',
  cache: 'off',
  async runStep(ctx) {
    if (ctx.step.kind !== 'assert' || ctx.step.instruction !== 'the screen says Ready') {
      return {
        status: 'blocked',
        errorCode: 'AUTOMATION_UNSUPPORTED',
        summary: 'This executor only checks whether the screen says Ready.',
      };
    }
    const screen = await ctx.observe();
    const ready = screen.text.includes('Ready');
    return {
      status: ready ? 'passed' : 'failed',
      summary: ready ? 'The screen says Ready.' : 'Ready is absent from the screen.',
    };
  },
};

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  agents: { default: { executor: scripted } },
} satisfies E2EConfig;
```

The executor receives this context:

| Member | What it is |
| --- | --- |
| `ctx.step` | The instruction, params, and `index` in the attempt's timeline. A registered secret value the test spelled into the instruction or a param string reads `<secret:name>`; a `secrets.get()` handle is a placeholder you fill with `typeSecret` |
| `ctx.observe({ tree, pixels })` | Redacted screen text, with an optional node tree and masked screenshot |
| `ctx.actions` | Checked and recorded actions: `tap`, `doubleTap`, `longPress`, `secondaryTap`, `hover`, `type`, `typeSecret`, `press`, `select`, `check`, `drag`, `scrollTo`, `scrollUntil`, `upload`, `scroll`, `navigate`, `back`, and the point and keyboard verbs below |
| `ctx.target` | The target's `name` and `platform`, and `verbs`, the actions its engine supports. Offer only these to the model. |
| `ctx.pixelsTainted` | True after a [secret fill](/reference/security#screenshots-after-a-secret-fill), when no screenshots are available. A secret an engine option holds (a basic-auth password) is redacted from text only and does not set it |
| `ctx.signal` | Aborts on cancellation, at the step deadline, or on any other hard stop. Stop promptly when it fires |
| `ctx.replayedPrefix` | Set when a cache replay ran part of the step before handing it over: the replayed actions and why replay stopped |
| `ctx.model`, `ctx.providerOptions` | The agent's configured model and `providerOptions`, when set |
| `ctx.agentContext` | The agent's `context` plus the test's `agentContext` |
| `ctx.ledger` | Completed steps in the test |
| `ctx.attempt` | Test and attempt ids, retry index, abort signal, and a `memory` map that is never reported |
| `ctx.budgets` | Accounting for custom tools and model calls |
| `ctx.attachTranscript(text)` | Attaches the model transcript to the step. Kept as a `log` artifact under `--debug`, a no-op otherwise; call once, at conclusion |
| `ctx.attachTurns(turns)` | Keeps a clipped record of the step's model turns (`{ index, calls, outcome }`) on the step record whatever the debug setting; the report shows the last ones under a failed step |
| `ctx.attachScreenshot(pixels, label)` | Keeps observed pixels as a `screenshot` artifact of the step and resolves with its report id |

`tapAt(point)` and `hoverAt(point)` use a node id when a listed control
occupies the point and otherwise call the engine's coordinate action.
`hitTest(point)` finds the listed control without acting. Keyboard-capable
engines also provide `typeText`, `pressKey`, and `dismissKeyboard` for the
focused control. `upload(target, paths)` authorizes every path against the
project root before the engine sees it: outside the project or hidden is
`POLICY_DENIED`, a missing file `INVALID_ARGUMENT`.

If semantic capture fails, an observation sets `treeUnavailable: true` and
omits `tree`. It includes a screenshot when policy allows one, even if pixels
were not requested. Earlier node ids are invalid, and a missing tree does
not prove a control is absent. Use fresh ids once the tree returns.

Secrets in params arrive as name-only placeholders.
`ctx.actions.typeSecret(target, name)` fills an authorized field without
passing the plaintext through your executor.

### What the executor handles

A custom executor handles `act` and `assert` through `runStep`. Both use the
agent's `maxSteps` and `maxModelCalls` and default to the configured
`timeout`. On `assert`, `vision` reaches `runStep` as `ctx.step.vision` only
when the executor declares `vision: true`; otherwise it raises
`UNSUPPORTED_CAPABILITY`, since your executor chooses what it observes.
`screenshot` still attaches evidence after your verdict.

`waitFor` and `extract` still use the built-in judgments. They require a
configured model and raise `MODEL_UNAVAILABLE` without one.

### Driving the page yourself

Use `surfaceOf(handle)` from `@e2e-dev/web` to access the current
attempt's `Page` and `BrowserContext`. Both accessors throw `INVALID_STATE`
outside an active attempt.

```ts
import type { E2EConfig, StepExecutor } from 'e2e';
import { web, surfaceOf } from '@e2e-dev/web';

const engine = web();
const own: StepExecutor = {
  name: 'own-tools',
  version: '1',
  cache: 'off',
  async runStep(ctx) {
    const page = surfaceOf(engine)!.page();   // the page app.open() navigated
    await ctx.budgets.runTool({ name: 'click', mutates: true }, () =>
      page.getByRole('button', { name: 'Save' }).click(),
    );
    return { status: 'passed', summary: 'saved' };
  },
};

export default {
  targets: [{ engine, app: { url: 'http://localhost:3000' } }],
  agents: { default: { executor: own } },
} satisfies E2EConfig;
```

Direct Playwright calls bypass the runner's action authorization and the
replay cache. The runner still enforces the step deadline and records the
verdict, but these calls have no automatic replay or artifacts. Use
`ctx.budgets` to count custom tool and model calls.

### Replay cache

`cache` on a `StepExecutor` sets how its `act` steps use the
[replay cache](/cache); `assert` steps are never cached. `'inherit'`, the
default, follows the configured cache mode. A recorded step replays without
calling `runStep`. A replay that stops partway calls `runStep` with
`ctx.replayedPrefix`: continue from the current screen and do not redo the
replayed actions. What a step does through `ctx.actions` is recorded; a
mutating tool call leaves a gap the executor fills on replay. Entries are
keyed by the configured agent and its context, so an entry one agent
recorded never replays for another; the executor itself is not part of the
key, so changing an agent's executor keeps its entries.

`'off'` never replays or records the executor's steps, so every step reaches
`runStep`. Use it for a brain whose own history or memory is the source of
truth, or one that must see every step run. The two `StepExecutor` samples on
this page set it so their code runs on every call.

## The verdict

Return `passed`, `failed`, or `blocked` with a summary. A blocked verdict
also needs an error code, and a passed one carries none.
[How agent steps work](/agent-steps#how-a-step-ends) lists the codes and
resulting exits. `STEP_BUDGET_EXHAUSTED`, `STEP_TIMEOUT`, and `CANCELLED`
belong to the runner: return one only when that budget is spent, the step
deadline has passed, or the test was cancelled. Returning one otherwise, or
a passed verdict with any code, is refused with `MODEL_OUTPUT_INVALID`.
