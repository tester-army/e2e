---
title: Pull request comments
description: The @e2edev/github reporter posts one comment per run from GitHub Actions and keeps it current.
---

A run that fails in CI is a red check and a log to open. `@e2edev/github` is
a [reporter](/reference/reporters) that turns it into one pull request
comment: the counts, every test that did not pass with its error and
evidence, and links to the source lines and to the workflow run holding the
screenshots, traces, and recordings. A rerun edits the same comment. The same
text goes to the job summary, so it is there on a push too.

## Setup

```bash
npm install --save-dev @e2edev/github
```

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { playwright } from '@e2edev/playwright';
import { github } from '@e2edev/github';

export default {
  targets: [{ engine: playwright({ url: 'http://localhost:3000' }) }],
  reporters: ['list', github()],
} satisfies E2EConfig;
```

Two lines in the workflow: the job may write pull request comments, and the
step that runs `e2e` gets the token.

```yaml title=".github/workflows/e2e.yml"
permissions:
  contents: read
  pull-requests: write

jobs:
  e2e:
    steps:
      # ...checkout, install, browsers
      - name: Run e2e
        run: npx e2e run --reporter list,junit
        env:
          GITHUB_TOKEN: ${{ github.token }}
      - name: Upload artifacts
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1
        with:
          name: e2e-artifacts
          path: .e2e/artifacts
```

Upload the artifacts on every non-cancelled outcome. The comment links to
the workflow run as the place to fetch them, and a flaky test that passed
on its second attempt can still leave evidence worth inspecting.

## The comment

```markdown
### 🔴 e2e: 1 failed, 1 flaky, 3 passed, 1 skipped
9 agent steps · 4 replayed from cache · 31 model calls · 128k tokens (62% cached) · $0.31

**🔴 billing › upgrades to Pro**

**ASSERTION_FAILED** at step 4 of 6: `agent.act` "Pick the Pro plan and pay", after 38.0s and 12 model calls

> expected heading "Your cart" to be visible
> The Pay button opened a page that still shows the Free plan.

- Turn 9: `tap({"target":"n41"})` → Screen changed: /checkout/plan. New: #n50 heading "Free plan"
- Screen: `/checkout/plan`

[tests/billing.e2e.ts:12](https://github.com/acme/shop/blob/1a2b3c/tests/billing.e2e.ts#L12) · Evidence: [screenshot, video, trace](https://github.com/acme/shop/actions/runs/123)

<details>
<summary>⚠️ 1 flaky test passed on a retry</summary>

**⚠️ invite a member by email**

**STEP_TIMEOUT** at step 3 of 3: `agent.waitFor` "the invitation email", after 30.0s

> the invitation email took too long

[tests/team.e2e.ts:21](https://github.com/acme/shop/blob/1a2b3c/tests/team.e2e.ts#L21) · Evidence: [screenshot, trace](https://github.com/acme/shop/actions/runs/123)
</details>

<details>
<summary>All 6 tests in 5 files</summary>

**tests/billing.e2e.ts** · 1 failed · 3 steps · 19 calls · 41.2s
- 🔴 billing › upgrades to Pro (41.2s)
...
</details>

<sub>e2e 0.13.0 · 2m 15s · web · [run artifacts](https://github.com/acme/shop/actions/runs/123)</sub>
```

The headline carries the counts; the line under it what the run spent, when
it used the agent: agent steps, how many the trace cache replayed, model
calls, tokens with the share the provider served from its prompt cache, and
the estimated cost. Each test that failed gets a block in short paragraphs:
one lead naming the error and the step it went wrong at; what the error and
the agent said, quoted; the facts as a list (expected and observed, whether
every attempt failed alike, the last model turns, the screen at failure,
where a loopback URL shows as its path since nobody reading the comment can
open it); then a link to the line in the test file at the pull request's
head commit (a test declared through a project helper that wraps `test()`
links to the helper call, not into the helper) and the evidence. The steps
before the failed one are not retold: the trace has them. A locator step's
label reads as code, an agent step's as the sentence the author wrote.
Flaky tests get the same block
each, folded under one summary: the run is green and the headline counts
them, so they are there for the reader who asks. Every test is folded away
under that, grouped by file worst first, each file with its counts, its
agent work, and its time. A green run is the headline, the folds, and one
line of small print. A run-level error such as `APP_UNREACHABLE` appears
above the blocks. Titles, labels, and messages are escaped and clipped, and
the body stays under GitHub's size limit: past thirty blocks the page says
how many more failed, and when room runs out the page is cut where it
stands, the folded list first, and says so. The page is
[`renderMarkdownReport`](/reference/reporters), the one the built-in
`markdown` reporter writes to `.e2e/summary.md`.

The comment carries a hidden marker naming the config's `projectId`, the
workflow, and the job, so two configs or two jobs on one pull request each
keep their own comment. Matrix replicas of one job share all three, so give
each its own `key`, which also names the comment in its headline
(`e2e chromium: 77 passed`) so the reader tells the comments apart:

```ts
reporters: ['list', github({ key: process.env.MATRIX_BROWSER })],
```

with `MATRIX_BROWSER: ${{ matrix.browser }}` in the step's `env`. Never use
the run id as the key: a rerun has a new one and would post a second comment.

## When nothing is posted

The reporter never changes the run's status or exit code. When it cannot
post, it says why in one row under the summary:

```
       Report  .e2e/report.json

       GitHub  not posted: set GITHUB_TOKEN in the step's env (GITHUB_TOKEN: ${{ github.token }}); written to the job summary
```

| Situation | What happens |
| --- | --- |
| Not on GitHub Actions | Nothing is written; the row says so. |
| A `push`, `schedule`, or `workflow_dispatch` run | The job summary is written; there is no pull request to comment on. |
| No `GITHUB_TOKEN` in the step's `env` | The job summary is written; the row shows the line to add. `GH_TOKEN` is read too. |
| A `pull_request` event from a fork | Its token is read-only, so the comment fails and the run prints the reason. A `pull_request_target` workflow has a writable token, with the care that event demands around secrets. |
| An `issue_comment` event | On a pull request's thread, the comment is posted without source links, since the checked-out commit is the default branch. |
| Missing `pull-requests: write` | The same failure, with the permission named. |

The reporter reads the token and the event payload when the run finishes,
never when the config loads, and the token never enters the report. GitHub
Enterprise Server works through `GITHUB_SERVER_URL` and `GITHUB_API_URL`.
