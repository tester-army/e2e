`@e2e-dev/github` is a reporter that posts the test results as a pull
request comment from GitHub Actions, and writes them to the job summary. A
rerun updates the same comment.

## Setup

<CodeGroup>
```bash npm
npm install --save-dev @e2e-dev/github
```

```bash pnpm
pnpm add -D @e2e-dev/github
```

```bash bun
bun add -d @e2e-dev/github
```
</CodeGroup>

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { github } from '@e2e-dev/github';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  reporters: ['list', github()],
} satisfies E2EConfig;
```

Give the workflow `pull-requests: write`. Pass `GITHUB_TOKEN` to the test
step:

```yaml title=".github/workflows/e2e.yml"
permissions:
  contents: read
  pull-requests: write

jobs:
  e2e:
    steps:
      # ...checkout, install, browsers
      - name: Run e2e
        run: npx e2e run --reporter list,junit
        env:
          GITHUB_TOKEN: ${{ github.token }}
      - name: Upload artifacts
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1
        with:
          name: e2e-artifacts
          path: .e2e/results
```

Upload the artifacts also when a retry passes: each failure's evidence
links open the run's Artifacts section. Keep `path: .e2e/results` so the
download has the same per-test directories as the report.

Source links start at the nearest directory with `.git` inside
`GITHUB_WORKSPACE`. A project below it, such as `packages/e2e-tests`, gets
links under that path. `actions/checkout` with a `path` input works too.

Run-level errors, when there are any, come before the failures. The test
list has an agent column only when the run used the agent.

The reporter shortens a large report to fit GitHub's comment limit. App text
that GitHub would turn into a mention, an issue link, or a URL shows as
code, so a screen that reads `@someone` notifies no one. The built-in
`markdown` reporter writes the same summary to `.e2e/summary.md`.

## Rerunning the failed tests

A `--last-failed` rerun updates the comment as one run with the first pass,
covering the whole suite:

```yaml
      - name: Run e2e
        run: npx e2e run || npx e2e run --last-failed
        env:
          GITHUB_TOKEN: ${{ github.token }}
```

| First pass | Rerun | Comment shows |
| --- | --- | --- |
| failed | passed | flaky |
| failed | failed | failed |
| interrupted | passed | passed |
| any other result | not run | the first-pass result |

The comment stays red while the rerun left out something it owed: a failed
test, a test that `--max-failures` stopped before it ran, or a failed
`beforeAll` or `afterAll` whose tests another filter kept out. It shows ⏹️
when the rerun left out a test that the first pass never finished. The
rerun's own exit code counts only what it ran. Each attempt's evidence links
to its own files.

## Matrix jobs

The reporter finds its comment by project, workflow, and job, which matrix
jobs share. Give each matrix entry its own `key`:

```ts
reporters: ['list', github({ key: process.env.MATRIX_BROWSER })],
```

Set `MATRIX_BROWSER: ${{ matrix.browser }}` in the step's `env`. The key
shows in the headline, such as `e2e chromium: 77 passed`. Keep it stable
across runs so a rerun updates the existing comment.

## When nothing is posted

The reporter never changes the run's status or exit code. When it can't
post, one row under the summary gives the reason:

```
       GitHub  not posted: set GITHUB_TOKEN in the step's env (GITHUB_TOKEN: ${{ github.token }}); written to the job summary
```

| Situation | What happens |
| --- | --- |
| Not on GitHub Actions | Nothing is written. The row says so. |
| A `push`, `schedule`, or `workflow_dispatch` run | The job summary is written. There is no pull request to comment on. |
| No `GITHUB_TOKEN` in the step's `env` | The job summary is written. The row shows the line to add. The reporter also reads `GH_TOKEN`. |
| A `pull_request` event from a fork | The token is read-only, so posting fails. The row says why. |
| An `issue_comment` event | On a pull request's thread, the comment has no source links, because the checked-out commit is on the default branch. |
| Missing `pull-requests: write` | Posting fails, and the reporter names the permission. |

The reporter reads the token when the run finishes, and the report doesn't
include it. On GitHub Enterprise Server, the reporter uses
`GITHUB_SERVER_URL` and `GITHUB_API_URL`.
