---
title: Reporters
description: Reporter objects in `reporters`, what they receive, and what the runner guarantees them.
---

`reporters` takes the built-in ids (`list`, `json`, `junit`, `markdown`; see
[CLI output](/reference/cli#output)) and reporter objects. Each id names a
`Reporter` the runner ships on the contract below. A reporter sees every run
event as it happens and receives the finished run, report and artifact paths
included, after the summary has printed. It lives in `e2e.config.ts`, never
on the command line.

```ts
import type { E2EConfig, Reporter } from 'e2e';
import { playwright } from '@e2edev/playwright';

const upload: Reporter = {
  name: 'upload',
  async onRunFinished(run) {
    const response = await fetch('https://example.test/runs', {
      method: 'POST',
      body: JSON.stringify(run.report),
    });
    const { url } = (await response.json()) as { url: string };
    return [{ label: 'Results', text: url }];
  },
};

export default {
  targets: [{ engine: playwright({ url: 'localhost:3000' }) }],
  reporters: ['list', upload],
} satisfies E2EConfig;
```

## The contract

```ts
interface Reporter {
  readonly name: string;
  onEvent?(event: RunEvent): void;
  onRunFinished?(run: FinishedRun, signal: AbortSignal): Promise<ReporterSummary | void>;
}

interface FinishedRun {
  readonly report: Report;                 // the report-1 document, as written
  readonly status: RunStatus;              // report.run.status
  readonly exitCode: RunExitCode;
  readonly projectRoot: string;            // what the terminal shows paths relative to
  readonly reportPath: string | undefined; // absent when the write failed
  readonly artifactsRoot: string;          // what the report's artifact paths are relative to
  readonly aiTracePath: string | undefined;
}

type ReporterSummary = readonly { label: string; text: string }[];
```

`Reporter`, `FinishedRun`, `ReporterSummary`, `Report`, `RunEvent`, and
`RunEventOf` are exported from the main entrypoint.

The built-in `junit` reporter is the smallest complete example: it reads
`run.report`, writes `junit.xml` beside `run.reportPath`, and returns one row
naming the file. `markdown` does the same with `summary.md` through
`renderMarkdownReport(report, options)`, also exported, so your own reporter
can post the same page elsewhere; `failurePages` links each block to a page
by result id. The built-in reporter also writes one page per failed or flaky
test under `failures/`, with the screen at failure inline, through
`renderFailurePage(report, result, outcome(result, groups), options)`, where
`readArtifact` supplies the screen text by report path. [`@e2edev/github`](/github) is that
reporter for GitHub Actions.

A name and at least one handler are required; anything else is
`INVALID_CONFIG`.

## The event stream

`onEvent` receives every lifecycle fact as plain JSON, the same records the
report persists, streamed while the run is going. It is the feed the `list`
reporter renders. Each event carries a `seq` and an ISO `at` timestamp.

```ts
type RunEventFact =
  | { type: 'run-started'; runId; projectId; projectRoot; artifactsRoot; ci; targets; agents?; model? }
  | { type: 'plan'; total; files: { file; target; tests }[] }
  | { type: 'notice'; target; message }
  | { type: 'setup'; step: SetupStep; state: 'started' }
  | { type: 'setup'; step: SetupStep; state: 'finished'; durationMs; outcome?: 'reused' }
  | { type: 'test-started'; testId; agent; title; file; serialId; target }
  | { type: 'step'; testId; agent; target; progress: StepProgress }
  | { type: 'test-finished'; result: RunEventResult }
  | { type: 'serial-group'; group: SerialGroupRecord }
  | { type: 'explore'; progress: ExploreProgress }
  | { type: 'run-error'; error: SerializedError }
  | { type: 'run-interrupted'; mode: 'graceful' | 'forced' }
  | { type: 'run-finished'; status; exitCode; reportPath?; aiTracePath? };
```

`explore` appears only in an `e2e explore` run: `started`, `planning`,
`step-started`, `step-finished`, `finding`, and `finished`. The record of all
of it is `run.explore` in the report.

New event types are added over time. Handle the types you know and ignore
the rest; leave the `default` branch of a `switch` empty.

`run-started` comes first and `run-finished` last. `test-finished` carries the
full result record, including every attempt's artifacts. A test pinned to
several agents starts and finishes once per agent, so key running state by
test id, target, and agent together. Secrets are redacted before events are
built. Error messages are only stripped of control characters; treat them as
untrusted.

`onEvent` must not block and must not throw. A throw quarantines the reporter
for the rest of the run. Slow work belongs in `onRunFinished`.

## The finished run

`onRunFinished` runs after `report.json` is written and the `list` summary
has printed. Every reporter's `onRunFinished` runs at once. Each is awaited
for one minute; one that takes longer, throws, or resolves with anything
other than rows is a line on stderr. A graceful interrupt (one Ctrl-C) still
runs the reporters; a forced one (a second Ctrl-C) abandons them. Nothing a
reporter does can change the run's status, exit code, or report.

The second argument is an `AbortSignal` that aborts when the budget runs out
or the run is forced to stop. Hand it to every request and timer, or an
abandoned reporter keeps the CLI alive after the run has ended.

The rows a reporter resolves with print under the `list` summary in the same
layout as `Report`; the `json` reporter does not carry them:

```
   Test Files  2 passed (2)
        Tests  6 passed (6)
     Start at  14:02:11
     Duration  8.41s
       Report  .e2e/report.json

        JUnit  .e2e/junit.xml
      Results  https://example.test/runs/0192c…
```

Artifact paths in the report are POSIX paths relative to `artifactsRoot`.
`path`, `size`, and `sha256` are optional: an artifact whose file never
appeared, or that a redaction withheld, is recorded without them. Check for
`path` before reading.

## What `--reporter` does to reporter objects

Nothing. `--reporter` replaces the built-in ids only. A config whose
`reporters` holds only objects prints nothing to the terminal.

## Where a reporter runs

In the runner's process only. Workers construct their own copy of every
reporter object but never call it, so constructing one must have no side
effects; read tokens inside the handlers. Reporters are no part of a
[trace cache key](/cache#what-must-match), so adding one leaves every
recording valid.
