e2e trusts the code you write and treats everything the app shows as
untrusted. App content can't grant the model tools, credentials, or a
larger budget.

## How secrets stay out of the model

A `Secret` is a handle with no plaintext accessor. The model sees only its
name and purpose. When the model asks to fill one, the runner checks the
field and types the value itself.

After a secret fill, the rest of the attempt has no screenshots, because
the app could show the value anywhere. Every known secret value becomes
`<secret:name>` in model input, reports, console output, and text
downloads.

## What can still leak

Redaction matches strings, and only a secret fill turns screenshots off:

- **Video and binary downloads.** Neither is masked. If the test typed a
  password, check them before you share them.
- **`command.log`.** It holds your app's stdout and stderr verbatim. Keep
  secrets out of your app's output.
- **Transformed values.** The last four characters of a key, or its base64,
  pass through. Assert the outcome, not the secret.
- **Values not filled as a secret.** A secret passed as a plain string, or a
  sign-in that sets a cookie, leaves screenshots on. Only a configured
  secret's value is redacted.
- **Request credentials.** `basicAuth` answers a `401` from any origin.
  `headers` reach every host under a shared domain such as `vercel.app`.
- **Committed recordings.** Cache entries store typed values verbatim, except
  secret fills. They aren't signed and replay with your permissions, so
  review them as you would test code.

[Where redaction stops](/reference/security#where-redaction-stops) lists
every case.

## What the model sees and does

The model sees your instruction, the screen as an accessibility tree, the
redacted URL, and records of earlier steps in the test. It gets a masked
screenshot when it asks for one or a step sets `vision`.

The model acts only through tools. The runner checks each call against a
closed schema before it runs, and never evaluates model text as code. A call
that breaks a rule, such as a navigation to `file:`, fails with
`POLICY_DENIED`. There is no origin allowlist: the agent can follow the app
to another site and use the step's secrets there.

## What runs with your permissions

Your tests, config, engines, tools, reporters, stores, secret providers, and
app commands run with your operating-system permissions, unsandboxed. Run
untrusted pull request code in an external sandbox with no secrets or write
tokens.

## What leaves your computer

A run connects to your model provider, the app under test, and, unless you
opt out, [telemetry](/telemetry) at `eu.i.posthog.com`. There is no crash
reporting or update check. Integrations such as Kernel, EAS Simulators, and
smol add their own destinations, listed with the rest under
[Outbound connections](/reference/security#outbound-connections).

## Report a vulnerability

Report privately through
[GitHub security advisories](https://github.com/tester-army/e2e/security/advisories/new)
or by mail to security@tester.army. The
[security policy](https://github.com/tester-army/e2e/blob/main/SECURITY.md)
states response times and supported versions.
